# 用 Agent 编码的完整流程：从目标到测试，可日志、可追溯、可审计

## 一句话结论

Agent 编码的本质不是「把需求丢给大模型然后等代码」，而是把一次开发任务拆成一条**有明确边界、可验证、可回放**的流水线：目标 → 需求 → 能力拆解 → 模块设计 → 数据设计 → 流程设计 → 接口设计 → 实现任务 → 测试验证。每一步既是产物的输入，也是下一个 Agent 的上下文；而日志、Trace 与审计字段应伴随整条流水线落地，让「Agent 做了什么、为什么这样做、结果是否可接受」随时可查。

## 问题与场景

让 Agent 直接写代码时最常见的失败，不是模型不会写代码，而是**上下文和验收标准错位**：

- 只给一句话需求，Agent 按自己的假设补全，交付后发现方向完全不对；
- 设计、数据、接口这些决策散落在多轮对话里，换一个 Agent、换一次会话就无法复现；
- Agent 改动了文件，但没人知道它改了什么、依据是什么、是否经过测试；
- 一旦出错，只能对着最终代码反推，无法回答「这一步当初为什么这么设计」。

要解决这些问题，需要把编码过程显式建模：先拆步骤、再定每步产物、最后把可观测性注入每一步。以下是从目标到验证的九步流水线，以及每步应当产出的「可审计证据」。

## 九步流水线

```text
目标 ──> 需求 ──> 能力拆解 ──> 模块设计 ──> 数据设计
                                        │
流程设计 <── 接口设计 <──────────────────┘
                                        │
                                        └──> 实现任务 ──> 测试验证
```

每一步的输入输出都应该写进一个结构化的任务上下文（通常是一个 Markdown 计划文件或任务清单），它是 Agent 的「记忆」，也是审计的依据。

### 1. 目标（Goal）

先用一两句话描述**要达成什么业务结果**，而不是「做什么功能」。例如「用户下单后，库存服务能在 5 秒内收到扣减事件」而不是「写一个发布消息的函数」。目标要可度量，否则后续每一步都没有验收基线。

### 2. 需求（Requirements）

把目标翻译成可测试的需求条目，区分功能需求与约束：

- 功能：触发条件、输入、输出、异常行为；
- 约束：技术栈、性能指标（如 P95 延迟）、合规要求、幂等要求；
- 非目标：明确「这一版不做 X」，避免 Agent 自由发挥。

需求条目编号（如 `REQ-01`）很重要：后面的设计、任务、测试都应引用它，形成需求到代码的可追溯链。

### 3. 能力拆解（Capability Breakdown）

把需求拆成 Agent 或系统需要具备的**原子能力**，例如「校验订单状态」「持久化事件」「投递消息」「重试与死信」。这一层回答「需要哪些能力」，下一层才回答「能力怎么实现」。能力之间应尽量正交，便于后续映射到模块和测试。

### 4. 模块设计（Module Design）

把能力归并成模块/服务，定义模块职责边界与依赖方向。产出模块清单、模块间关系图和每个模块的对外职责。例如「下单模块负责业务校验」「Outbox Relay 负责投递」——这里最容易联想到经典的 [Transactional Outbox](/daily/2026/08/2026-08-06-daily-transactional-outbox) 模式：业务写库与事件落表在同一个事务里，投递交给独立进程，模块边界天然清晰。

### 5. 数据设计（Data Design）

定义实体、字段、状态机、索引与幂等键。数据设计决定了后面能否正确实现，也决定了审计能记录什么：

- 每张表/每个实体的字段与类型；
- 状态机（如 `pending → in_flight → sent`）及状态迁移规则；
- 幂等键与唯一约束；
- 与审计相关的字段：`created_at`、`created_by`、`updated_at`、`trace_id`、`attempt`、`last_error`。

以 Outbox 为例，事件表里同时保存 `attempt` 和 `last_error`，就是「数据设计服务可观测性」的典型做法。

### 6. 流程设计（Flow Design）

描述一次业务操作经过哪些步骤、哪些同步哪些异步、失败如何回退。用泳道图或顺序图表达，并显式标出**日志与 Trace 埋点**的位置。这一步决定跨模块、跨消息队列的因果关系能否串起来。

### 7. 接口设计（Interface Design）

定义模块间、服务间的接口契约：方法签名、参数、返回、错误码、超时与重试策略。接口契约要写在实现之前，让实现任务可以并行且互不猜忌。同时约定上下文传播方式——参考 [OpenTelemetry 的 W3C Trace Context](/daily/2026/08/2026-08-05-daily-opentelemetry)：

- HTTP/gRPC：在请求头携带 `traceparent`；
- 消息队列：在消息 Header 中注入 `traceparent`，消费者提取后建立 process Span；
- 业务身份（`run_id`、`order_id`）与 Trace 上下文分离，前者用于审计与幂等，后者用于关联遥测。

### 8. 实现任务（Implementation Tasks）

把模块、接口、数据落成一组**带验收条件的任务**。每个任务应引用需求编号、涉及的接口和数据表，并注明「需要打什么日志、建什么 Span、写什么审计记录」。任务粒度以能被单个测试覆盖为准。

### 9. 测试验证（Test Verification）

每个任务对应至少一种验证方式：单元测试、集成测试、契约测试、端到端测试。验证不是只看「测试通过」，还要验证可观测性本身：手动或自动断言 Trace 结构完整、关键日志存在、审计记录落库。这一步把「功能正确」和「可追溯」一起验收。

## 如何在每一步加入日志、追溯与审计

可观测性不应该在实现阶段才想起，而应该从第 4 步设计时就确定埋点位置。按生命周期和用途可以把日志分成四层，它们解决的问题不同，保存策略也不同：

| 类型 | 主要解决的问题 | 是否长期保存 |
| --- | --- | ---: |
| 运行日志 Application Log | 程序为什么报错 | 短/中期 |
| Trace / Span | 这次请求经过了哪些模块 | 中短期 |
| Audit Log | 谁修改了什么 | 长期 |
| Business / Provenance Event | 业务对象为什么变成现在这样 | 长期 |

- **运行日志**解决排障，量大、噪音多，通常按容量或天数滚动删除（如 7～30 天），只对错误和高价值事件做留存；
- **Trace / Span** 解决链路定位，随采样率与后端保留周期而定（如 30 天），超期后只保留聚合指标；
- **Audit Log** 解决「谁在什么时候做了什么」，是合规和追责的依据，必须长期保留且不可篡改；
- **Business / Provenance Event**（来源事件）回答「业务对象为什么变成现在这样」，是数据血缘与回放的基石，与业务数据同生命周期，长期保留——这正是 [Transactional Outbox](/daily/2026/08/2026-08-06-daily-transactional-outbox) 中事件记录扮演的角色。

四层之间用 `trace_id`、`run_id`、`req_id` 互相串联，但存取路径严格区分：运行日志进日志系统、Trace 进 Trace 后端、Audit 与 Provenance Event 进独立的审计/事件存储。这样既能按需扩容每层的容量，也能避免把排障细节混进不可篡改的审计库里。

在 Agent 编码的场景里，三层工具的分工如下。

| 类型 | 回答的问题 | 落地方式 | 关联字段 |
| --- | --- | --- | --- |
| 日志（Log） | 某时刻发生了什么具体事件 | 结构化日志，带上 `run_id`、`trace_id`、事件名与错误分类 | `trace_id`、`span_id`、`run_id` |
| 追溯（Trace） | 这次任务经历了哪些步骤、各花了多久 | 在业务边界建立 Span，跨消息队列传播上下文 | `trace_id`、`span_id`、`parent_id` |
| 审计（Audit） | 谁在什么时候基于什么依据做了什么、结果如何 | 把关键决策与副作用落库，字段带业务键与操作者 | `run_id`、`request_id`、`action`、`created_by` |

### 在各阶段的具体做法

- **目标与需求阶段**：为每个需求条目分配 `req_id`，作为后续一切追溯的起点。需求清单本身落库或进版本管理，记录谁提出、何时修改。
- **设计阶段**：模块、数据、接口设计都带版本号。接口契约变更要有审计记录（旧版本、新版本、变更原因），避免 Agent 静默破坏兼容。
- **实现阶段**：每个实现任务在开始时建立 `agent.run` Span，结束时记录 `req_id`、改动文件列表、测试结果摘要。Agent 的每次「思考摘要」可写入日志，但**完整 Prompt 与模型输出不进 Span 属性**，参考 [OpenTelemetry 的隐私边界](/daily/2026/08/2026-08-05-daily-opentelemetry)：默认不采集，字段白名单优先。
- **副作用操作**：凡有副作用的调用（发布消息、改库存、写库），用 `operation.id` 或幂等键记录，并写成审计事件。以 [Transactional Outbox](/daily/2026/08/2026-08-06-daily-transactional-outbox) 为例，投递成功与否落在 `status`、`attempt`、`last_error`，死信要有告警与重放入口——这就是数据层提供的审计能力。
- **测试验证阶段**：测试通过后，把 Trace 结构（关键 Span 是否齐全、上下文是否跨队列传播成功）纳入断言；审计表能按 `req_id` 或 `run_id` 回溯出完整的「需求 → 设计 → 实现 → 验证」链条。

```text
需求 req-01
  └─> 设计 v2（变更记录：v1→v2，原因：去掉同步投递）
       └─> 任务 task-07（Agent.run span，改动 file A/B，测试 3 通过）
            └─> 审计行：{ run_id, req_id, action: "implement", result: "pass" }
```

这条链就是「审计」的最终形态：任何人（或另一个 Agent）都能沿着它复现并评估一次开发决策。

## 实践建议

1. **把流水线当成可复用上下文，而不是一次性对话。** 九步产物写进一个结构化的计划文件（如 `PLAN.md`），每个 Agent 任务开始时先加载它。这样换会话、换模型都能保持决策一致。
2. **每步都要有明确验收物。** 没有验收物的步骤（比如「再想想」）不要进入下一步；Agent 的自由发挥空间只应存在于「实现任务」内部，设计层面要收敛假设。
3. **需求编号贯穿始终。** 设计、任务、测试、审计都引用需求编号，可追溯性从一句口号变成可以查询的约束。
4. **可观测性从设计阶段开始设计。** 埋点位置、上下文传播、幂等键在流程设计与数据设计里就确定，不要等实现完再补。
5. **区分遥测、审计与调试信息。** `trace_id` 用于关联链路，业务键（`req_id`、`run_id`）用于审计与幂等，完整 Prompt/输出属于调试信息且要受控留存。三者混用会让隐私、采样与审计边界全部失守。
6. **测试同时验证功能与可观测性。** 断言关键 Span 存在、日志字段齐全、审计行可回查，否则「有 Trace」和「有用」是两回事。
7. **审计记录要不可变。** 关键决策记录只增不改，修改通过追加新版本体现，避免事后被覆盖导致无法还原事实。
