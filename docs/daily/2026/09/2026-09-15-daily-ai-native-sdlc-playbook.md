# AI-Native SDLC：当写代码不再是研发的瓶颈

## 一句话结论

AI-Native SDLC 的重点不是让 Agent 替人完成需求、编码、测试和上线，而是把整个研发流程改造成一个由版本化工件驱动、由自动反馈加速、由确定性控制约束，并由人类对关键判断负责的闭环。当代码可以在数小时内生成，真正需要重构的是代码左右两侧仍以人工速度运行的计划、评审、测试、部署和维护流程。

## 1. 原文提出了什么问题？

Anthropic 在 [The AI-Native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook) 中提出了一个很直接的判断：**代码不再是软件交付中唯一或最大的瓶颈**。

传统 SDLC 围绕一个前提建立：写代码昂贵而缓慢，所以组织需要通过 PRD、估算、阶段评审和层层交接，确保进入实现阶段的工作已经充分对齐。但 Agent 显著压缩 Build 阶段后，其他阶段并不会自动加速：

- 需求仍然等待会议澄清；
- 安全团队仍然逐项排队审查；
- QA 仍然在阶段末集中验证；
- 发布仍然等待固定窗口和人工审批；
- 生产事故仍然依靠人发现、分析并重新创建任务。

这时，单纯提高代码产量可能不会缩短端到端交付时间，反而会更快地制造 PR、测试和安全审查队列。局部效率的提升，把压力转移给了相邻环节。

因此，衡量 AI 编码价值时，不能只看生成了多少代码或单个任务节省了多少时间，还要看：

- 从提出意图到上线的总周期；
- 首次 CI 通过率与需求返工率；
- PR 和安全审查的等待时间；
- 变更失败率与恢复时间；
- 生产问题重新进入开发流程的速度。

## 2. 六个阶段如何变化？

原文仍然沿用 Plan、Design、Build、Test、Deploy、Maintain 六个阶段，但不再把它们看作由不同角色顺序交接的瀑布，而是看作一组可以自动传递、持续反馈的工作循环。

| 阶段 | AI-Native 的变化 | 主要产物或证据 |
| --- | --- | --- |
| Plan | 发起人与 Agent 澄清问题、范围、约束和成功标准 | `intent.md` |
| Design | Agent 依据组织的安全、合规、品牌和 UX 规则生成规格，并标记冲突 | `spec.md` |
| Build | 工程师先审计划，再让 Agent 实现；项目知识被写成机器可读规则 | `plan.md`、代码、测试、`CLAUDE.md`、Skills |
| Test | Agent 在实现过程中反复运行构建、测试、Lint 和视觉检查 | 测试输出、截图、持续 Evals |
| Deploy | Agent 执行一致的 PR 审查和流水线任务，人类保留高风险批准 | PR、Review Findings、审批记录 |
| Maintain | 生产异常触发确定性检测和 Agent 诊断，结果重新成为开发意图 | 事故记录、新的 `intent.md`、回归 Eval |

这条链可以简化为：

```text
intent.md
  -> spec.md
  -> plan.md
  -> code + tests
  -> PR + review findings
  -> deploy + production signals
  -> new intent.md
```

每个阶段结束时提交一个下一阶段既能阅读又能执行的工件。Git 历史则记录谁提出了什么、Agent 生成了什么、谁修改和批准了结果。

## 3. Markdown 不是目的，稳定的交接协议才是

我认为这份 Playbook 最重要的设计不是规定团队必须创建几个 `.md` 文件，而是给阶段之间建立了**显式的中间表示**。

传统流程中的事实经常散落在会议、Jira、Figma、聊天记录和代码里。Agent 如果只看到最后的工单和当前仓库，就很难知道一个设计为何存在，也无法检查实现是否偏离原始目标。`intent.md`、`spec.md` 和 `plan.md` 把原本留在不同人脑中、不同会话里的决策外显出来，让人和 Agent 可以基于同一份上下文协作。

但 Markdown 本身并不解决治理问题。企业已经使用 Jira、ServiceNow 或专门的需求系统时，更关键的是明确每类工件的 **Source of Truth**：

- 仓库是事实来源，外部系统引用文件和 Commit SHA；
- 外部系统是事实来源，Agent 通过 MCP 读取并写回；
- 迁移期至少建立双向链接，避免两份记录无关联地各自演化。

如果没有唯一事实来源或可靠链接，AI 只会更快地执行彼此矛盾的需求。

## 4. Agent 能力与控制必须分层

原文区分了三类容易混淆的机制：

### `CLAUDE.md`：项目上下文

它记录构建命令、架构、编码约定和常见错误，相当于把“新成员第一天必须知道的事”放进仓库。它适合项目局部知识，并且应该短小、准确、持续维护。

### Skills：组织级建议

Skills 将安全标准、API 规范、品牌或合规政策转成可复用指令。它能让 Agent 更可能在生成规格和代码时主动应用政策，但仍然属于自然语言控制，可能不触发、被误解或与其他规则冲突。

### Hooks、CI 与权限：确定性边界

不能被违反的规则必须进入确定性系统，例如：

- Hook 禁止读取凭据或修改受保护路径；
- CI 强制执行测试、Lint、静态分析和依赖扫描；
- 沙箱和网络策略限制 Agent 的文件、命令与外部访问；
- 分支保护禁止 Agent 直接写入主分支；
- 生产部署要求指定人员批准。

可以将三者概括为：**上下文告诉 Agent 项目是什么，Skill 告诉 Agent 应该怎么做，Hook 和 CI 决定哪些事情绝对不能做。** Prompt 不是安全边界，也不能代替权限系统。

## 5. 测试对象从代码扩展到“生产代码的系统”

传统测试主要验证代码，AI-Native SDLC 还需要验证产生代码的配置。模型升级、Prompt 调整、`CLAUDE.md` 或 Skill 变化，都可能让 Agent 的行为发生回归。

原文建议从真实任务中建立 Eval Suite，在 Agent 配置变化时持续检查：

- 能否完成预期行为；
- 是否通过构建、测试和 Lint；
- 是否遵守安全与合规政策；
- 是否重现过去在生产中发生过的问题。

这意味着测试分成两层：

```text
代码测试：这次实现是否正确？
Agent Eval：换模型或修改规则后，Agent 是否仍能稳定地产生正确实现？
```

事故也不应只留下复盘文档。每次有代表性的生产失败都应转成测试或 Eval，使修复真正成为系统的长期记忆。

## 6. 人类没有退出，而是离开机械路径

AI-Native 并不等于无人审批。原文给出的边界很清楚：Agent 可以行动到生产门之前，但不能自行越过生产门。

人类注意力应从逐行观察 Agent 编辑文件，转向更少但更重要的问题：

- 这个问题是否值得解决；
- `intent.md` 是否准确表达了业务目标；
- 规格中的风险和政策冲突能否接受；
- 计划是否覆盖了关键边界；
- 高风险变更是否可以发布；
- 生产异常究竟需要修复、安排还是忽略。

换句话说，Agent 承担可重复、可验证和可回滚的动作，人类承担意图、取舍、授权和责任。人工判断仍然在闭环之上，只是不应重新成为每个低风险动作的同步阻塞点。

## 7. 最值得借鉴的是渐进式落地

这套流程不适合一次性全自动化。更稳妥的采用顺序是：

1. 明确数据边界、权限、审批要求和事实来源。
2. 建立简短的 `CLAUDE.md`，把 Build、Test、Lint 收敛成一键命令。
3. 为一个高频政策建立 Skill，并为不可违反的部分增加 Hook 或 CI 检查。
4. 从真实任务开始使用 `intent.md -> spec.md -> plan.md`，先由人手动触发各阶段。
5. 在反馈循环可靠后，再开放 Auto Mode、并行 Worktree、Subagent 和 AI PR Review。
6. 最后才连接生产监控，并且只允许 Agent 开 PR 或执行预先批准、反复演练过的回滚 Runbook。

这里的成熟度不应该用“Agent 能自动运行多久”衡量，而应该用“在减少人工机械操作后，质量、审计和恢复能力是否仍然成立”衡量。

## 8. 我的理解

这份 Playbook 描述的不是一条更快的流水线，而是一个反馈控制系统：版本化工件传递状态，测试和 Evals 提供反馈，Hooks 和权限限定可行动范围，生产信号重新生成意图，人类则负责设定目标并批准不可逆的高风险决策。

它也提醒了一个容易被忽略的问题：**生成代码的能力越强，组织越不能依赖人工逐项兜底。** 否则 AI 提高的只是局部产量，最终会以更长的评审队列、更草率的批准和更高的治理成本偿还。

真正的 AI-Native SDLC，不是让机器接管整个软件生命周期，而是让生命周期中的信息可以被机器读取、结果可以被机器验证、风险可以被确定性规则约束，并让有限的人类注意力集中在真正需要判断的地方。
