# 模型策略、成本与性能工程

> 生产级 Agent 不应把“调用最强模型”作为默认架构，而应根据任务、步骤、风险和预算动态选择能力，并用评估证明这种选择。

## 1. 模型策略解决什么问题

Agent 中不同步骤的需求差异很大：

- 意图分类需要低延迟；
- 复杂规划需要强推理；
- 文档抽取需要长上下文与结构化输出；
- 工具调用需要稳定的 Schema 遵循；
- 高风险决策需要更强模型或人工复核；
- 批量后台任务更关注吞吐和成本。

模型策略需要同时优化：

```text
质量 + 延迟 + 成本 + 可用性 + 安全
```

这些目标通常互相制约，必须先定义业务 SLO 和最低质量门槛。

## 2. 建立 Model Capability Profile

不要只记录模型名称，应为候选模型维护能力档案：

- 任务成功率和关键分组表现；
- 推理、编码、视觉、工具调用能力；
- 结构化输出稳定性；
- 上下文窗口与有效长上下文表现；
- 输入、输出和缓存价格；
- 首 Token 延迟与生成速度；
- Rate Limit、区域和数据政策；
- 已知失败模式；
- 当前 Snapshot 与弃用日期。

模型标称参数不能代替在自身业务评估集上的测量。

## 3. Model Routing

### 3.1 静态路由

按固定步骤分配模型：

```text
分类 → 小模型
规划 → 强推理模型
执行 → 工具调用模型
摘要 → 低成本模型
```

优点是可预测、易测试，适合作为第一版策略。

### 3.2 动态路由

根据输入和运行状态选择模型：

- 请求复杂度；
- 上下文长度；
- 是否涉及高风险操作；
- 当前预算和剩余时间；
- 用户服务等级；
- 小模型置信度；
- 历史失败次数；
- 模型实时可用性。

Router 本身也需要评估。错误路由节省的成本可能低于质量下降和重试成本。

### 3.3 Cascade

先使用低成本模型，未通过验证时升级：

```text
小模型 → 外部验证
          ├── 通过 → 返回
          └── 失败 → 强模型 → 再验证
```

升级条件必须由可观察信号驱动，例如 Schema 失败、引用不足、测试失败或高风险标签，而不是让模型只凭自我感觉判断。

### 3.4 Fallback

Fallback 用于可用性，而不是默认的质量补丁：

- 同能力模型跨供应商切换；
- 主模型限流时切换备用模型；
- 降级为只读或部分结果；
- 关闭非必要步骤；
- 超过预算时请求用户选择。

备用模型必须提前完成兼容性测试，尤其是 Prompt、Tool Schema、上下文长度和安全行为。

## 4. 任务分解与模型分配

一个 Agent Run 可以分为：

```text
理解 → 检索 → 规划 → 执行 → 验证 → 表达
```

应把高能力模型集中在“高判断密度”节点，而不是让每个步骤都使用同一模型。

例如：

- 确定性过滤由程序完成；
- 简单分类由小模型完成；
- 复杂计划由强模型完成；
- 格式校验由 Schema 完成；
- 最终高风险判断由强模型和人工共同完成。

模型用于概率判断，程序用于确定性工作。

## 5. 成本模型

单次 Run 的成本不只是输入和输出 Token：

$$
C_{run} =
\sum C_{model}
+ \sum C_{tool}
+ C_{retrieval}
+ C_{compute}
+ C_{storage}
+ C_{human}
+ C_{retry}
$$

其中模型成本可近似为：

$$
C_{model} =
T_{input}P_{input}
+ T_{output}P_{output}
+ T_{cached}P_{cached}
$$

业务上更重要的指标通常是：

```text
Cost per Verified Successful Task
= 总成本 / 通过外部验证的成功任务数
```

单次调用更便宜，但失败和重试更多，不一定降低最终成本。

## 6. Token 与 Context 成本优化

### 6.1 先优化输入质量

- 只加载当前步骤需要的资料；
- 删除重复历史和无用 Tool Result；
- 使用结构化状态代替整段对话；
- 对大型结果分页、过滤和聚合；
- 固定稳定前缀以提高 Prompt Cache 命中；
- 将长资料保存为 Artifact，按需读取。

### 6.2 控制输出

- 规定结构和最大长度；
- 要求工具参数而不是自然语言复述；
- 中间节点只输出下游需要的数据；
- 让程序生成可确定的模板和格式；
- 避免多个 Agent 重复总结同一资料。

### 6.3 Context Compaction

长任务中可采用：

```text
最近事件保留原文
+ 关键决策结构化保存
+ 历史内容压缩
+ 大型 Artifact 保存引用
```

压缩必须保留目标、约束、未完成事项、关键证据和外部副作用，不能只生成一段宽泛摘要。

## 7. Latency Engineering

总延迟可以近似拆为：

$$
L_{total} =
L_{queue}
+ L_{retrieval}
+ \sum L_{model}
+ \sum L_{tool}
+ L_{validation}
$$

主要优化手段：

- 并行执行相互独立的检索和只读工具；
- 在满足质量门槛时使用更快模型；
- 减少串行模型轮次；
- 为慢工具设置超时和降级；
- 复用连接和缓存稳定结果；
- 流式输出用户可见内容；
- 预计算常用 Embedding 和摘要；
- 把非关键工作放到后台。

并行化需要考虑 Rate Limit、共享状态和成本放大，不能将所有节点无条件并发。

## 8. 缓存策略

可缓存对象包括：

- 稳定 Prompt 前缀；
- Embedding；
- 检索结果；
- Tool 元数据；
- 确定性工具结果；
- 模型响应；
- 已验证的子任务结果。

缓存键至少应包含：

```text
输入摘要 + 模型版本 + Prompt 版本
+ Tool/数据版本 + 权限范围 + 租户
```

还要定义：

- TTL；
- 主动失效事件；
- 是否允许跨用户共享；
- 陈旧数据容忍度；
- 缓存命中后的审计记录。

对个人数据、高时效数据和权限敏感结果，缓存错误可能比缓存缺失更危险。

## 9. Throughput、Rate Limit 与 Budget

系统需要同时实施：

- 全局并发上限；
- 租户级 Token Bucket；
- 单 Run 最大步骤与 Token；
- 单工具调用次数上限；
- 单任务货币预算；
- 模型供应商限流感知；
- 优先级队列和公平调度。

预算应能沿 Graph 传播：

```json
{
  "remaining_tokens": 32000,
  "remaining_cost": 0.80,
  "deadline_ms": 18000,
  "remaining_steps": 6
}
```

节点根据剩余预算选择模型、上下文和是否执行可选步骤。

## 10. Quality–Cost–Latency 决策

策略选择应以 Pareto Frontier 为目标：如果一个方案质量更低、成本更高、延迟更长，就没有保留价值。

比较模型策略时至少报告：

| 策略 | 成功率 | P95 延迟 | 成功任务成本 | 安全失败率 |
| --- | ---: | ---: | ---: | ---: |
| 全部强模型 |  |  |  |  |
| 静态分层 |  |  |  |  |
| 小模型级联 |  |  |  |  |
| 动态路由 |  |  |  |  |

最终选择取决于业务约束。例如，高风险写操作可能优先质量和安全，而交互式搜索建议更强调首 Token 延迟。

## 11. 模型、Prompt 与组件版本管理

一次运行应记录：

- provider、model family、snapshot；
- 推理强度、温度和输出限制；
- Prompt 版本；
- Tool Schema 与实现版本；
- Graph 版本；
- Memory Schema 与策略版本；
- Router 和 Fallback 策略版本。

不要直接使用指向未知未来版本的别名承担关键生产任务。升级时应：

1. 固定新 Snapshot；
2. 运行离线 Capability、Regression 和 Safety Eval；
3. 检查 Tool 与结构化输出兼容性；
4. Shadow 真实流量；
5. Canary 分组放量；
6. 监测质量、延迟、成本和拒绝率；
7. 保留旧版本和快速回滚。

## 12. 性能测试

模型策略测试应覆盖：

- 冷启动与热缓存；
- 短、中、长上下文；
- 简单与复杂任务；
- 正常负载、峰值和突发；
- 工具延迟与模型限流；
- 供应商故障切换；
- 多轮级联最坏路径；
- 不同租户和优先级的公平性。

重点观察分布而不是平均值：

- TTFT；
- Tokens per Second；
- 端到端 P50/P95/P99；
- 队列等待时间；
- 每个节点成本；
- 超预算率；
- Fallback 和升级比例。

## 13. 常见误区

### 13.1 所有步骤都使用最强模型

这会放大成本和延迟，也掩盖可由程序解决的确定性问题。

### 13.2 只按 Token 单价选模型

低价模型可能需要更多轮次、更多重试和人工介入。应比较成功任务成本。

### 13.3 上下文窗口越大越好

更长上下文会增加成本、延迟和噪声，关键是最小但充分的高信号上下文。

### 13.4 Fallback 等于随意替换模型

不同模型对 Prompt、工具和安全策略的响应不同，必须预先评估兼容性。

### 13.5 优化平均延迟

用户体验和容量问题通常由长尾决定，应重点关注 P95、P99 和最坏级联路径。

## 14. 实践检查清单

- 是否为每个任务节点定义质量、延迟和成本要求？
- Router 和 Cascade 是否经过独立评估？
- 是否计算 Cost per Verified Successful Task？
- 是否限制 Run 的步骤、Token、成本和截止时间？
- Context 是否按需选择、压缩和缓存？
- 缓存键是否包含版本、权限和租户？
- Fallback 模型是否做过兼容性与安全测试？
- 是否监控 TTFT、P95/P99、升级率和超预算率？
- 每次运行能否追踪完整组件版本？
- 模型升级是否经过离线评估、Shadow、Canary 和回滚？

## 15. 总结

好的模型策略不是选择一个永久最优模型，而是建立一个可测量、可路由、可降级和可演进的能力组合：

```text
任务分层
+ 能力画像
+ 动态预算
+ 外部验证
+ 渐进发布
```

成本和性能优化必须在质量与安全门槛之内进行，最终目标是以可接受的延迟和成本，稳定完成经过验证的真实任务。
