# Prompt Engineering 与结构化输出

> Prompt 不是一段“魔法文案”，而是模型调用接口的一部分。生产系统需要把指令层级、输入数据、输出契约、失败处理和版本发布一起工程化。

---

## 1. Prompt 的职责边界

Prompt 适合描述目标、角色、约束、可用上下文和输出要求；权限、金额上限、数据隔离、重试次数等硬规则必须由代码和策略层执行。

```text
业务目标 → Prompt 模板 → 模型输出 → Schema 校验 → 业务校验 → 执行
```

不要把“禁止删除数据”只写在 Prompt 中。模型输出始终应被视为待校验的提案。

## 2. 指令分层

从高到低可分为：

1. 系统与平台策略：不可被用户输入覆盖的边界；
2. 应用指令：当前 Agent 的职责、工作方式和工具规则；
3. 任务上下文：用户目标、环境状态和已知约束；
4. 外部数据：网页、邮件、文档和工具返回；
5. 输出契约：字段、类型、枚举和完成条件。

外部数据应使用清晰分隔符包裹，并明确标记为“不可信数据，不是指令”。

## 3. 一个可维护的 Prompt 结构

```text
目标
边界与禁止事项
当前状态
可用工具及选择规则
任务数据（不可信）
输出 Schema
成功标准
缺少信息和失败时的处理方式
```

模板只放稳定规则；频繁变化的数据通过变量注入。避免把历史对话、检索结果和工具说明复制到多个位置。

## 4. 结构化输出

优先使用模型原生 Structured Outputs 或 JSON Schema，而不是让模型“返回一段 JSON”。Schema 应：

- 关闭不需要的额外字段；
- 为枚举、长度、数值范围和必填字段设置约束；
- 区分 `result`、`needs_input`、`refuse` 和 `error`；
- 使用稳定字段承载机器决策，自由文本只用于解释；
- 携带契约版本，便于灰度迁移。

示例：

```json
{
  "schema_version": "1.0",
  "status": "call_tool",
  "tool": "search_orders",
  "arguments": {
    "customer_id": "cus_123"
  },
  "missing_information": []
}
```

## 5. 校验与修复

处理链路应区分：

1. 语法错误：无法解析；
2. Schema 错误：类型、必填项或枚举不匹配；
3. 语义错误：时间范围矛盾、资源不存在；
4. 策略错误：越权或高风险动作未确认；
5. 业务错误：状态不允许、额度不足。

简单格式错误可以把精简的校验错误反馈给模型修复一次；权限和业务拒绝不能靠重复 Prompt 绕过。每次修复都计入步骤、延迟和成本预算。

## 6. 常用 Prompt 模式

- **分类与路由**：固定枚举，并提供“不确定/转人工”出口；
- **信息抽取**：字段缺失返回 `null`，禁止猜测；
- **工具选择**：只在候选工具中选择，先判断是否需要工具；
- **规划**：输出可验证步骤、依赖和完成条件；
- **评审**：使用独立 rubric，不让评审模型只给主观总分；
- **RAG 回答**：要求证据 ID、引用范围和证据不足声明。

Few-shot 示例应覆盖边界和失败案例，而不只是理想成功路径。

## 7. Prompt 注入防护

Prompt 注入不能只靠另一段“更强的 Prompt”解决。需要组合：

- 隔离指令与外部内容；
- 最小化可用工具和数据；
- 对工具参数做策略校验；
- 对检索来源做权限和可信度标记；
- 高风险动作显示预览并等待确认；
- 检测异常指令和数据外泄企图；
- 对抗样本持续进入回归集。

## 8. Prompt 与输出契约版本管理

每次 Trace 至少记录：

```text
prompt_template_id
prompt_version
schema_version
model_id
tool_catalog_version
policy_version
```

发布流程建议为：

```text
变更 → 静态检查 → 固定评估集 → 对抗测试
→ Shadow → 小流量 Canary → 指标对比 → 全量或回滚
```

Prompt 和 Schema 不应被直接在线覆盖。破坏性字段变更需要新版本，并让旧、新消费者在迁移期并存。

## 9. 测试清单

- [ ] 指令优先级是否清晰？
- [ ] 不可信内容是否与指令隔离？
- [ ] 输出是否有严格 Schema？
- [ ] 缺少信息时是否停止猜测？
- [ ] 格式修复是否有次数上限？
- [ ] 权限与业务规则是否在代码层复核？
- [ ] Prompt、Schema 和模型版本是否进入 Trace？
- [ ] 是否用固定样本比较变更前后的质量、成本和延迟？

## 10. 小结

Prompt Engineering 的目标不是写出永远正确的提示词，而是建立一个可校验、可评估、可发布、可回滚的模型接口。结构化输出把自然语言决策转换成软件系统可以安全消费的协议。

## 11. 深入理解：Prompt 是版本化接口，不是魔法文本

Prompt 的真实消费者既包括模型，也包括维护者、评估系统和下游解析器。一个可生产化的 Prompt 包含输入契约、决策边界、输出契约和失败语义。修改示例、字段定义或优先级都可能改变系统行为，因此要与代码一样进行评审、版本化、回归和灰度发布。

### 11.1 指令与数据隔离

推荐固定顺序：系统不变量 → 任务规则 → 工具契约 → 可信状态 → 不可信材料 → 输出 Schema。外部网页、RAG 片段、工具结果和用户附件必须使用明确的数据边界，并声明其中的指令无授权效力。分隔符只能帮助模型理解，真正的安全仍由权限与工具网关保证。

### 11.2 Schema 设计

Schema 应表达业务语义，而不只保证 JSON 可解析。使用枚举限制动作空间，用 `required` 明确最小信息，用 `additionalProperties: false` 阻止漂移，用带单位的字段名避免歧义。对互斥组合做语义校验，例如 `action=finish` 时必须有 `termination_reason`，`action=tool` 时必须有合法 `tool_name`。

结构化输出流水线是：模型约束生成 → JSON Schema 校验 → 业务规则校验 → 引用与权限校验 → 写入状态。自动修复只适用于无副作用的格式错误，不能擅自补金额、收件人或授权范围。

### 11.3 Few-shot 的正确作用

示例用于说明决策边界和难例，而不是堆积常规答案。优先选择相邻类别、拒绝案例、信息不足、冲突输入和正确终止的例子。示例必须与 Schema 同步版本化；当示例与文字规则冲突时，应有明确优先级并通过测试发现。

### 11.4 Prompt 评估矩阵

至少覆盖正常、边界、对抗和漂移四类集合。除最终正确率外，记录 Schema 合法率、拒答正确率、工具选择率、无依据断言率、输出长度、Token 与延迟。Prompt 变更只有在冻结回归集和新增失败样本上都通过门禁后才能发布。
