# Agent Evaluation、Testing 与 Observability

> 生产级 Agent 的质量不能只看最终回答是否“像是正确”，还要验证任务结果、执行过程、系统行为以及版本变更是否可控。

## 1. 为什么传统软件测试不够

传统函数通常具有相对确定的输入输出，而 Agent 同时受到以下因素影响：

- 模型与采样参数；
- Prompt 和上下文；
- 检索结果与记忆；
- 工具可用性和外部系统状态；
- Agent Graph 的路由与重试；
- 多轮运行中不断变化的中间状态。

因此，同一个输入可能得到不同但都可接受的结果，也可能最终答案正确、执行过程却存在越权调用、无效循环或过高成本。

Agent 质量应分层衡量：

```text
最终结果质量
+ 执行过程质量
+ 系统运行质量
+ 安全与合规质量
```

## 2. Evaluation、Testing 与 Observability 的关系

- **Evaluation**：回答“系统整体表现有多好”。
- **Testing**：回答“某个明确行为是否满足预期”。
- **Observability**：回答“一次运行实际发生了什么，以及为什么失败”。

三者形成闭环：

```text
线上 Trace → 发现失败模式 → 构建 Eval Dataset
    ↑                              ↓
发布监控 ← Canary / A/B ← 回归测试与改进
```

没有可观测性，很难建立真实评估集；没有评估与测试，Trace 只能用于事后排错，不能阻止回归。

## 3. 建立评估对象

### 3.1 最终结果评估

关注用户最终得到的结果：

- 任务是否完成；
- 事实是否正确并可溯源；
- 是否满足格式和业务约束；
- 是否遗漏关键内容；
- 结果是否可执行、可交付；
- 不确定性是否被正确表达。

### 3.2 轨迹评估

评估 Agent 的执行路径：

- 是否选择了正确工具；
- 工具参数是否正确；
- 是否读取了必要资料；
- 是否出现重复调用和无效循环；
- 高风险操作前是否获得授权；
- 是否在完成前执行了验证；
- 失败后是否选择了正确的重试、降级或终止策略。

轨迹并不存在唯一正确答案。评估时应关注允许集合和关键约束，而不是强制每次都复现同一条路径。

### 3.3 组件评估

将复杂系统拆开测量：

- Prompt 指令遵循率；
- Router 分类准确率；
- RAG 的 Recall@K、Precision@K、Groundedness；
- Tool Selection 与参数正确率；
- Memory 写入质量、召回率和陈旧率；
- Planner 的计划完整性与可执行性；
- Guardrail 的拦截率与误杀率。

组件评估能帮助定位问题，但不能替代端到端评估。

### 3.4 系统指标

常见运行指标包括：

- Task Success Rate；
- Verified Success Rate；
- P50、P95、P99 延迟；
- 单任务 Token 与货币成本；
- 平均步骤数和工具调用数；
- Tool Error Rate；
- Retry Rate 与 Recovery Rate；
- Human Intervention Rate；
- 安全拒绝率；
- 用户放弃率。

## 4. 构建 Eval Dataset

评估集应来自多个来源：

- 真实线上请求的脱敏样本；
- 产品需求和验收标准；
- 历史故障与用户投诉；
- 专家编写的标准案例；
- 边界条件和对抗样本；
- 合成数据扩充的长尾场景。

每条案例至少记录：

```json
{
  "case_id": "refund-017",
  "input": "...",
  "initial_state": {},
  "allowed_tools": ["lookup_order"],
  "forbidden_actions": ["issue_refund_without_approval"],
  "expected_properties": ["引用真实订单状态", "说明下一步"],
  "tags": ["high_risk", "tool_use", "regression"]
}
```

不要只保存“标准答案”。开放任务更适合保存：

- 必须满足的属性；
- 禁止出现的行为；
- 可接受结果集合；
- 关键证据；
- 评分 Rubric。

评估集还应按难度、语言、用户类型、工具、风险等级和业务场景分层，避免总体平均分掩盖关键分组的退化。

## 5. Grader 设计

### 5.1 确定性检查

优先使用可复现的程序规则：

- JSON Schema 校验；
- 单元测试和集成测试；
- SQL 查询验证；
- 文件或资源是否真实存在；
- 数值范围和业务不变量；
- 工具调用参数白名单；
- 引用能否支持结论。

确定性检查适合判断“是否满足”，但通常无法完整衡量开放文本的质量。

### 5.2 Model-as-a-Judge

模型评分器适合评价：

- 相关性；
- 完整性；
- 表达质量；
- 是否遵循复杂 Rubric；
- 两个版本结果的成对比较。

Judge Prompt 应包含清晰维度、分数锚点、输入证据和结构化输出。还应使用人工标注集校准 Judge，检查：

- 与人工判断的一致性；
- 位置偏差；
- 偏好冗长答案；
- 同模型自我偏好；
- 对提示注入内容的敏感性。

### 5.3 人工评审

人工评审用于：

- 高风险业务；
- 新能力上线；
- Judge 校准；
- 主观体验；
- 发现评估规则未覆盖的新失败模式。

应提供统一 Rubric、盲测和复核机制，并记录评审者分歧。

### 5.4 组合评分

生产评估通常使用多种 Grader：

```text
硬门槛：权限、安全、Schema、关键业务规则
软评分：正确性、完整性、体验
运行约束：延迟、成本、步骤数
```

安全硬门槛失败时，不应被高语言质量平均掉。

## 6. Testing 策略

### 6.1 单元测试

对确定性组件测试：

- Context Builder；
- Tool 参数验证；
- 状态转换；
- 权限策略；
- 重试与退避；
- Prompt 模板渲染；
- 输出解析器。

### 6.2 Contract Test

测试模型、工具和服务之间的接口契约：

- Tool Schema 是否向后兼容；
- 必填参数和枚举是否一致；
- 超时和错误是否结构化；
- MCP Server 能力是否符合声明；
- 模型结构化输出是否可被下游解析。

### 6.3 Integration Test

使用真实或高保真测试环境检查：

- 模型是否能正确选择工具；
- 多个工具结果能否被合并；
- 数据库写入是否幂等；
- Graph 路由是否符合状态；
- 人工审批后能否继续执行。

### 6.4 End-to-End Test

从用户目标到最终验证运行完整 Harness。外部依赖可以分级：

```text
PR：Stub / Fake，快速且稳定
Nightly：测试环境中的真实服务
Pre-release：影子流量或 Canary
```

### 6.5 非功能测试

- 并发与负载测试；
- 长任务和上下文压缩测试；
- 限流、超时和部分故障注入；
- 崩溃恢复和重复消息测试；
- Prompt Injection 与工具滥用测试；
- 成本预算和延迟预算测试。

## 7. 回归评估与发布门禁

应区分：

- **Capability Eval**：新系统能否解决更难的问题；
- **Regression Eval**：已有能力是否退化；
- **Safety Eval**：新能力是否扩大风险面。

每次变更都应记录以下版本：

```text
Model + Prompt + Tool + Graph + Memory Schema + Dataset + Grader
```

推荐发布流程：

1. 离线回归评估；
2. 固定随机性并重复运行高方差案例；
3. 与生产基线做成对比较；
4. 检查关键分组和硬门槛；
5. Shadow 或 Canary；
6. 监控业务指标和失败模式；
7. 达到阈值后逐步放量，否则回滚。

## 8. Agent Observability

一次 Trace 至少应串联：

```text
Request → Run → Span → Model Call / Tool Call / State Transition
```

建议记录：

- run_id、tenant_id、task_id；
- 模型、Prompt、Graph、Tool、Memory 版本；
- 输入输出 Token、缓存命中和成本；
- 工具名称、参数摘要、状态与耗时；
- Graph 节点和状态迁移；
- 重试、降级、审批与策略拒绝；
- 最终验证结果；
- 错误类型和恢复结果。

日志、指标和 Trace 的职责不同：

| 信号 | 主要用途 |
| --- | --- |
| Logs | 查看离散事件和错误细节 |
| Metrics | 观察趋势、分位数和告警 |
| Traces | 重建一次任务的因果链路 |

可观测性系统必须处理隐私和安全：

- 默认不记录密钥和完整凭据；
- 对 PII 脱敏或分级存储；
- 大型 Tool Result 保存引用而非全量复制；
- 设置访问控制、保留周期和审计；
- 区分调试采样与安全审计日志。

## 9. 告警与 SLO

Agent SLO 不应只看 API 可用性。可以定义：

- 99% 请求能够返回明确终态；
- 高风险操作 100% 经过权限策略；
- Verified Success Rate 高于业务阈值；
- P95 延迟低于目标；
- P95 单任务成本低于预算；
- Trace 完整率高于目标。

告警应尽量指向可执行问题，例如：

- 某工具错误率突增；
- 某模型版本的 Schema 失败率上升；
- Agent Loop 超限比例增加；
- Memory 召回后正确率下降；
- Canary 的高风险拒绝率异常。

## 10. 常见误区

### 10.1 只测试最终文本

最终文本正确不代表过程安全，也无法发现无效成本和偶然成功。

### 10.2 用单次运行判断版本

模型输出具有方差。关键案例需要重复运行，比较均值、分位数和失败率。

### 10.3 测试集长期不更新

固定评估集可能被过拟合，也无法覆盖线上新分布。应持续将真实失败转化为回归案例。

### 10.4 把 Judge 分数当作绝对真值

Judge 也是概率模型，需要人工校准、版本固定和偏差监控。

### 10.5 记录一切却无法查询

高质量可观测性不是堆积日志，而是能够用统一 ID、版本和时间关系重建运行。

## 11. 实践检查清单

- 是否同时评估结果、轨迹、组件与系统？
- 是否有真实失败和高风险边界案例？
- 硬安全门槛是否独立于平均质量分？
- Grader 是否经过人工校准？
- 每次发布是否绑定完整组件版本？
- 是否建立离线、Shadow、Canary 和回滚流程？
- Trace 是否能够解释工具调用和状态迁移？
- 日志是否完成脱敏、权限和保留期设计？
- 线上失败是否会进入新的回归评估？

## 12. 总结

Agent 质量工程的核心闭环是：

```text
可观测运行
→ 发现真实失败
→ 构建可复现评估
→ 测试并改进
→ 渐进发布
→ 再次观察
```

评估负责定义质量，测试负责守住质量，可观测性负责解释质量。
