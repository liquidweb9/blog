# 高并发系统专题笔记

## 1. 什么是高并发

高并发是指系统在同一时间内需要处理大量请求、连接、任务或数据操作。

常见指标包括：

- **QPS**：每秒处理的请求数量。
- **TPS**：每秒完成的事务数量。
- **并发数**：同一时刻正在处理的请求数量。
- **响应时间**：一次请求从发起到完成所花费的时间。
- **吞吐量**：单位时间内系统处理的数据量或任务量。

并发数可以粗略理解为：

```text
并发数 ≈ QPS × 平均响应时间
```

例如：

```text
QPS = 1000
平均响应时间 = 0.2 秒

并发数 ≈ 1000 × 0.2 = 200
```

因此，响应时间增加不仅会让用户感觉系统变慢，还会导致系统中堆积的并发请求进一步增加。

---

## 2. 高并发会带来什么后果

高并发本身不一定是问题。

真正的问题是请求量超过了系统某个环节的承载能力，形成性能瓶颈。

典型故障链路如下：

```text
请求量增加
    ↓
服务响应时间变长
    ↓
线程、连接、内存占用时间增加
    ↓
请求开始排队
    ↓
调用方发生超时
    ↓
调用方自动重试
    ↓
请求量进一步增加
    ↓
数据库、Redis、下游服务被压垮
    ↓
出现雪崩、宕机或数据异常
```

高并发可能造成：

1. 服务响应时间变长。
2. CPU 使用率过高。
3. 内存持续上涨。
4. 线程池耗尽。
5. 数据库连接池耗尽。
6. Redis 连接数耗尽。
7. 数据库锁竞争和死锁。
8. 缓存击穿、穿透或雪崩。
9. 消息队列大量积压。
10. 网络带宽被占满。
11. 文件描述符耗尽。
12. 服务频繁超时。
13. 重试导致流量放大。
14. 部分服务故障扩散为系统雪崩。
15. 数据重复、丢失、乱序或不一致。

---

## 3. 高并发系统的典型架构

一个常见的高并发请求链路如下：

```text
客户端
  ↓
CDN
  ↓
WAF / 防火墙
  ↓
负载均衡
  ↓
API 网关
  ↓
业务服务集群
  ↓
Redis / 本地缓存
  ↓
数据库
  ↓
消息队列
  ↓
异步任务服务
```

每一层承担不同的职责：

| 层级     | 主要作用           |
| ------ | -------------- |
| CDN    | 缓存静态资源，减少源站请求  |
| WAF    | 拦截恶意流量、爬虫和攻击   |
| 负载均衡   | 将请求分发到多台服务实例   |
| API 网关 | 鉴权、限流、路由、日志、熔断 |
| 服务集群   | 执行业务逻辑         |
| Redis  | 缓存热点数据，降低数据库压力 |
| 数据库    | 保存核心业务数据       |
| 消息队列   | 削峰填谷、异步解耦      |
| 监控系统   | 监控系统状态和异常      |

## 4. 高并发对业务服务的影响

### 4.1 CPU 使用率过高

#### 可能原因

* 大量请求同时执行复杂计算。
* JSON 序列化和反序列化频繁。
* 数据压缩、解压缩或加密操作过多。
* 正则表达式复杂。
* 代码中存在死循环或低效循环。
* 线程上下文切换过于频繁。
* 大量日志格式化和写入。
* 单次请求处理的数据量过大。

#### 可能后果

* 请求响应时间增加。
* 请求大量超时。
* 服务失去响应。
* 健康检查失败，实例不断重启。
* CPU 长时间达到 100%。

#### 解决方案

1. 优化算法和数据结构。
2. 减少不必要的序列化操作。
3. 将复杂计算异步化。
4. 使用缓存保存重复计算结果。
5. 限制单次请求的数据量。
6. 减少同步日志输出。
7. 对 CPU 密集型任务使用独立计算服务。
8. 增加服务实例并进行负载均衡。
9. 使用性能分析工具定位热点代码。

---

### 4.2 内存使用过高

#### 可能原因

* 单次查询返回大量数据。
* 对象未及时释放。
* 存在内存泄漏。
* 本地缓存无限增长。
* 请求大量排队。
* 消息一次性加载到内存。
* 上传文件未采用流式处理。
* 线程数量过多。
* GC 回收效率降低。

#### 可能后果

* GC 频繁。
* 服务出现长时间停顿。
* 系统发生内存交换。
* 容器被 OOM Kill。
* 服务直接崩溃。

#### 解决方案

1. 限制分页大小。
2. 大文件采用流式读取和写入。
3. 本地缓存设置最大容量和过期时间。
4. 避免一次性加载大量数据。
5. 限制任务队列长度。
6. 使用内存分析工具检查泄漏。
7. 合理设置容器内存限制。
8. 控制线程池大小。
9. 对大对象进行拆分或压缩。
10. 避免把 Redis 当作对象后再全部加载到服务内存。

---

### 4.3 线程池耗尽

#### 典型场景

一个服务配置了 200 个工作线程。

当数据库变慢后，每个请求都需要等待数据库返回。线程不能及时释放，最终 200 个线程全部处于等待状态。

后续请求只能进入队列或被拒绝。

#### 可能后果

* 请求大量排队。
* 接口超时。
* 服务看似存活，但无法处理新请求。
* 请求队列不断占用内存。
* 上游服务不断重试。

#### 解决方案

1. 设置合理的线程池大小。
2. 为任务队列设置最大长度。
3. 设置明确的拒绝策略。
4. 为数据库、Redis和HTTP调用设置超时时间。
5. 避免在请求线程中执行长时间任务。
6. 将耗时任务放入消息队列。
7. 对不同业务使用独立线程池。
8. 避免所有功能共用同一个线程池。

线程池隔离示例：

```text
核心交易线程池
普通查询线程池
文件处理线程池
消息消费线程池
第三方接口线程池
```

这样即使第三方接口大量超时，也不会占满核心交易线程。

---

### 4.4 连接池耗尽

服务通常会使用连接池访问：

* MySQL。
* PostgreSQL。
* Redis。
* HTTP 下游服务。
* Elasticsearch。
* 消息队列。

#### 典型问题

```text
服务线程数：500
数据库连接池：50
```

500 个请求同时查询数据库时，只有 50 个请求可以获得数据库连接，其余请求只能等待。

#### 可能后果

* 获取连接超时。
* 请求大量排队。
* 接口响应时间突然增加。
* 服务线程被阻塞。
* 数据库连接数达到上限。

#### 解决方案

1. 设置连接获取超时时间。
2. 缩短连接占用时间。
3. 减少事务范围。
4. 优化慢 SQL。
5. 不要在事务中调用远程接口。
6. 根据数据库能力设置连接池大小。
7. 不要盲目增大连接池。
8. 对连接池使用率进行监控。

盲目增加数据库连接池可能会产生反效果：

```text
连接池增大
    ↓
数据库同时执行更多 SQL
    ↓
CPU、磁盘和锁竞争加剧
    ↓
SQL 整体变慢
    ↓
连接占用时间更长
    ↓
数据库彻底被压垮
```

---

## 5. 高并发对数据库的影响

### 5.1 数据库连接数耗尽

#### 表现

* 获取数据库连接超时。
* 数据库提示 Too many connections。
* 应用接口大量超时。
* 数据库连接池使用率接近 100%。

#### 解决方案

1. 优化慢 SQL，缩短连接使用时间。
2. 事务执行完毕后及时释放连接。
3. 合理设置连接池最大连接数。
4. 设置连接获取超时。
5. 增加数据库只读副本。
6. 将热点查询迁移到 Redis。
7. 对非核心请求进行限流。
8. 使用数据库代理统一管理连接。

---

### 5.2 慢 SQL 放大

低并发下，一条执行 500 毫秒的 SQL 可能没有明显问题。

高并发下，如果每秒执行 1000 次：

```text
单次 SQL 耗时 500ms
每秒请求 1000 次
```

数据库会积累大量并发查询，最终造成：

* CPU 飙升。
* 磁盘 I/O 飙升。
* 数据库连接占满。
* 请求大量排队。
* 其他正常 SQL 也变慢。

#### 常见原因

* 缺少索引。
* 索引失效。
* 查询返回数据过多。
* 使用 `SELECT *`。
* 深分页。
* 大量排序。
* 大量临时表。
* 对索引列进行函数计算。
* 模糊查询以 `%` 开头。
* 多表关联数据量过大。
* N+1 查询。
* 大事务。

#### 解决方案

1. 使用执行计划分析 SQL。
2. 建立合理索引。
3. 避免 `SELECT *`。
4. 只查询需要的字段。
5. 限制返回数据量。
6. 使用覆盖索引。
7. 避免深分页。
8. 批量查询代替循环查询。
9. 拆分复杂 SQL。
10. 对查询结果进行缓存。
11. 定期分析慢查询日志。

深分页问题：

```sql
SELECT *
FROM orders
ORDER BY id
LIMIT 1000000, 20;
```

数据库可能需要扫描前面大量数据。

可以改为游标分页：

```sql
SELECT *
FROM orders
WHERE id > 1000000
ORDER BY id
LIMIT 20;
```

---

### 5.3 锁竞争

多个请求同时修改同一条或同一批数据时，会产生锁竞争。

#### 常见热点数据

* 商品库存。
* 用户余额。
* 优惠券剩余数量。
* 秒杀商品。
* 热门文章阅读量。
* 订单状态。
* 全局序号。

#### 可能后果

* SQL 等待锁。
* 事务执行时间增加。
* 请求超时。
* 数据库连接长期占用。
* 死锁。
* 吞吐量下降。

#### 解决方案

1. 缩短事务执行时间。
2. 减少事务中执行的 SQL 数量。
3. 不要在事务中调用第三方接口。
4. 按固定顺序更新数据。
5. 使用乐观锁。
6. 对热点数据进行分片。
7. 使用 Redis 预扣库存。
8. 将非实时更新改为异步聚合。
9. 合理降低事务隔离级别。
10. 避免无索引更新导致大范围加锁。

乐观锁示例：

```sql
UPDATE product_stock
SET stock = stock - 1,
    version = version + 1
WHERE product_id = 1001
  AND stock > 0
  AND version = 10;
```

通过检查受影响行数判断更新是否成功。

---

### 5.4 数据库死锁

#### 典型场景

事务 A：

```text
先锁订单 1
再锁订单 2
```

事务 B：

```text
先锁订单 2
再锁订单 1
```

双方都在等待对方释放锁，形成死锁。

#### 解决方案

1. 所有业务按照固定顺序访问数据。
2. 缩短事务时间。
3. 减少事务操作的数据量。
4. 对死锁事务进行有限次数重试。
5. 记录死锁日志。
6. 优化索引，减少锁定范围。
7. 避免一个事务更新大量数据。

---

### 5.5 热点行问题

例如秒杀商品库存：

```text
product_id = 1001
stock = 10000
```

所有请求都更新同一行：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1001
  AND stock > 0;
```

即使 SQL 本身很快，也会因为大量请求竞争同一行锁而降低吞吐量。

#### 解决方案

1. Redis 预扣库存。
2. 库存分桶。
3. 请求进入消息队列后串行扣减。
4. 按用户或商品进行分区。
5. 使用本地库存分段。
6. 将实时精确统计改为异步汇总。

库存分桶示例：

```text
商品总库存：10000

拆分为：
stock_bucket_1 = 1000
stock_bucket_2 = 1000
stock_bucket_3 = 1000
...
stock_bucket_10 = 1000
```

请求随机或按哈希访问不同库存桶，降低单行竞争。

---

### 5.6 主从复制延迟

读写分离架构中：

```text
写请求 → 主库
读请求 → 从库
```

高并发写入可能造成从库同步延迟。

#### 可能问题

用户刚创建订单，立即查询订单时，从库还没有同步到最新数据，导致查询结果为空。

#### 解决方案

1. 写入后的短时间内强制读取主库。
2. 对一致性要求高的数据直接读主库。
3. 使用版本号判断数据是否同步。
4. 监控主从复制延迟。
5. 降低大事务和批量写入的影响。
6. 将分析查询与业务查询隔离。
7. 根据业务选择最终一致性或强一致性。

---

### 5.7 数据库解决方案总结

| 问题    | 常见解决方案            |
| ----- | ----------------- |
| 连接数耗尽 | 连接池、超时、限流、数据库代理   |
| 慢 SQL | 索引、执行计划、分页优化、减少字段 |
| 读压力过高 | Redis、读写分离、只读副本   |
| 写压力过高 | 分库分表、批量写、异步写      |
| 锁竞争   | 短事务、乐观锁、热点拆分      |
| 热点行   | 分桶、Redis 预扣、消息队列  |
| 数据量过大 | 分区、归档、冷热数据分离      |
| 主从延迟  | 关键查询读主库、监控复制延迟    |
| 大事务   | 拆分事务、批量分段执行       |
| 数据库雪崩 | 限流、熔断、降级、缓存保护     |

## 6. 高并发对 Redis 的影响

### 6.1 Redis 连接数耗尽

#### 可能原因

* 连接未正确释放。
* 每次请求都新建 Redis 连接。
* 连接池配置过小。
* Redis 响应变慢，连接长期占用。
* 服务实例数量增长后，总连接数过多。

#### 解决方案

1. 使用 Redis 连接池。
2. 复用连接。
3. 设置连接超时和读取超时。
4. 监控当前连接数。
5. 避免每个请求创建新连接。
6. 合理限制应用实例的连接池大小。
7. 使用代理或 Redis Cluster 分散连接。

---

### 6.2 热 Key

热 Key 是指某一个 Redis Key 被大量请求集中访问。

例如：

```text
product:1001
hot_news
homepage_data
seckill_stock:1001
```

#### 可能后果

* 某个 Redis 节点网络流量过高。
* 单节点 CPU 使用率过高。
* Redis Cluster 出现节点负载不均衡。
* 热点节点成为系统瓶颈。
* Redis 超时。

#### 解决方案

1. 使用本地缓存。
2. 将一个热点 Key 拆成多个副本。
3. 对 Key 增加随机后缀。
4. 将热点数据分散到不同节点。
5. 对静态内容使用 CDN。
6. 限制热点接口访问频率。
7. 提前识别和预热热点数据。

热点 Key 副本示例：

```text
hot_product:1001:1
hot_product:1001:2
hot_product:1001:3
hot_product:1001:4
```

读取时随机选择一个副本。

---

### 6.3 Big Key

Big Key 是指占用内存很大，或内部元素数量很多的 Key。

例如：

* 一个 String 保存几十 MB 数据。
* 一个 Hash 有上百万个字段。
* 一个 List 有上百万个元素。
* 一个 Set 或 ZSet 数据量极大。

#### 可能后果

* 读取和删除操作阻塞 Redis。
* 网络传输时间增加。
* Redis 主从同步压力增加。
* 数据迁移时间增加。
* Redis Cluster 节点负载不均衡。
* 内存释放时产生延迟抖动。

#### 解决方案

1. 拆分 Big Key。
2. 限制单个 Value 大小。
3. 使用分页读取。
4. 删除大 Key 时使用非阻塞删除。
5. 不要一次获取整个 Hash、List 或 Set。
6. 定期扫描和监控 Big Key。
7. 根据业务维度进行分片。

例如：

```text
原始 Key：
user_messages:1001

拆分后：
user_messages:1001:2026-07
user_messages:1001:2026-08
user_messages:1001:2026-09
```

---

### 6.4 缓存穿透

缓存穿透是指请求查询一个数据库中不存在的数据。

由于数据不存在，Redis 中通常也没有缓存，导致每次请求都访问数据库。

#### 攻击示例

```text
GET /product?id=-1
GET /product?id=-2
GET /product?id=-3
```

#### 解决方案

1. 缓存空值。
2. 使用布隆过滤器。
3. 对参数进行合法性校验。
4. 对异常请求进行限流。
5. 在网关层拦截恶意请求。

缓存空值示例：

```text
Key：product:-1
Value：NULL
TTL：60 秒
```

空值缓存时间不宜过长，避免真实数据创建后仍然查询不到。

---

### 6.5 缓存击穿

缓存击穿是指某个热点 Key 失效瞬间，大量请求同时访问数据库。

#### 典型场景

```text
热点商品缓存过期
    ↓
10000 个请求同时未命中 Redis
    ↓
10000 个请求同时查询数据库
    ↓
数据库被压垮
```

#### 解决方案

1. 热点数据永不过期。
2. 使用逻辑过期。
3. 使用互斥锁重建缓存。
4. 提前刷新缓存。
5. 使用后台线程异步更新缓存。
6. 对数据库查询进行限流。

互斥重建思路：

```text
请求发现缓存不存在
    ↓
尝试获取重建锁
    ↓
获取成功：查询数据库并写入缓存
获取失败：短暂等待后重新读取缓存
```

---

### 6.6 缓存雪崩

缓存雪崩是指大量缓存同时失效，导致请求集中访问数据库。

#### 常见原因

* 大量 Key 使用相同过期时间。
* Redis 整体宕机。
* Redis 网络故障。
* Redis Cluster 多个节点故障。
* 缓存批量清理。

#### 解决方案

1. 过期时间增加随机值。
2. 热点数据设置不同过期策略。
3. 使用 Redis 高可用架构。
4. 使用本地缓存作为二级缓存。
5. 对数据库设置限流和熔断。
6. 提前预热缓存。
7. 缓存故障时启用降级数据。
8. 避免同时批量删除大量缓存。

示例：

```text
基础过期时间：30 分钟
随机时间：0～10 分钟

实际过期时间：30～40 分钟
```

---

### 6.7 Redis 单线程阻塞

Redis 的命令执行核心通常是串行处理的。

如果执行高复杂度命令，可能阻塞其他请求。

#### 危险操作

```text
KEYS *
HGETALL 超大 Hash
SMEMBERS 超大 Set
LRANGE 0 -1
一次删除超大 Key
复杂 Lua 脚本
```

#### 解决方案

1. 使用 `SCAN` 代替 `KEYS`。
2. 对集合数据分页读取。
3. 避免查询整个大集合。
4. 拆分 Big Key。
5. 控制 Lua 脚本执行时间。
6. 使用非阻塞删除。
7. 将复杂统计迁移到其他系统。

---

### 6.8 Redis 内存耗尽

#### 可能后果

* Redis 拒绝写入。
* Key 被自动淘汰。
* 缓存命中率下降。
* 数据库请求突然增加。
* 主从复制异常。
* Redis 进程被系统杀死。

#### 解决方案

1. 配置最大内存。
2. 选择合适的淘汰策略。
3. 所有缓存 Key 设置合理过期时间。
4. 定期清理无效数据。
5. 监控内存碎片率。
6. 拆分 Redis 集群。
7. 不要在 Redis 中存放过大的原始对象。
8. 对数据进行压缩或字段精简。

---

### 6.9 Redis 分布式锁问题

常见问题包括：

* 锁未设置过期时间。
* 业务未执行完，锁提前过期。
* 线程 A 删除了线程 B 的锁。
* 获取锁后服务宕机。
* 锁续期失败。
* 主从切换导致锁状态异常。

#### 正确做法

1. 加锁时设置唯一标识。
2. 设置合理过期时间。
3. 删除锁时校验唯一标识。
4. 解锁使用 Lua 脚本保证原子性。
5. 长任务使用自动续期机制。
6. 分布式锁只保护必要的临界区。
7. 对强一致场景谨慎使用 Redis 锁。

伪代码：

```text
SET lock_key random_value NX PX 30000
```

释放锁时：

```text
只有 lock_key 的值等于 random_value 时才能删除
```

## 7. 高并发对消息队列的影响

### 7.1 消息积压

当生产速度大于消费速度时，会产生消息积压。

```text
生产速度：每秒 10000 条
消费速度：每秒 3000 条
积压速度：每秒 7000 条
```

#### 可能后果

* 业务处理延迟。
* 队列磁盘空间快速增长。
* 消息过期。
* 消费者重启后恢复时间很长。
* 下游数据长时间不一致。

#### 解决方案

1. 增加消费者实例。
2. 增加队列分区。
3. 提升单个消费者处理速度。
4. 批量消费和批量写入。
5. 将慢任务拆分。
6. 临时关闭非核心生产者。
7. 对历史积压启动专门消费者。
8. 监控消息积压数量和消费延迟。

---

### 7.2 消息重复

消息队列通常更容易保证“至少投递一次”，因此消费者可能收到重复消息。

#### 解决方案

消费者必须具备幂等性。

常见幂等方案：

1. 使用业务唯一键。
2. 建立消息消费记录表。
3. 数据库唯一索引。
4. 状态机校验。
5. Redis `SETNX`。
6. 更新时携带版本号。

例如：

```sql
INSERT INTO payment_record (
    payment_no,
    order_id,
    amount
)
VALUES (
    'PAY202608040001',
    1001,
    99.00
);
```

为 `payment_no` 建立唯一索引，即使消息重复消费，也不会重复创建支付记录。

---

### 7.3 消息丢失

消息可能在以下阶段丢失：

```text
生产者 → 消息队列
消息队列内部
消息队列 → 消费者
消费者处理过程
```

#### 解决方案

1. 生产者开启发送确认。
2. 消息队列开启持久化。
3. 使用多副本机制。
4. 消费成功后再确认消息。
5. 消费失败时重新入队。
6. 使用死信队列。
7. 对关键消息进行业务对账。
8. 使用本地消息表或事务消息。

---

### 7.4 消息乱序

同一个订单的消息可能出现：

```text
订单创建
订单支付
订单取消
```

实际消费顺序却可能变为：

```text
订单支付
订单创建
订单取消
```

#### 解决方案

1. 相同业务 ID 发送到同一分区。
2. 单分区内顺序消费。
3. 使用业务状态机校验状态转换。
4. 消息增加版本号。
5. 消费者发现版本不连续时延迟处理。

---

## 8. 高并发对网络和网关的影响

### 8.1 网络带宽耗尽

#### 常见原因

* 返回数据过大。
* 图片和视频直接经过业务服务器。
* 大量文件下载。
* 接口未启用压缩。
* 恶意请求或流量攻击。
* 重复请求过多。

#### 解决方案

1. 静态资源使用 CDN。
2. 文件存储使用对象存储。
3. 接口开启合理压缩。
4. 减少响应字段。
5. 图片使用缩略图和合适格式。
6. 设置下载限速。
7. 对异常流量进行封禁和限流。

---

### 8.2 文件描述符耗尽

每个网络连接通常需要占用文件描述符。

高并发连接过多时，可能出现：

```text
Too many open files
```

#### 解决方案

1. 调整系统文件描述符限制。
2. 开启连接复用。
3. 设置合理的连接超时。
4. 及时关闭无效连接。
5. 限制单个客户端连接数。
6. 监控当前连接数量。
7. 检查连接泄漏。

---

### 8.3 网关过载

网关通常承担：

* 认证。
* 鉴权。
* 限流。
* 路由。
* 日志。
* 签名校验。
* 数据转换。

如果所有请求都经过单个网关实例，网关可能成为瓶颈。

#### 解决方案

1. 网关集群化。
2. 使用负载均衡。
3. 减少网关中的复杂业务逻辑。
4. 对鉴权结果进行短时间缓存。
5. 异步记录访问日志。
6. 按接口和用户进行限流。
7. 对网关进行独立压测。

---

## 9. 高并发下的级联故障

假设服务调用关系如下：

```text
订单服务
  ↓
商品服务
  ↓
库存服务
  ↓
数据库
```

当数据库变慢时：

```text
数据库响应变慢
    ↓
库存服务线程被占满
    ↓
商品服务等待库存服务
    ↓
商品服务线程被占满
    ↓
订单服务等待商品服务
    ↓
订单服务线程被占满
    ↓
整个系统不可用
```

这就是级联故障。

## 10. 防止系统雪崩的核心机制

### 10.1 超时

所有远程调用都应该设置超时时间：

* 数据库连接超时。
* 数据库查询超时。
* Redis 连接超时。
* Redis 读取超时。
* HTTP 连接超时。
* HTTP 响应超时。
* 消息处理超时。

错误示例：

```text
调用下游服务，无限等待
```

正确示例：

```text
连接超时：500ms
读取超时：1000ms
总调用超时：1500ms
```

超时时间应根据业务实际耗时设置，不能机械套用固定值。

---

### 10.2 重试

重试可以处理临时故障，但错误的重试会放大流量。

例如：

```text
原始请求：1000 QPS
每个请求失败后重试 3 次
最大流量可能放大到：4000 QPS
```

#### 正确的重试策略

1. 只重试可恢复错误。
2. 限制最大重试次数。
3. 使用指数退避。
4. 增加随机抖动。
5. 设置总重试时间预算。
6. 非幂等操作不要随意重试。
7. 服务过载时不要立即重试。

指数退避示例：

```text
第一次重试：100ms
第二次重试：200ms
第三次重试：400ms
第四次重试：800ms
```

加入随机抖动：

```text
实际等待时间 = 退避时间 + 随机时间
```

这样可以避免大量客户端同时重试。

---

### 10.3 限流

限流用于保护系统，避免请求量超过最大处理能力。

#### 常见限流维度

* 按接口限流。
* 按用户限流。
* 按 IP 限流。
* 按租户限流。
* 按商品限流。
* 按服务实例限流。
* 按业务优先级限流。

#### 常见算法

##### 固定窗口

```text
每分钟最多允许 1000 次请求
```

优点：简单。

缺点：窗口边界可能产生瞬时流量。

##### 滑动窗口

统计最近一段连续时间内的请求数量。

优点：比固定窗口更平滑。

缺点：实现成本更高。

##### 漏桶

请求以固定速度流出。

适合严格控制处理速率。

##### 令牌桶

系统按固定速度生成令牌，请求获取令牌后才能执行。

优点：

* 可以限制平均速率。
* 允许一定程度的突发流量。
* 实际系统中使用较多。

---

### 10.4 熔断

当下游服务持续失败时，调用方暂时停止调用下游，快速返回失败或降级结果。

熔断器常见状态：

```text
关闭状态
    ↓ 失败率达到阈值
打开状态
    ↓ 等待一段时间
半开状态
    ↓ 少量请求测试
恢复正常或重新打开
```

熔断可以防止线程和连接持续浪费在已经不可用的下游服务上。

---

### 10.5 降级

系统压力过大时，临时关闭非核心功能，优先保证核心功能可用。

例如电商系统可以：

```text
保留：
- 商品查询
- 下单
- 支付
- 订单查询

暂时关闭：
- 个性化推荐
- 商品评论
- 销量排行
- 浏览记录
- 营销统计
```

常见降级方式：

1. 返回默认值。
2. 返回缓存数据。
3. 返回旧数据。
4. 隐藏非核心模块。
5. 暂停复杂统计。
6. 延迟执行非核心任务。

---

### 10.6 舱壁隔离

像船舱一样，将不同功能隔离。

```text
核心业务资源池
非核心业务资源池
第三方调用资源池
报表任务资源池
文件任务资源池
```

这样某个功能出现故障时，不会占满整个系统的资源。

可以隔离：

* 线程池。
* 数据库连接池。
* Redis 集群。
* 消息队列。
* 服务实例。
* Kubernetes 节点。
* 数据库实例。

---

### 10.7 削峰填谷

当瞬时请求量远高于系统处理能力时，可以使用消息队列缓冲请求。

```text
瞬时流量：10000 QPS
系统处理能力：2000 QPS

请求先进入消息队列
消费者按照 2000 QPS 处理
```

适合：

* 秒杀。
* 邮件发送。
* 短信发送。
* 文件处理。
* 报表生成。
* 日志处理。
* 数据同步。
* AI 推理任务。
* 批量导出。

不适合所有场景。

用户需要立即得到结果的强实时接口，不能简单地全部改为异步。

## 11. 数据一致性问题

高并发系统为了提升性能，通常会引入：

* Redis。
* 消息队列。
* 读写分离。
* 分库分表。
* 异步任务。

这些机制会增加数据一致性的复杂度。

### 11.1 缓存和数据库不一致

例如：

```text
数据库更新成功
Redis 删除失败
```

此时 Redis 中仍然存在旧数据。

#### 常见解决方案

1. 先更新数据库，再删除缓存。
2. 删除失败时进行重试。
3. 使用消息队列异步删除。
4. 使用延迟双删。
5. 使用数据库变更日志更新缓存。
6. 设置合理过期时间作为兜底。

常见流程：

```text
更新数据库
    ↓
提交事务
    ↓
删除 Redis 缓存
    ↓
后续请求重新加载最新数据
```

---

### 11.2 重复提交

用户可能因为：

* 网络卡顿。
* 连续点击按钮。
* 客户端重试。
* 网关重试。
* 消息重复投递。

导致同一请求执行多次。

#### 解决方案

1. 幂等键。
2. 唯一业务编号。
3. 数据库唯一索引。
4. 防重复提交 Token。
5. 状态机校验。
6. 分布式锁。

例如创建订单时，由客户端或服务端生成：

```text
request_id = 8d0d4d9c-xxxx
```

服务端记录已处理的 `request_id`，重复请求直接返回第一次处理结果。

---

### 11.3 超卖

高并发扣减库存时，如果先查询再更新：

```text
查询库存：1
请求 A 判断有库存
请求 B 判断有库存
请求 A 扣减成功
请求 B 也扣减成功
```

就可能出现超卖。

#### 解决方案

使用数据库条件更新：

```sql
UPDATE product_stock
SET stock = stock - 1
WHERE product_id = 1001
  AND stock > 0;
```

检查受影响行数：

```text
受影响行数 = 1：扣减成功
受影响行数 = 0：库存不足
```

其他方案：

* Redis 原子扣减。
* Lua 脚本。
* 消息队列串行消费。
* 库存分桶。
* 数据库乐观锁。

---

## 12. 水平扩展与垂直扩展

### 12.1 垂直扩展

提升单机配置：

* 增加 CPU。
* 增加内存。
* 使用更快的磁盘。
* 提升网络带宽。

优点：

* 改造成本较低。
* 实现简单。

缺点：

* 单机能力存在上限。
* 成本越来越高。
* 仍然存在单点故障。

---

### 12.2 水平扩展

增加服务节点：

```text
1 台服务 → 10 台服务 → 100 台服务
```

优点：

* 扩展能力更强。
* 可以实现高可用。
* 可以动态扩容。

缺点：

* 需要处理分布式问题。
* 会增加数据一致性复杂度。
* 需要负载均衡。
* 会增加监控和运维成本。

服务要支持水平扩展，通常需要尽量做到无状态。

错误方式：

```text
用户 Session 只保存在某一台服务的内存中
```

改进方式：

```text
Session 存储在 Redis
或使用无状态 Token
```

---

## 13. 分库分表

当单个数据库无法承载数据量或并发量时，可以进行分库分表。

### 13.1 垂直拆分

按照业务模块拆分：

```text
用户库
订单库
商品库
库存库
支付库
```

优点：

* 降低单库压力。
* 业务边界清晰。

缺点：

* 跨库事务复杂。
* 跨库关联查询困难。

---

### 13.2 水平拆分

按照某个字段将同一类数据拆到多个库或表。

例如按用户 ID：

```text
database_index = user_id % 8
table_index = user_id % 32
```

优点：

* 提升数据容量。
* 分散读写压力。

缺点：

* 跨分片查询复杂。
* 分页和排序复杂。
* 数据迁移复杂。
* 分布式事务复杂。
* 扩容需要重新分片或使用一致性哈希。

## 15. 高并发压测

上线前应进行容量评估和压力测试。

### 15.1 常见压测类型

#### 基准测试

确定系统在正常配置下的基础性能。

#### 负载测试

逐步增加请求量，观察系统性能变化。

##v# 压力测试

持续增加压力，找到系统最大承载能力。

#### 峰值测试

模拟流量突然增长。

#### 稳定性测试

保持一定流量运行数小时或数天，检查：

* 内存泄漏。
* 连接泄漏。
* 磁盘增长。
* 消息积压。
* 性能衰减。

#### 故障测试

主动模拟：

* Redis 宕机。
* 数据库变慢。
* 消息队列不可用。
* 下游服务超时。
* 部分服务实例下线。
* 网络延迟和丢包。

---

### 15.2 压测需要关注什么

不能只关注最大 QPS，还需要关注：

```text
QPS
响应时间
错误率
CPU
内存
数据库连接数
Redis 延迟
消息积压
线程池状态
网络带宽
```

系统最大承载能力不能以“服务刚好不崩”为标准。

应该保留一定安全余量，例如：

```text
压测极限：10000 QPS
建议线上稳定容量：6000～7000 QPS
```

具体安全余量应根据业务波动、扩容速度和故障恢复能力决定。

---

## 16. 高并发故障排查流程

当系统突然变慢时，可以按照以下顺序排查。

### 第一步：判断影响范围

确认：

* 所有接口都慢，还是某个接口慢？
* 所有用户都受影响，还是部分用户？
* 所有服务实例都异常，还是某一台异常？
* 是持续异常，还是瞬时抖动？
* 是否刚刚发布了新版本？
* 是否存在突发活动或异常流量？

---

### 第二步：查看入口流量

检查：

* QPS 是否突然增加。
* 是否有爬虫或攻击。
* 某个 IP 是否请求异常。
* 某个接口是否流量暴增。
* 网关是否发生限流。
* 负载均衡是否均匀。

---

### 第三步：查看服务资源

检查：

* CPU。
* 内存。
* GC。
* 线程池。
* 请求队列。
* 文件描述符。
* 网络连接数。
* 容器是否发生重启。
* 是否出现 OOM。

---

### 第四步：查看下游依赖

检查：

* 数据库是否变慢。
* Redis 是否超时。
* 消息队列是否积压。
* Elasticsearch 是否变慢。
* 第三方接口是否超时。
* 下游服务是否发生熔断。

---

### 第五步：查看数据库

检查：

* 慢 SQL。
* 活跃连接。
* 锁等待。
* 死锁。
* CPU。
* 磁盘 I/O。
* 主从延迟。
* 是否存在大事务。
* 是否执行了批量任务。

---

### 第六步：检查是否出现流量放大

重点检查：

* 客户端重试。
* 网关重试。
* 服务内部重试。
* 消息重复消费。
* 定时任务集中执行。
* 缓存同时失效。
* 服务重启后的缓存预热流量。

---

### 第七步：采取临时止损措施

常见措施：

1. 对异常接口限流。
2. 关闭非核心功能。
3. 扩容服务实例。
4. 暂停批量任务。
5. 暂停非核心消费者。
6. 启用缓存或静态数据。
7. 熔断异常下游。
8. 屏蔽恶意 IP。
9. 降低重试次数。
10. 将流量切换到备用集群。

---

## 17. 常见错误做法

### 17.1 无限制增加线程数

线程越多不代表吞吐量越高。

线程过多会造成：

* 上下文切换增加。
* 内存占用增加。
* 数据库连接竞争增加。
* 系统调度开销增加。

---

### 17.2 无限制增加数据库连接数

数据库连接数增加后，数据库需要同时处理更多 SQL。

如果数据库 CPU、磁盘或锁已经达到瓶颈，增加连接只会让问题更加严重。

---

### 17.3 所有接口统一超时时间

不同接口的正常耗时不同。

应该根据接口特点设置不同超时：

```text
缓存查询：较短
数据库查询：中等
文件处理：较长
异步任务：不应占用同步请求
```

---

### 17.4 对所有失败进行重试

以下错误通常不应该重试：

* 参数错误。
* 权限不足。
* 数据不存在。
* 业务状态不允许。
* 请求格式错误。
* 明确的库存不足。
* 明确的余额不足。

---

### 17.5 把 Redis 当数据库使用

Redis 更适合：

* 缓存。
* 临时状态。
* 排行榜。
* 计数器。
* 分布式协调。
* 短期会话数据。

核心业务数据仍然需要可靠的持久化方案。

---

### 17.6 只做扩容，不做限流

扩容只能提高系统容量，不能阻止无限增长的流量。

成熟的高并发系统通常同时具备：

```text
扩容
限流
熔断
降级
超时
重试控制
监控告警
```

---

## 18. 高并发设计原则

### 原则一：优先保护核心业务

系统资源不足时，优先保证核心链路。

```text
核心：登录、下单、支付
非核心：推荐、排行、统计、日志分析
```

---

### 原则二：快速失败优于无限等待

当系统已经无法处理请求时，应尽快返回明确结果，而不是让请求无限排队。

无限排队会持续占用：

* 线程。
* 内存。
* 连接。
* 文件描述符。

---

### 原则三：所有外部调用都要有超时

不存在永远可靠的网络和下游服务。

---

### 原则四：重试必须有边界

需要限制：

* 重试次数。
* 重试总时间。
* 重试请求类型。
* 重试流量比例。

---

### 原则五：消费者必须幂等

只要使用消息队列，就应该默认消息可能重复。

---

### 原则六：缓存不是无限容量

所有缓存都需要考虑：

* 过期时间。
* 最大容量。
* 淘汰策略。
* 缓存一致性。
* 热 Key。
* Big Key。
* 缓存失效后的数据库保护。

---

### 原则七：先测量，再优化

不要仅凭感觉优化。

应该通过：

* 指标监控。
* 链路追踪。
* 慢查询日志。
* 性能分析。
* 压力测试。

确定真正的瓶颈。

---

## 19. 高并发解决方案总表

| 系统环节   | 常见问题          | 主要解决方案                 |
| ------ | ------------- | ---------------------- |
| 网关     | 流量过大、恶意请求     | 限流、WAF、黑名单、网关集群        |
| 业务服务   | CPU 高、线程耗尽    | 扩容、线程池隔离、异步化、代码优化      |
| 数据库连接池 | 连接耗尽          | 超时、短事务、SQL 优化、合理池大小    |
| 数据库    | 慢 SQL、锁竞争     | 索引、读写分离、分库分表、乐观锁       |
| Redis  | 热 Key、Big Key | 本地缓存、Key 拆分、集群化        |
| 缓存     | 穿透、击穿、雪崩      | 空值缓存、布隆过滤器、互斥重建、随机 TTL |
| 消息队列   | 积压、重复、丢失      | 扩容消费者、幂等、确认机制、死信队列     |
| 网络     | 带宽和连接耗尽       | CDN、压缩、连接复用、连接限制       |
| 下游服务   | 超时、故障扩散       | 超时、熔断、降级、舱壁隔离          |
| 突发流量   | 瞬时过载          | 消息队列、限流、预热、弹性扩容        |
| 数据一致性  | 缓存不一致、重复执行    | 幂等、唯一索引、消息重试、补偿机制      |

## 22. 总结

高并发问题的本质不是简单的“请求数量很多”，而是：

```text
有限的系统资源
无法及时处理不断进入的请求
```

系统资源包括：

* CPU。
* 内存。
* 线程。
* 数据库连接。
* Redis 连接。
* 网络带宽。
* 磁盘 I/O。
* 锁。
* 消息队列消费能力。
* 下游服务处理能力。

解决高并发问题不能只依赖某一种技术。

完整的治理思路应该是：

```text
减少请求
    ↓
缓存结果
    ↓
分散流量
    ↓
异步处理
    ↓
保护数据库
    ↓
限制最大压力
    ↓
隔离故障
    ↓
快速失败
    ↓
监控和持续优化
```

可以概括为十二个关键词：

```text
缓存
扩容
限流
削峰
异步
隔离
超时
熔断
降级
幂等
监控
压测
```
