# GraphRAG 入门：为什么知识图谱能回答跨文档问题？

## 一句话结论

GraphRAG 不是用知识图谱替代向量检索，而是把文档中的实体、关系和主题组织成图，再按问题取回相关子图或社区摘要。它尤其适合回答“哪些团队受到了某项政策影响”“两个事件如何关联”这类需要跨文档连接信息的问题。

## 1. 普通 RAG 卡在哪里？

向量 RAG 的基本单元是 Chunk：将问题和每个 Chunk 编码成向量，取相似度最高的若干段文字，再交给 LLM 回答。

这对事实定位非常有效，例如“退款到账需要多久？”通常只要召回包含规则的一段文档。

但当答案分散在多处时，Top K Chunk 容易出现两个问题：

- **局部正确，整体缺失**：每个段落都相关，却没有一段同时说明完整因果链。
- **语义相近，不等于结构相关**：问题中的实体可能没有出现在同一个 Chunk，向量相似度难以显式表达它们之间的关系。

例如，企业知识库中有三段独立资料：

```text
文档 A：支付团队迁移了结算服务。
文档 B：结算服务由基础架构团队维护。
文档 C：基础架构团队本季度的变更窗口被冻结。
```

对于“支付团队的迁移为什么延期？”，答案依赖 `支付团队 -> 结算服务 -> 基础架构团队 -> 变更冻结` 这条跨文档路径。GraphRAG 的目标正是把这类路径变成可检索的结构化上下文。

## 2. GraphRAG 里存的是什么？

GraphRAG 的核心是把非结构化文本转换为图：

```text
Chunk
  -> 实体抽取：支付团队、结算服务、基础架构团队、变更窗口
  -> 关系抽取：迁移、维护、冻结
  -> 图中的节点与边
```

可以把一条关系表示为三元组：

```text
(支付团队) -[迁移]-> (结算服务)
(基础架构团队) -[维护]-> (结算服务)
(基础架构团队) -[冻结]-> (变更窗口)
```

实际系统还应保留证据，而不是只保存 LLM 抽取出的结论：

```json
{
  "source_chunk_id": "architecture-update-17",
  "relation": "维护",
  "subject": "基础架构团队",
  "object": "结算服务",
  "source_url": "kb://architecture/update-2026-q3",
  "confidence": 0.88
}
```

证据 Chunk、来源和时间使答案可以追溯，也为后续人工纠错、权限过滤和增量更新留下基础。

## 3. 两条检索路径：局部与全局

GraphRAG 常见的价值不只在“有图”，而在于提供两种不同粒度的上下文。

| 问题类型 | 需要的上下文 | 合适策略 |
| --- | --- | --- |
| “服务 X 由谁维护？” | 某个实体附近的事实 | 局部检索：找到实体，扩展一到两跳邻居与证据 |
| “这次迁移为何延期？” | 多个实体之间的关系路径 | 局部检索：取相关子图，再回链原文验证 |
| “本季度平台工程的主要风险是什么？” | 多份文档中的主题和趋势 | 全局检索：对图社区的摘要进行 map-reduce 式回答 |

所谓**社区**，是图中联系紧密的一组节点，例如“支付域”“身份认证域”或“某项项目计划”。构建时可对社区生成摘要；面对全局问题时，先检索这些摘要，再让模型归纳答案，避免把大量零散 Chunk 全塞进上下文。

```text
用户问题
  -> 判断问题范围
  -> 局部：实体匹配 -> 子图扩展 -> 证据 Chunk
  -> 全局：社区摘要检索 -> 分段回答 -> 聚合
  -> LLM 基于带引用的上下文生成答案
```

## 4. 最小落地架构

不要一开始就把所有检索都改成图检索。更稳妥的做法是让向量、关键词和图互补：

```text
离线索引
原始文档 -> 清洗与切分 -> 实体/关系抽取 -> 图数据库
                       -> Embedding ------------> 向量数据库
                       -> 社区发现与摘要 -------> 摘要索引

在线查询
问题 -> 查询理解/实体识别
     -> 向量、关键词、图路径并行召回
     -> 合并、去重、重排
     -> 原文证据 + 子图事实 -> LLM -> 带引用答案
```

一个概念性的本地检索函数如下。它展示了边界：图查询负责找到关联，原文 Chunk 才是最终回答的证据。

```python
def retrieve_context(question: str) -> list[dict]:
    entities = extract_query_entities(question)
    graph_facts = graph_store.expand(
        entities=entities,
        max_hops=2,
        max_edges=30,
    )

    evidence_ids = {fact.source_chunk_id for fact in graph_facts}
    vector_hits = vector_store.search(question, top_k=8)
    candidates = load_chunks(evidence_ids) + vector_hits

    return rerank(question, deduplicate(candidates), top_k=6)
```

`max_hops` 必须严格受限。无限扩图会迅速引入无关实体，让上下文膨胀，并使答案看起来有逻辑但失去依据。

## 5. 什么时候值得用？

优先考虑 GraphRAG 的信号包括：

- 文档存在大量实体、依赖、组织关系、事件链或时间线。
- 用户经常提出“影响了谁”“为什么发生”“A 与 B 如何关联”“有哪些共性”这类问题。
- 答案需要综合多个来源，并且必须能展示推理依据。
- 需要将同一实体在不同系统、不同命名中的信息连接起来。

反过来，FAQ、产品说明书定位、少量短文档的问答，通常先把分块、元数据过滤、混合检索和重排做好就足够。GraphRAG 会增加抽取成本、图谱质量治理和索引更新复杂度，不是普通 RAG 的默认升级选项。

## 6. 生产实践中的三个关键点

### 6.1 把实体消歧作为第一等问题

“Apollo”可能是项目名、服务名或客户名。若直接按字符串合并节点，错误关系会在图上被放大。实体节点至少应保存类型、规范名称、别名、所属租户和来源；不确定的匹配进入人工审核或低置信度队列。

### 6.2 图谱必须增量更新且可删除

每条节点和边都要能回溯到源文档和版本。文档更新或删除时，应重算受影响的关系和社区摘要；否则过期边会持续污染回答。将 `document_id`、`chunk_id`、`version` 作为索引记录的一部分，能让这条链路可维护。

### 6.3 评估“关系是否正确”，不只评估最终答案

除常规的答案正确性和引用完整性外，还应抽样检查：

- 实体是否被正确识别和归并。
- 关系是否有原文证据支持。
- 子图扩展是否覆盖了答案必需的路径。
- 图检索相比纯向量检索，是否真的提升了目标问题集的召回率和延迟表现。

图谱质量差时，GraphRAG 会以更有说服力的形式放大错误。因此评估集应包含跨文档、跨实体和全局归纳问题，而不只是一跳事实问答。

## 7. 总结

```text
向量 RAG：擅长找“哪段文字最像这个问题”。
GraphRAG：擅长找“这些实体和事件是怎样连起来的”。
```

从混合检索开始，用图补足关系路径和全局主题；保留原文证据，并以实体消歧、增量更新和可观测评估约束图谱质量，才能让 GraphRAG 成为可靠的生产能力。
