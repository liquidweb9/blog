# PagedAttention 与 Continuous Batching：大模型推理如何高效服务多个请求？

## 一句话结论

**PagedAttention 把 KV Cache 分块存储、按需分配，让有限显存容纳更多活跃序列；Continuous Batching 在每轮推理边界重新组织批次，让已完成请求退出、新请求及时加入。前者解决“缓存怎么放”，后者解决“这一轮谁来算”，两者共同提高大模型服务的吞吐量。**

如果还不熟悉 Key、Value 缓存，可以先读 [KV Cache 基础](/daily/2026/09/2026-09-01-daily-kv-cache)。本文重点讨论多个请求共享一套模型时，推理引擎如何管理显存和调度计算。

## 1. 为什么有了 KV Cache，服务仍然不够高效？

大模型的自回归推理可以分为两个阶段：

| 阶段 | 做什么 | 对服务调度的影响 |
| --- | --- | --- |
| Prefill | 处理 Prompt，建立 KV Cache，通常也产生首个输出 Token | 长 Prompt 会占用较多计算时间 |
| Decode | 每步处理新 Token，读取历史 KV 并追加新 KV | 请求需要反复执行，缓存持续增长 |

假设客服服务同时收到三个请求：一个只需回答“是”，一个生成 200 字摘要，一个分析长文档。它们的输入长度、输出长度和完成时间都不同，输出长度通常也无法提前准确知道。

于是出现两个独立问题：

1. **显存浪费。** 若给每个请求预留一段最大长度的连续 KV 空间，短请求用不满；若连续空间随生成扩展，又需要处理搬迁或碎片问题。
2. **批次空位。** 若一组请求必须整体结束后才接收下一组，短请求结束后释放出的处理能力无法及时服务排队请求。

KV Cache 消除了历史计算的重复执行，但不会自动解决这两件事。

## 2. PagedAttention：逻辑连续，物理不必连续

### 2.1 用块表找到历史 KV

PagedAttention 借鉴操作系统分页的思路，把一个序列的 KV Cache 划分为固定 Token 数的块，再用 **Block Table（块表）** 将逻辑块映射到物理显存块。

为了便于画图，假设每块保存 4 个 Token 的 KV，请求 A 已缓存 10 个 Token：

```text
逻辑块       对应 Token 下标      物理块
A0           0～3                P7
A1           4～7                P2
A2           8～9（余下 2 格）    P9

块表：A -> [P7, P2, P9]
```

模型看到的上下文顺序仍然是 `0, 1, 2, ..., 9`，但 KV 实际位于三个不相邻的物理块中。支持分页布局的注意力内核根据块表访问数据，不必先把所有块复制成一段连续缓存。

例如读取下标为 9 的 Token 时：

```text
逻辑块编号 = 9 // 4 = 2
块内偏移   = 9 % 4  = 1
物理块     = block_table[2] = P9
```

这里简化了实际张量地址计算；真实 KV 还包含层、KV 头和 Head Dimension 等维度。

**分块改变的是存储和访问方式，不是注意力的数学含义。** 对全注意力模型，新 Query 仍需关注全部有效历史 KV；不能在每个块内分别做 Softmax 后直接拼接，因为归一化必须覆盖整个有效上下文。

### 2.2 按需增长，减少预留和碎片

在上面的例子中，后续 Token 可以继续写入 P9 的剩余位置。需要缓存第 13 个 Token 时，才为新的逻辑块 A3 分配一个空闲物理块，比如 P4：

```text
原块表：A -> [P7, P2, P9]
新块表：A -> [P7, P2, P9, P4]
```

历史块无需整体搬迁。请求结束后，独占块可归还空闲池，其他请求再按需使用。

若原方案为这个请求预留 16 个 Token 的空间，当前 10 个 Token 会空出 6 格；分页方案只需分配 3 块、共 12 格，空出 2 格。对普通、未共享的序列，块内空闲通常只发生在最后一块，小于一个块的容量。

这种收益在大量、长度差异明显的请求上更重要。以一个 32 层、8 个 KV 头、每头维度 128、BF16 KV 的模型为例，不考虑分片时，每个 Token 的缓存约为：

$$
2 \times 32 \times 8 \times 128 \times 2
= 131072\ \text{bytes} = 128\ \text{KiB}
$$

因此，4,096 个已缓存 Token 约占 512 MiB，16 个 Token 的块约占 2 MiB。省掉多个请求的无效预留，就能腾出可观的缓存容量。

但分页不会压缩真实 KV：同样的有效 Token 数，缓存数据本身仍然这么大。块表、计算工作区和模型权重也需要显存；引擎还可能在启动时预分配整块缓存池，再在池内按需分配。

### 2.3 共享块与写时复制

多个生成分支可以共享相同 Prompt 的 KV，而不必各存一份：

```text
分支 A： [P1, P2, P8]
分支 B： [P1, P2, P5]
          └─共享─┘  └─各自生成的后缀─┘
```

引擎用引用计数管理共享块。若一个分支需要修改仍被其他分支使用的块，例如向共享的未满尾块追加不同 Token，就通过 **Copy-on-Write（写时复制）** 获得私有副本，避免影响其他分支。

PagedAttention 为共享提供了基础，但跨请求的 **Prefix Caching** 还需要前缀识别、匹配和淘汰策略。复用通常要求相同模型配置及完全一致的 Token 前缀，不能因为两段文字语义相似就共享 KV。

操作系统分页只是类比：这里的“页”是推理引擎管理的 KV 块，不意味着会自动使用硬盘或 CPU 内存，也不意味着消除了长上下文的读取成本。

## 3. Continuous Batching：每一轮都可以调整批次

### 3.1 固定批次为什么留下空位？

假设 A、B、C、D 四个请求都已到达，分别需要生成 2、6、2、2 个 Token，最多同时处理 2 个请求。为突出调度差异，暂不计 Prefill，每轮每个活跃请求生成一个 Token。

| 轮次 | 固定批次：当前组结束后再换组 | Continuous Batching：逐轮补入 |
| --- | --- | --- |
| 1 | A1、B1 | A1、B1 |
| 2 | A2（完成）、B2 | A2（完成）、B2 |
| 3 | 空位、B3 | C1、B3 |
| 4 | 空位、B4 | C2（完成）、B4 |
| 5 | 空位、B5 | D1、B5 |
| 6 | 空位、B6（完成） | D2（完成）、B6（完成） |
| 7 | C1、D1 | 全部完成 |
| 8 | C2（完成）、D2（完成） | — |

固定批次中，A 的结果可以先返回，但 C、D 仍要等 B 结束才能进入下一组。Continuous Batching 则在第 3 轮补入 C，第 5 轮补入 D。

这只是调度示意，不代表真实耗时从 8 秒降到 6 秒：每轮耗时会随活跃序列数、上下文长度和计算内容变化。它说明的是**已完成请求留下的位置可以立即用于其他工作**。

### 3.2 调度粒度从“整个请求”变成“单次迭代”

常见的请求级动态批处理，会用一个短时间窗口收集请求，再组成批次。Continuous Batching 的关键进一步在于：**批次在生成过程中也能变化**，而不是只在开始执行之前动态组批。

概念上，调度器反复执行以下流程：

```text
每个调度边界：
  1. 接收新请求，移除已完成或取消的请求
  2. 回收不再使用的 KV 块
  3. 按 Token 预算、序列数上限和 KV 容量选择本轮工作
  4. 为需要增长的序列分配 KV 块
  5. 执行本轮 Prefill / Decode，输出可返回的 Token
  6. 更新序列状态，进入下一轮
```

这里的“边界”指一次引擎迭代之间，不是任意时刻打断正在运行的 GPU 算子。真实实现也可能重叠调度与执行，或通过推测解码一次接受多个 Token。

不同请求虽然共享一次模型执行，但各自保留独立的 KV、位置、采样参数和结束条件。它们不会被拼成一段互相可见的聊天上下文。

## 4. 两者为什么经常一起出现？

Continuous Batching 不断引入、结束和扩展序列，要求显存分配足够灵活；PagedAttention 的块池和映射表恰好适合这种生命周期：

```text
请求完成 → 释放独占 KV 块 → 新请求获得块 → 加入下一轮计算
请求继续 → 尾块还有空间则追加，满了再申请新块
```

更少的无效预留让更多请求有机会进入活跃集合，逐轮调度则把这部分容量用于实际计算。vLLM 将这类缓存管理与连续批处理结合，是它提升服务吞吐的重要基础。

两者也可以独立存在：有分页缓存不代表调度器一定逐轮补入；采用连续批处理也不必使用某一种分页实现。

几个常见概念的分工可以这样记：

| 技术 | 主要解决的问题 |
| --- | --- |
| KV Cache | 避免每步重新计算历史 Token 的中间状态 |
| PagedAttention | 高效管理、访问和共享非连续存储的 KV |
| Continuous Batching | 在迭代边界动态选择活跃请求 |
| Prefix Caching | 复用相同前缀的 KV，减少重复 Prefill |
| FlashAttention | 优化注意力的 GPU 内存访问与计算实现 |

PagedAttention 与 FlashAttention 的关注点不同，支持相应布局的注意力后端可以同时利用分页 KV 和高效注意力计算。

## 5. 新请求的 Prefill 会不会拖慢已有请求？

会。连续批处理没有消除 Prefill 的计算量：一个新到达的长 Prompt 如果整段处理，可能让已经在流式输出的请求等待更久。

**Chunked Prefill（分块预填充）** 将长 Prompt 拆成多个计算片段，逐步建立 KV，并与已有请求的 Decode 一起调度。例如，本轮 Token 预算为 512，32 个普通 Decode 请求各处理 1 个 Token，就还剩最多 480 个 Token 的预算用于 Prefill；后续还要满足 KV 容量等限制。

这里的“分块”是计算调度粒度，与 PagedAttention 的存储块是两个概念。Prefill 尚未完成的请求通常还不能开始正常输出。

需要平衡的目标是：

- **照顾已有 Decode：** 输出间隔更稳定，但新请求可能更晚拿到首 Token。
- **增加每轮 Prefill 工作量：** 更快推进新请求，却可能延长这一轮，让已有请求的输出停顿。

因此，吞吐更高不保证单个用户感觉更快。真正的优化目标应是满足延迟要求时，能完成多少有效工作。

## 实践建议

在已安装并验证 GPU 环境的 vLLM 中，可以用下面的配置建立实验基线。这里使用 Bash 换行语法，数值需按模型和硬件调整：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --max-model-len 8192 \
  --max-num-seqs 32 \
  --max-num-batched-tokens 2048 \
  --gpu-memory-utilization 0.9 \
  --enable-chunked-prefill
```

连续批处理由引擎调度器负责，无需应用把多个用户请求手工拼成一次生成。具体注意力后端和默认行为会随 vLLM 版本、模型及硬件变化，实验时应记录版本和完整配置。

1. **分清三个长度或容量参数。** `max-model-len` 是单序列上下文长度上限，包含输入与输出；`max-num-seqs` 是单轮最多处理的序列数；`max-num-batched-tokens` 是单轮处理的 Token 预算，不是整批历史 KV 的 Token 总数。
2. **估算真实 KV 需求。** 普通全注意力、无共享时，可按“每 Token KV 大小 × 所有活跃序列已缓存长度之和”估算。共享、缓存保留、滑动窗口和多卡分片会改变实际占用。
3. **同时测首 Token 和输出间隔。** TTFT 包含排队、输入处理和 Prefill；ITL 反映相邻输出 Token 的间隔。记录 P50/P95/P99，以及输出 Token/s、等待队列和抢占次数，不要只看 GPU 利用率。
4. **用混合长度和持续到达的请求压测。** 短问答、长输入摘要、长输出分别测试，再混合测试，并逐步提高请求到达率。仅同时提交一小批等长请求，难以发现长请求阻塞和过载排队问题。
5. **控制显存压力。** `gpu-memory-utilization` 调整引擎的显存使用预算，不是 GPU 算力利用率。并发过高或缓存增长过快会触发等待、抢占或重算，应结合延迟指标调整序列上限与 Token 预算。
6. **检查取消与结束的生命周期。** 用户中断生成后应及时取消引擎请求，让独占 KV 被释放；开启 Prefix Caching 时，已完成请求的可复用块可能仍保留在缓存池中，并非所有块都会立即清空。

最终可以把整个过程理解为：**KV Cache 保存历史，PagedAttention 管好显存，Continuous Batching 持续安排工作，Chunked Prefill 平衡新请求与正在输出的请求。** 优化这条链路时，要用真实负载下的吞吐与延迟共同判断结果。
