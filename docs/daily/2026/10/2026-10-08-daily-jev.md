# Jev：把 AI 判断变成可组合的类型化决策

## 一句话结论

**Jev 是 TypeSafe AI 的 System One 决策模型：给它当前状态和边界明确的问题，它返回选项、评分或“是”的概率，再由业务代码组合成流程。它适合分类、路由和相关性判断；需要撰写回复或复杂推理时，仍应交给生成式模型。**

理解 Jev 最直接的方式，是把它看作软件里的“语义判断函数”：模型负责理解，代码负责计算、分支和执行。

## 1. 为什么软件需要一种决策模型？

假设一个客服系统要根据工单完成三件事：

1. 判断应该交给账单、技术还是销售团队；
2. 判断故障影响有多严重；
3. 判断用户是否表达了紧急诉求。

常见做法是调用 LLM，让它生成 JSON，再读取字段继续处理。普通 LLM 的 Structured Outputs 也能约束输出结构，但这条路径仍以文本生成及其结构约束为中心。

Jev 则把接口直接设计成有限答案空间上的判断：输入 `state` 和 `questions`，输出类型化答案及概率。根据官方介绍，它采用面向决策的模型架构、并行采样与 **RLCD（Reinforcement Learning for Calibrated Decisions）** 训练方法，目标是让软件获得快速、可利用不确定性的判断。

```text
工单文本 + 相关上下文
          ↓
Jev：团队选择 / 影响评分 / 紧急概率
          ↓
业务代码：阈值判断、优先级规则、队列分配
          ↓
技术处理流程 / 生成式回复 / 人工分流
```

这里的变化不只是少写一段 JSON 解析代码，而是**把语义判断拆小，把业务逻辑显式留在代码中**。当优先级规则变化时，可以修改条件和权重，而不是把所有规则重新塞进一个大 Prompt。

## 2. 三种原语：Choice、Score、Noul

Jev 通过 TypeSafe API 暴露三类问题，可以在一次请求中混合使用：

| 原语 | 适合的问题 | 主要返回字段 | 怎样使用 |
| --- | --- | --- | --- |
| `Choice` | 应该交给哪个团队？ | `choice`、`probabilities`、`confidence` | 在预先提供的选项中选择，再决定路由 |
| `Score` | 故障影响处于什么等级？ | `score`、`legend`、`probabilities`、`confidence` | 按有序等级评分，用于排序或阈值判断 |
| `Noul` | 用户是否表达了紧急诉求？ | `noul`，范围为 0～1 | 直接使用“是”的概率 |

### Choice：选项由你提供

`Choice` 的 `criteria` 是选项到描述的映射，例如 `billing`、`technical`、`sales`、`other`。它返回的选择来自这组候选，适合映射到已有处理器或工具。

选项描述应该清楚区分含义；如果输入可能不属于任何已知类别，就显式加入 `other`。**低置信度和 `other` 是两件事**：前者表示答案不确定，后者表示模型认为当前输入不属于已知类别。

### Score：等级要有可理解的语义

`Score` 的 `criteria` 是有序描述，例如“没有服务中断”“部分功能受影响”“关键流程完全不可用”。对于三个等级，位置通常对应 0、1、2，返回的 `score` 可以是小数。

不要把小数评分当成精确的物理量：`1.6` 可以用于优先级排序，但不表示“有 80% 的用户受影响”。用户数、金额和时长应由代码或业务数据计算。

### Noul：概率不是程度

`Noul` 返回“是”的概率，没有单独的 `confidence` 字段。接近 1 表示倾向“是”，接近 0 表示倾向“否”，接近 0.5 表示不确定。

例如，“是否紧急”的 `noul=0.5` 不等于“紧急程度中等”。要表达程度，应使用定义了等级的 `Score`。

## 3. 一个具体例子：工单分流

下面用 Python SDK，把三个独立判断放进同一请求。安装 SDK 需要 Python 3.10 或更高版本：

```bash
pip install typesafe-sdk
```

在 [TypeSafe 控制台](https://console.typesafe.ai/keys) 获取 API Key，并设置环境变量。Windows PowerShell 示例：

```powershell
$env:TYPESAFE_API_KEY = "<your-api-key>"
```

Bash 中可使用 `export TYPESAFE_API_KEY="<your-api-key>"`。客户端会从环境变量读取密钥；底层接口是 `POST https://api.typesafe.ai/v1/systemone`。

```python
from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

state = {
    "ticket_message": (
        "Since this morning every API call returns 500, "
        "so no customer orders can be processed. Please help ASAP."
    ),
}

with TypeSafeClient(model="jev-1.13.0") as client:
    response = client.system_one(
        state=state,
        questions={
            "department": Choice(
                instructions="Which team should handle `ticket_message`?",
                criteria={
                    "billing": "Charges, invoices, or subscription payments.",
                    "technical": "Bugs, API errors, or integration failures.",
                    "sales": "Pricing inquiries or purchasing a product.",
                    "other": "The request does not fit any of these teams.",
                },
            ),
            "impact": Score(
                instructions=(
                    "How severe is the service disruption explicitly "
                    "reported in `ticket_message`?"
                ),
                criteria=[
                    "No service disruption is reported.",
                    "Some functions fail, but the core workflow still works.",
                    "The core workflow is completely blocked.",
                ],
            ),
            "is_urgent": Noul(
                instructions=(
                    "Does `ticket_message` explicitly ask for urgent "
                    "or immediate help?"
                ),
            ),
        },
    )

department = response.answers["department"]
impact = response.answers["impact"]
urgent_probability = response.answers["is_urgent"].noul

# 示例阈值：实际项目需要用自己的样本调优。
if department.choice == "other" or department.confidence < 0.8:
    queue = "manual_triage"
else:
    queue = department.choice

if impact.confidence < 0.7 or 0.4 < urgent_probability < 0.6:
    priority = "needs_review"
elif impact.score >= 1.5 and urgent_probability >= 0.85:
    priority = "P1"
else:
    priority = "P2"

print("model:", response.model)
print("department probabilities:", department.probabilities)
print("queue:", queue, "priority:", priority)
```

这段代码只计算队列和优先级，便于先观察结果。真正接入系统时，队列写入、重试和任务执行由应用层完成。

示例固定了截至 2026-10-08 官方文档列出的 `jev-1.13.0`。快速探索可以用 `jev-latest`，但在同一批回归样本上调过阈值后，固定模型版本更容易比较变化。

三个问题都直接读取 `ticket_message`，**没有让“影响评分”依赖“团队选择”的回答**。这种设计很适合并行评估。

## 4. 概率与 confidence 应该怎样读？

`probabilities` 是每个选项或等级的概率分布；`confidence` 是从该分布计算出的集中程度指标，并不是模型额外生成的一句“我很有把握”。

以三个选项的 `Choice` 为例，当前官方定义为：

$$
\text{confidence} = \frac{p_{\max} - 1/n}{1 - 1/n}
$$

其中 $n$ 是选项数量，$p_{\max}$ 是最大选项概率。如果概率为 `0.80 / 0.15 / 0.05`，则 `confidence=0.70`，而不是 `0.80`。

`Score` 的置信度还考虑等级之间的距离；`Noul` 则直接用概率阈值处理不确定性。

因此要注意两点：

- **`confidence=0.9` 不能直接读成“线上正确率是 90%”。** 它反映概率分布的形状，实际准确率和校准情况需要在自己的任务数据上验证。
- **阈值是业务配置。** 示例中的 `0.8`、`0.7`、`0.85` 只是起点。应观察自动分流覆盖率、误分率以及进入复核的比例，再决定取舍。

一次判断即使给出了合法选项，也可能选错。有限答案空间解决的是输出范围与类型问题，语义正确性仍取决于输入、问题定义和模型能力。

## 5. 并行提问与生成式模型怎样配合？

### 共享状态的独立问题，一次问完

Jev 的同一请求中，每个问题独立评估相同 `state`。可以同时询问团队、紧急程度和影响范围，再由代码选择需要的答案。这也是官方所说的 **Speculative fan-out（推测式扇出）**：提前问出可能用到的独立问题，减少串行网络往返。

但批量问题不是共享推理链。第二个问题不能隐式读取第一个问题的答案；如果后续判断必须根据前一答案查询数据库、补充状态或构造新候选，应该在代码中发起下一次请求。

### 需要生成内容时，交给 LLM

一个客服或 Agent 流程可以这样组合：

```text
请求进入
  → 代码读取订单、服务状态等事实
  → Jev 判断意图、相关性和处理方向
  → 代码按概率与规则选择处理器
  → LLM 根据已选流程撰写回复
  → 代码校验结果并完成业务动作
```

在 RAG 中，也可以先召回候选片段，再让 Jev 对每个候选做相关性判断，由代码排序和过滤，最后交给生成式模型回答。它处于判断层，检索和文本生成仍由各自的组件完成。

[Jev Ultrafast](https://github.com/browser-use/jev-ultrafast) 提供了一个直观例子：Jev 从当前页面可用操作和编号元素中选择动作及目标，只有需要输入文字时才调用文本模型。这说明“选择做什么”和“生成具体内容”可以使用不同接口，再由执行器组合起来。

## 实践建议

1. **先选择一个窄任务。** 从工单分类、工具选择或候选片段筛选开始，每个问题只判断一件事。
2. **让 state 保持相关。** 提供判断需要的文本和字段，避免把整段历史、无关文档全部塞进去；在指令中明确引用具体字段。
3. **把确定性工作留给代码。** 金额计算、计数、日期比较和精确规则检查使用程序实现，Jev 处理需要理解语义的部分。
4. **让候选覆盖边界。** 给 Choice 增加合适的 `other`，给 Score 写清各等级含义，并检查选项顺序变化是否影响判断。
5. **按真实数据调阈值。** 固定样本、问题定义和模型版本，记录概率、置信度、耗时与最终业务结果。
6. **单独验证中文任务。** 当前官方说明英语表现最好，其他语言表现不完全等同；中文工单应使用中文样本评估，而不是直接复用英文示例的阈值。

Jev 的价值，是让软件以类型化接口使用语义判断，并把不确定性作为可处理的数据。设计好问题与候选、用代码组合答案，才是把一次模型调用变成稳定工程能力的关键。
