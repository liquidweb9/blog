# 稠密 LLM vs MoE LLM：总参数、激活参数与部署成本

## 一句话结论

**稠密（Dense）LLM 让每个 Token 经过同一套主要计算模块；稀疏混合专家（MoE，Mixture of Experts）LLM 则在部分层中，通过路由器为每个 Token 选择少数专家。MoE 能在较低的每 Token 计算量下扩大模型参数容量，但仍需存放全部专家，并承担路由、负载均衡和可能的跨卡通信成本。**

理解两者，关键是分清三件事：**模型有多少参数、一个 Token 使用多少参数、服务实际需要多少资源。** 这三个问题不能用同一个数字回答。

## 1. 为什么一个大模型会有两种“参数量”？

假设你在为摘要服务选模型，看到两个候选：

- 一个稠密模型，标注为 8B。
- 一个 MoE 模型，标注为“总参数 22B，每 Token 激活约 10B”。

这里 B 表示十亿。第一个数字描述模型的整体规模，第二个模型则额外给出了**每个 Token 实际参与计算的参数规模**。

容易出现的误解是：既然 MoE 每次只用一部分参数，就只需要加载那一部分。实际上，不同 Token、不同层、不同生成步骤可能选择不同专家，因此通常仍要让全部专家权重可用。

可以把稠密模型理解为“每次都走同一条计算路径”，把 MoE 理解为“公共路径加上按需选择的分支”。不过，专家通常是模型内部的前馈子网络，**不是多个独立聊天模型，也不是让几个模型各写一个答案再投票**。

## 2. 架构区别主要发生在哪里？

一个常见的 Transformer 层包含注意力与前馈网络（FFN，也常称 MLP），以及归一化、残差连接等组件。下面省略归一化和残差，只看主要路径：

```text
稠密层：Token 隐藏状态 → Attention → 同一个 FFN → 下一层

MoE 层：Token 隐藏状态 → Attention → Router → 选中的少数 FFN 专家
                                                    ↓
                                               加权合并 → 下一层
```

本文讨论大模型中常见的 **Token 级稀疏 MoE**：用一组专家替换部分或全部 Transformer 层中的 FFN，注意力等模块通常仍由所有 Token 共用。并非所有名为 MoE 的架构都采用这一布局。

稠密模型中的“全部激活”也是一种简写：它强调没有按 Token 跳过大批专家，并不表示每个 Token 都读取整张输入词嵌入表，或者每个神经元的数值都非零。

### 2.1 Router 如何选择专家？

设某一 MoE 层有 $E$ 个专家，当前 Token 的隐藏状态为 $h$。一种常见的 Top-k 路由方式是：

$$
p=\operatorname{softmax}(W_rh),\qquad
S(h)=\operatorname{TopK}(p,k)
$$

然后只计算选中的专家，并组合它们的输出：

$$
y=\sum_{i\in S(h)}\alpha_i(h)\,\operatorname{Expert}_i(h),
\qquad
\alpha_i(h)=\frac{p_i}{\sum_{j\in S(h)}p_j}
$$

其中 $W_r$ 是路由器参数，$S(h)$ 是选中的专家集合。这里展示的是**选中后重新归一化**的一种实现，实际模型的打分函数、权重归一化方式和路由约束可能不同。

例如有 4 个专家，路由概率为：

```text
专家：       E1    E2    E3    E4
路由概率：  0.10  0.50  0.30  0.10
```

若采用 Top-2，选择 E2 和 E3，重新归一化后的权重为：

$$
\alpha_2=0.50/0.80=0.625,\qquad
\alpha_3=0.30/0.80=0.375
$$

输出就是 $0.625\,E_2(h)+0.375\,E_3(h)$。E1、E4 不执行这次 Token 的专家前向计算，但它们的权重仍然存在。

### 2.2 专家是不是“数学专家”“代码专家”？

“专家”首先是结构名称：多个独立参数化的子网络。路由与专家通常通过训练共同学习，不要求人为给每个专家指定学科。

训练后可能出现某种分工，但不能直接把专家编号解释为固定业务标签。路由输入是该层的上下文隐藏状态，同一个词在不同上下文、不同层里也可能走不同专家。

因此，常见 MoE 的路由粒度是**每个 Token、每个 MoE 层**，而不是一整条请求选定一个专家后就不再变化。

## 3. 总参数与激活参数：一个可手算的例子

假设一个简化模型有：

- 始终参与的公共模块共 6B 参数。
- 4 个 MoE 层，每层有 8 个专家，每个专家 0.5B 参数。
- 每层为每个 Token 选择 2 个专家。

暂时忽略路由器和嵌入计数等细节，总参数为：

$$
P_{\text{total}}=6+4\times8\times0.5=22\text{B}
$$

每 Token 激活参数为：

$$
P_{\text{active}}\approx6+4\times2\times0.5=10\text{B}
$$

更一般地，若第 $\ell$ 个 MoE 层有 $E_\ell$ 个等大小专家，每个为 $P_{e,\ell}$ 参数，选取 $k_\ell$ 个，则：

$$
P_{\text{total}}
\approx P_{\text{common}}+\sum_\ell E_\ell P_{e,\ell},
\qquad
P_{\text{active}}
\approx P_{\text{common}}+\sum_\ell k_\ell P_{e,\ell}
$$

这里的公共部分包括非路由模块；若模型有**始终执行的共享专家**，也要把它们计入两边。不同模型对词嵌入、输出层等参数的统计口径可能不同，比较时要看具体说明。

这个例子说明：

1. **不能直接用总参数乘以 $k/E$。** 只有被路由选择的专家部分按该比例减少；公共计算依然存在。$22\times2/8=5.5$B 并不是本例的激活参数量。
2. **22B 总参数不等于 22B 稠密模型的计算量。** 每个 Token 并不执行全部专家。
3. **10B 激活参数不等于 10B 稠密模型的部署成本。** 权重存储、路由和计算组织仍有差异。

一个真实例子是 [Mixtral 8×7B](https://arxiv.org/abs/2401.04088)：每层有 8 个 FFN 专家，每个 Token 选择其中 2 个；论文报告约 47B 总参数、13B 激活参数。名称中的“8×7B”不等于 8 个完整 7B 模型的简单相加，也不能算成 $8\times7=56$B。

## 4. 为什么计算量少，显存却不一定少？

### 4.1 权重存储主要看总参数

不考虑量化元数据、分片和框架开销时，权重占用可以粗估为：

$$
M_{\text{weights}}\approx P_{\text{total}}\times\text{每参数字节数}
$$

对上面的 22B MoE，BF16 每参数 2 字节，全部权重约需 **44 GB，约 41 GiB**；不能按 10B 激活参数估成 20 GB。这还没有计入 KV Cache、激活、中间缓冲区和运行时开销。

多卡分片能降低单卡权重占用，但系统整体仍需存放这些权重。CPU 卸载或按需搬运可以减少 GPU 常驻权重，代价则可能是传输等待；它不是免费的显存节省。

另外，“每 Token 只选两个专家”不代表一批 Token 总共只用两个专家。一个批次中的不同 Token 可能覆盖全部专家，调度时需要把 Token 按专家分组处理。

### 4.2 KV Cache 不会随专家选择比例缩小

KV Cache 主要由注意力结构、层数、KV 头数、上下文长度、并发和缓存精度决定。MoE 稀疏化的是 FFN 时，并没有自动把这些缓存一起压缩。

因此，长上下文或高并发部署仍要单独估算缓存预算，可以结合 [KV Cache 基础](/daily/2026/09/2026-09-01-daily-kv-cache) 理解。模型权重能装下，只是服务能够运行的第一步。

## 5. 为什么 MoE 不一定比稠密模型更快？

对固定专家大小和 Top-k 数量，增加专家数量可以扩大总参数容量，而专家前向的主要算术量不必同比增长。**这正是 MoE 的吸引力，但不是端到端速度保证。** 路由器本身也有开销，激活参数量只能作为计算规模的粗略线索，不能代替 FLOPs 或实测延迟。

实际速度还受以下因素影响：

| 因素 | 对 MoE 的影响 |
| --- | --- |
| 专家负载 | 部分专家收到过多 Token，会成为慢节点；其他专家可能闲置 |
| 矩阵计算规模 | 每个专家分到的 Token 太少时，容易出现大量利用率偏低的小矩阵运算 |
| 跨卡通信 | 专家分布在不同 GPU 时，需要分发隐藏状态并收集结果 |
| 显存带宽与权重复用 | 小批次 Decode 可能受权重读取和搬运限制，算术量更少不一定同比加速 |
| 推理引擎 | 专家融合算子、量化支持、调度和通信重叠的成熟度会改变结果 |

其中 **专家并行（Expert Parallelism）** 是把不同专家放到不同设备上：Token 被发送给对应专家，算完后再合并，常涉及 All-to-All 通信。它与“把同一个权重矩阵拆到多卡”的张量并行不同，两者也可以组合。

Prefill 一次处理很多输入 Token，Decode 则通常每条序列每步只处理一个新 Token，两者的计算、访存和通信比例不同。不能只凭单个吞吐数字，就断定某种架构在所有并发和长度下都更快。服务调度还可以结合 [PagedAttention 与 Continuous Batching](/daily/2026/10/2026-10-10-daily-paged-attention-continuous-batching) 一起分析。

## 6. 训练时多出来的难题是什么？

MoE 需要让路由器学会有效分配 Token，同时让专家得到足够训练：

- **负载均衡：** 如果大部分 Token 都涌向少数专家，既浪费其他专家的容量，也会拖慢训练。常见方法包括辅助负载均衡损失，或调整路由偏置等策略。
- **容量与溢出：** 有些实现限制每个专家单步接收的 Token 数，溢出后丢弃部分专家分支或改道；另一些使用不丢 Token 的实现。具体行为必须看模型和训练框架，不能认为所有 MoE 都会丢 Token。
- **稳定性与资源：** 路由打分、梯度和精度处理需要协调。即使单 Token 只激活少数专家，全部参数及其梯度、优化器状态仍需存储或分片管理，训练显存不会直接按 $k/E$ 缩小。

稠密模型结构更规整，通常更容易利用成熟的训练与部署工具链。MoE 则增加了一个设计维度：在训练数据、计算预算与系统条件允许时，用更多专家容量换取更好的质量—计算量折中。

比较效果时必须说明基准：**同总参数、同激活参数、同训练计算量和同部署成本，是四种不同的比较。** 专家更多不保证一定更聪明，稠密模型也不保证一定更弱；数据、训练预算和后训练方法同样重要。

## 实践建议

| 决策维度 | 稠密 LLM | 稀疏 MoE LLM |
| --- | --- | --- |
| 每 Token 的主要路径 | 共用同一套模块 | 公共模块加少数路由专家 |
| 参数规模怎么读 | 通常主要看总参数 | 同时看总参数、激活参数和统计口径 |
| 权重容量预算 | 主要按总参数和精度估算 | 同样按总参数估算，不能只看激活量 |
| 运行时复杂度 | 结构规整，工具链通常较成熟 | 额外关注路由、专家负载、算子和通信 |
| 值得优先评估的场景 | 显存紧张、低并发、希望简化部署 | 权重能容纳、引擎支持好，希望扩大容量并控制每 Token 计算量 |

选型时可以按下面的顺序做：

1. **先筛质量，再谈省钱。** 用自己的摘要、代码、工具调用等任务集评估，记录正确率、任务通过率或人工偏好，不以参数量代替能力。
2. **先算能否容纳完整服务。** 权重按总参数计算，再加目标上下文与并发下的 KV、工作区；明确量化格式、卡数、分片和是否卸载。
3. **核对真实推理支持。** 确认引擎支持该架构的专家算子、量化和并行方式；能加载模型不等于已经有高效执行路径。
4. **按目标负载压测。** 分别测低并发与高并发、短输入与长输入，记录首 Token 延迟（TTFT）、输出 Token 间隔（ITL）、P95 延迟、吞吐和峰值显存。
5. **在质量与延迟达标后算总账。** 比较每个成功任务的 GPU 时间或费用，计入多卡、通信和运维成本；通过 API 使用模型时，直接按实际账单、质量和服务表现判断。

最终可以这样记：**稠密模型让参数参与方式更统一；MoE 让参数容量与每 Token 计算量部分解耦。总参数管存储预算，激活参数辅助理解计算规模，真实质量和性能仍要在目标硬件与负载上验证。**
