# RRF：如何把多路检索结果融合成一个排名？

## 一句话结论

Reciprocal Rank Fusion（RRF，倒数排名融合）是一种只用**排名**、不用**分数**来合并多路检索结果的方法。它给每个文档的最终得分是它在各路结果中排名的倒数之和：`score(d) = Σ 1 / (k + rank_i(d))`。因为不依赖不同检索器之间不可比的相似度分数，RRF 实现简单、无需调参，是混合检索里最稳健的默认融合策略。

## 1. 为什么需要融合多路召回？

单一的检索方式都有盲区。以 RAG 中最常见的两条路为例：

| 检索方式 | 擅长 | 不擅长 |
| --- | --- | --- |
| 关键词检索（BM25） | 精确匹配术语、编号、错误码、人名 | 同义改写、语义泛化 |
| 向量检索（Embedding） | 语义相近、口语化提问 | 精确术语、生僻词、数字 |

用户问“订单状态码 5001 代表什么”，BM25 能精准命中 `5001`；用户问“为什么我的退款一直没到账”，向量检索能召回“退款到账时效说明”。两条路各有胜负，于是自然的想法是：**都跑一遍，把结果合并**。

但合并时立刻会遇到一个麻烦：BM25 的分数是未归一化的浮点数（可能从 0 到几十），向量检索的分数是余弦相似度（通常 -1 到 1）。它们**量纲不同、分布不同，直接相加没有意义**。

## 2. RRF 的核心直觉

RRF 绕开了“分数不可比”这个难题：它不看分数，只看**排名**。

一个文档如果在某一路检索里排第 1，那它很可能是相关的；排第 100，那大概率不太相关。排名本身就是一种跨检索器通用的、天然的归一化信号。

RRF 的公式非常简洁：

```text
score(d) = Σ_i  1 / (k + rank_i(d))
```

其中：

- `rank_i(d)` 是文档 `d` 在第 `i` 路结果中的排名，从 1 开始；
- `k` 是一个平滑常数，通常取 `60`；
- 对所有包含文档 `d` 的检索路求和。

直观理解：

- **排名越靠前，贡献越大**。排第 1 的贡献是 `1/(k+1)`，排第 10 是 `1/(k+10)`，衰减很快。
- **多路都靠前的文档得分高**。被多个检索器同时认可，说明它确实相关，这是一种“投票”机制。
- **`k` 抑制头部垄断**。如果没有 `k`，排第 1 的得分是 1，排第 2 是 0.5，头部权重过于极端；加上 `k=60` 后，`1/61` 和 `1/62` 差距很小，让“多路中等靠前”比“单路第一”更有优势。

## 3. 一个具体例子

假设 BM25 和向量检索各返回 5 条结果（文档用 A～E 表示），我们取 `k = 60`：

| 排名 | BM25 | 向量检索 |
| --- | --- | --- |
| 1 | A | C |
| 2 | B | A |
| 3 | C | D |
| 4 | E | B |
| 5 | — | E |

逐文档计算 RRF 得分：

| 文档 | BM25 排名 | 向量排名 | 计算 | RRF 得分 |
| --- | --- | --- | --- | --- |
| A | 1 | 2 | `1/61 + 1/62` | **0.03252** |
| B | 2 | 4 | `1/62 + 1/64` | 0.03175 |
| C | 3 | 1 | `1/63 + 1/61` | 0.03227 |
| D | — | 3 | `1/63` | 0.01587 |
| E | 4 | 5 | `1/64 + 1/65` | 0.03101 |

融合后的最终排名是：

```text
A > C > B > E > D
```

值得注意的是 **A 反超了 C**。C 虽然被向量检索排在第 1，但在 BM25 里只排第 3；A 在两路都稳定靠前。这正是 RRF 想要的：**奖励被多个检索器共同认可的文档**，而不是盲目相信单路的头名。

## 4. `k` 到底影响什么？

`k` 控制的是头部排名的“锐度”：

- `k` 越小（如 `k=1`），头部名次权重差异越大，结果更接近“谁的头部更靠前谁赢”；
- `k` 越大（如 `k=60` 甚至 `k=100`），各路名次差异被抹平，结果更依赖“被多少路同时召回”。

经验上 `k=60` 来自原论文并被广泛沿用，绝大多数场景不需要调整。如果发现某一路检索质量明显更高、希望它更有话语权，更好的做法是给它做加权：

```text
score(d) = Σ_i  w_i / (k + rank_i(d))
```

但要注意：一旦引入权重，就重新引入了需要调参和维护的判断，应先用不带权重的版本建立基线。

## 5. 一个可用的实现

RRF 的实现非常短，核心只是一个按排名累加的字典：

```python
from collections import defaultdict

def reciprocal_rank_fusion(
    result_lists: list[list[str]],
    k: int = 60,
    weights: list[float] | None = None,
) -> list[tuple[str, float]]:
    if weights is None:
        weights = [1.0] * len(result_lists)

    scores: dict[str, float] = defaultdict(float)
    for results, weight in zip(result_lists, weights):
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] += weight / (k + rank)

    return sorted(scores.items(), key=lambda item: item[1], reverse=True)
```

使用时把 BM25 和向量检索的文档 ID 列表传进来即可：

```python
bm25_hits = ["A", "B", "C", "E"]
vector_hits = ["C", "A", "D", "B", "E"]

fused = reciprocal_rank_fusion([bm25_hits, vector_hits])
for doc_id, score in fused:
    print(doc_id, round(score, 5))
```

输出即上一节得到的 `A > C > B > E > D`。可以看到，RRF 不需要任何训练、不需要分数归一化，也不受分数尺度影响。

## 6. RRF 与“分数加权求和”怎么选？

另一种常见融合方式是把各路分数归一化后加权求和：

```text
score(d) = α · normalize(bm25_score) + (1 - α) · normalize(vector_score)
```

| 维度 | 分数加权求和 | RRF |
| --- | --- | --- |
| 需要的信息 | 原始分数 + 归一化方式 | 只需排名 |
| 调参 | 需要调 `α`、归一化方法 | 基本不用（`k` 固定） |
| 换模型/换检索器 | 分数分布变化，需重新校准 | 不受影响 |
| 分数质量高时 | 能利用细粒度差异，可能更好 | 丢弃了分数，信息有损 |
| 稳定性 | 跨系统迁移易失效 | 非常稳定 |

选择建议：

- **多路检索器异构、分数不可比**（如 BM25 + 向量）：优先 RRF。
- **同一检索器、只想调权重**（如两个 Embedding 模型）：归一化加权求和可能更精细。
- **不确定时**：先用 RRF 建立稳定基线，再考虑是否值得引入分数级融合。

## 7. 生产实践中的几个关键点

### 7.1 先做去重，再融合

同一个文档可能在多路中以不同 Chunk 形式出现。融合前应确定**文档粒度**：是按 Chunk 融合，还是先聚合到文档再融合。若按 Chunk，需要用稳定 ID 去重，否则同一内容会占据多个排名。

### 7.2 RRF 之后仍需重排

RRF 只解决“排序合并”，不解决“精排”。生产链路通常是：

```text
BM25 Top-N  ─┐
              ├─ RRF 融合 → Top-M → Cross-Encoder / Reranker → Top-K → LLM
向量检索 Top-N ┘
```

RRF 负责把召回候选稳定地收窄，重排模型负责最终的精度。

### 7.3 各路召回数量要匹配

如果一路返回 100 条、另一路只返回 10 条，短的那一路相当于提前“放弃”了大量候选。应保证各路 Top-N 数量相当，通常 N 取 50～100。

### 7.4 把融合策略当作可评估对象

不要假设 RRF 一定比单路好。应固定评估集，对比：

- 单路 vs 融合的 Recall@K、nDCG、MRR；
- 不同 `k` 值的敏感度；
- 融合后延迟是否可接受。

用数据确认融合确实带来收益，而不是只在直觉上“看起来更全”。

## 8. 总结

```text
单路检索：一种信号，有盲区。
分数融合：信息更全，但分数不可比、需要调参。
RRF：只信排名，多路投票，简单、稳定、几乎不用调参。
```

RRF 的价值不在于它多先进，而在于它用最小的假设解决了混合检索里最棘手的问题——**不同检索器的分数无法直接比较**。当你在 BM25 与向量检索之间犹豫如何合并结果时，RRF 通常是最值得先试的那个默认答案。
