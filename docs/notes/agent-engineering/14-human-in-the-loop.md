# Human-in-the-loop 与 Agent 产品交互

> Human-in-the-loop 不是 Agent 能力不足时的临时补丁，而是把人的授权、判断和责任设计进系统运行过程。

## 1. 为什么 Agent 产品需要人参与

Agent 与普通对话产品的关键区别是：Agent 不仅生成内容，还可能执行操作。

```text
回答一个问题
≠
发送邮件、付款、删除数据或发布代码
```

模型具有概率性，现实任务又常包含：

- 模糊意图；
- 不完整信息；
- 价值判断；
- 高风险副作用；
- 无法自动验证的结果；
- 需要由人承担的法律或业务责任。

因此，生产级 Agent 的目标不应是“完全消除人工”，而应是：

> 让自动化处理适合自动化的部分，让人只在需要授权、判断或接管的位置介入。

## 2. Human-in-the-loop 的主要模式

### 2.1 Human-on-the-loop

Agent 自动运行，人主要监控和抽查。

适用于：

- 风险较低；
- 操作可逆；
- 自动验证充分；
- 错误可以快速恢复。

### 2.2 Human-in-the-loop

人在工作流中的特定节点提供输入、审核或批准。

适用于：

- 缺少关键业务信息；
- 存在多种合理方案；
- 操作具有明显副作用；
- 业务规则要求人工签字。

### 2.3 Human-in-command

人决定目标、边界和终止，Agent 只在明确授权范围内行动。

适用于：

- 医疗、法律、金融等高风险领域；
- 生产环境变更；
- 大额交易；
- 对外发布；
- 涉及员工、客户权益的决策。

这三种模式不是互斥的。同一任务在低风险阶段可以自动执行，在高风险步骤切换为人工批准。

## 3. 人工介入的五种触发点

### 3.1 Clarification：澄清

当输入不足以确定目标时，请用户补充。

不应询问模型能够安全推断或通过工具获取的信息。好的澄清问题应：

- 只问真正阻塞任务的内容；
- 明确说明该选择会影响什么；
- 尽量提供可比较的选项；
- 保留用户自定义输入；
- 避免一次提出过多问题。

### 3.2 Confirmation：确认

Agent 已理解操作，但执行前需要确认。

例如：

```text
将向 327 名客户发送邮件。
主题：服务条款更新
发送时间：今天 18:00
此操作无法整体撤回。
```

确认界面必须展示即将发生的真实副作用，而不是仅显示“是否继续”。

### 3.3 Approval：审批

确认关注用户意图，审批还涉及组织权限和责任。

审批记录应包含：

- 谁申请；
- 谁审批；
- 审批对象；
- 变更摘要；
- 风险与影响范围；
- 有效期；
- 审批时看到的版本；
- 最终执行结果。

如果审批后内容发生实质变化，原审批应失效。

### 3.4 Review：复核

Agent 生成草稿或建议，人检查后再使用。

适合：

- 合同和政策草稿；
- 对外沟通；
- 代码变更；
- 诊断建议；
- 招聘和绩效材料。

复核界面应突出证据、改动和不确定性，而不是要求用户重新阅读全部过程。

### 3.5 Takeover：接管

当 Agent 陷入循环、遇到例外或用户不再信任自动化时，人可以接管。

接管时必须保留：

- 当前目标；
- 已完成步骤；
- 当前状态；
- 工具调用记录；
- 已产生的副作用；
- 未解决问题；
- 可继续执行的入口。

否则“转人工”只是把一个缺少上下文的问题重新丢给人。

## 4. 基于风险的介入策略

是否需要人工介入，不应只由工具名称决定。可以建立风险函数：

$$
Risk =
Impact
\ Probability
\ Irreversibility
\ Uncertainty
\ Scope
$$

工程上可以考虑：

- **影响**：错误会造成多大损失；
- **概率**：当前任务出错的可能性；
- **不可逆性**：能否撤销或补偿；
- **不确定性**：输入、规则和模型判断是否明确；
- **范围**：影响一个草稿、一个用户还是整个组织。

一个简单策略是：

| 风险 | 典型操作 | 交互方式 |
| --- | --- | --- |
| 低 | 搜索、摘要、生成本地草稿 | 自动执行，允许撤销 |
| 中 | 修改共享草稿、创建待办 | 执行前预览或执行后通知 |
| 高 | 发送外部消息、写业务系统 | 明确确认或审批 |
| 极高 | 删除生产数据、大额交易 | 默认禁止或多方审批 |

风险不是静态标签。同一个工具在不同参数下风险不同：

```text
发送邮件给自己
<
发送邮件给一个客户
<
发送邮件给全部客户
```

## 5. Approval Gate 的工程设计

一个审批节点可以表示为：

```json
{
  "approval_id": "approval_001",
  "task_id": "task_123",
  "action": "send_email",
  "arguments_digest": "sha256:...",
  "risk": "high",
  "reason": "external_side_effect",
  "expires_at": "timestamp",
  "status": "pending"
}
```

### 5.1 审批必须绑定具体动作

不要使用：

```text
允许 Agent 继续完成任务
```

应使用：

```text
允许向指定的 12 个收件人发送当前预览版本
```

授权应绑定：

- 参数；
- 内容版本；
- 目标资源；
- 时间范围；
- 最大数量；
- 费用上限。

### 5.2 批准后仍需验证

人工批准不代表工具执行一定成功。系统仍需：

```text
批准
→ 再次校验参数与权限
→ 执行
→ 验证副作用
→ 记录结果
```

### 5.3 拒绝不是失败

用户拒绝操作后，Agent 可以：

- 保存草稿；
- 提供低风险替代方案；
- 询问希望修改哪一项；
- 安全结束任务。

不得反复诱导用户批准。

## 6. Agent UX 的核心原则

### 6.1 预览真实操作

在确认前展示：

- 将调用什么系统；
- 影响哪些对象；
- 使用哪些关键参数；
- 是否产生费用；
- 是否可撤销；
- 预计耗时。

### 6.2 渐进式披露

默认显示用户做决定所需的信息，同时允许展开：

- 来源；
- 推理依据摘要；
- 工具调用；
- 风险说明；
- 完整差异；
- 原始日志。

界面不应把全部 Trace 一次性堆给普通用户。

### 6.3 可编辑，而不只是接受或拒绝

好的交互允许用户修改：

- 目标；
- 计划；
- 工具参数；
- 草稿；
- 收件人；
- 时间；
- 预算和范围。

```text
Agent Draft
→ User Edit
→ Revalidate
→ Execute
```

### 6.4 明确状态

长任务至少应显示：

```text
等待输入
正在执行
等待批准
验证结果
已完成
已失败
已取消
```

“思考中”不是足够的状态说明。用户需要知道系统是否仍在工作、是否需要自己行动以及能否安全离开。

### 6.5 可暂停、取消和恢复

取消语义必须明确：

- 只是停止界面等待；
- 停止后续步骤；
- 取消远程任务；
- 回滚已完成操作；
- 保留当前产物。

对于长任务，暂停点应保存 Durable State，使用户稍后可以恢复，而不是从头开始。

### 6.6 展示不确定性与证据

不要只显示一个虚假的精确置信度。更有用的信息包括：

- 哪些事实有来源支持；
- 哪些是假设；
- 哪些输入缺失；
- 哪些检查已经通过；
- 哪些风险仍未消除；
- Agent 建议人工重点检查什么。

## 7. Interrupt 与 Resume

Human-in-the-loop 在运行时通常表现为可持久化中断：

```text
Agent 执行
→ 到达 Approval Node
→ 保存 Checkpoint
→ 状态变为 INPUT_REQUIRED
→ 人工响应
→ 重新校验
→ 从 Checkpoint 恢复
```

Checkpoint 应保存：

- 当前 Graph Node；
- 输入与状态版本；
- 待审批操作；
- 工具调用结果；
- 已完成副作用；
- 重试次数；
- Trace 上下文。

恢复时需要防止：

- 同一操作重复执行；
- 使用过期审批；
- 外部资源已发生变化；
- 模型或 Prompt 版本变化导致状态不兼容。

因此恢复前应执行：

```text
幂等检查
+ 审批有效性检查
+ 外部状态刷新
+ Schema / Version 检查
```

## 8. 多用户与多角色审批

复杂业务可能存在：

```text
提交人 → 业务负责人 → 安全负责人 → 执行人
```

系统应明确：

- 谁可以批准哪类操作；
- 是否允许自己审批自己的请求；
- 并行审批还是顺序审批；
- 一票否决还是多数通过；
- 审批超时如何处理；
- 代理审批是否允许；
- 内容变化是否要求重新审批。

不要把多角色审批简化为一个布尔字段。审批本身是一个有状态工作流。

## 9. 失败与异常交互

### 9.1 工具失败

告诉用户：

- 哪一步失败；
- 是否产生副作用；
- 系统是否会自动重试；
- 用户需要做什么；
- 是否可以从当前状态恢复。

### 9.2 部分成功

例如 100 封邮件中 92 封发送成功。界面必须清楚区分：

- 已完成；
- 未完成；
- 状态未知；
- 可安全重试。

### 9.3 Agent 循环或低置信度

触发人工介入的信号可以包括：

- 连续多次工具错误；
- 相同动作重复；
- 评估器持续不通过；
- 预算接近上限；
- 多来源证据冲突；
- 关键字段无法确定。

系统应提供当前最佳结果和失败摘要，而不是仅显示“发生错误”。

## 10. 衡量 Human-in-the-loop

人工介入率不是越低越好。

如果介入率突然降低，可能意味着：

- 自动化能力提高；
- 风险门被错误绕过；
- 用户没有看懂确认界面；
- 系统在不确定时仍擅自执行。

建议组合监测：

- 人工介入率；
- 批准、拒绝和修改比例；
- 平均等待时间；
- 审批后失败率；
- 人工修改幅度；
- 错误升级率；
- 接管后完成率；
- 高风险操作漏拦截率；
- 不必要打断率；
- 用户撤销率；
- 任务总完成时间。

可以将人工成本表示为：

$$
HumanCost =
Frequency
\times
ReviewTime
\times
ExpertiseCost
$$

优化目标不是只降低 Frequency，而是在维持安全和质量的前提下降低总人工成本。

## 11. 测试 Human-in-the-loop

测试集应覆盖：

- 低风险操作不会被过度打断；
- 高风险操作一定进入审批；
- 审批绑定的参数被修改后自动失效；
- 拒绝后不会执行副作用；
- 重复点击不会重复执行；
- 审批超时后无法继续；
- 无权限用户不能审批；
- 暂停后可以恢复；
- 取消能传播到子任务；
- 部分成功状态能被正确展示；
- 日志能够还原审批责任链。

还应进行可用性测试：

- 用户是否理解将发生什么；
- 是否能找到取消和修改入口；
- 是否能区分草稿与已执行结果；
- 是否能识别风险与不确定性；
- 是否能在合理时间内完成审核。

## 12. 常见误区

### 12.1 所有工具调用都询问用户

这会造成确认疲劳，最终使用户机械点击“允许”。

### 12.2 只在最后确认

如果 Agent 已经执行了不可逆步骤，最后的确认没有意义。Gate 必须放在副作用之前。

### 12.3 让人复核全部内容

人应重点检查高风险变化、低置信度判断和冲突证据。要求用户从头审阅所有中间过程会抵消自动化价值。

### 12.4 用户批准后系统不再负责

人工批准不能替代参数校验、权限检查、事务、幂等和执行后验证。

### 12.5 转人工时不传递状态

没有上下文的人工接管会造成重复劳动，也容易遗漏已经产生的副作用。

## 13. 实践检查清单

- 哪些操作必须人工批准？
- 风险是否根据参数、范围和可逆性动态计算？
- 确认界面是否展示真实副作用？
- 用户能否修改计划和参数？
- 审批是否绑定内容版本与有效期？
- 执行前是否再次校验权限？
- 拒绝后是否安全停止？
- 是否支持暂停、取消和恢复？
- 接管时是否传递完整状态？
- 是否区分草稿、待批准和已执行？
- 是否展示来源、假设与未解决风险？
- 是否监测不必要打断和漏拦截？
- 是否测试重复提交、超时和部分成功？

## 14. 最终总结

Human-in-the-loop 的核心不是“在页面上增加一个确认按钮”，而是建立一套人机共同控制系统：

```text
Agent 提出计划
→ 系统评估风险
→ 人在关键节点澄清、修改或批准
→ Harness 执行并验证
→ 全过程可暂停、恢复和审计
```

好的 Agent UX 应让用户始终知道：

- 系统正在做什么；
- 为什么需要自己介入；
- 批准后将发生什么；
- 哪些内容仍然不确定；
- 如何修改、拒绝、暂停或接管；
- 最终结果是否真正执行成功。

自动化负责效率，人负责目标、价值判断与高风险授权，确定性系统负责边界和验证。
