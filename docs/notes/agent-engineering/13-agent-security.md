# Agent 安全、威胁建模与可靠性

> Agent 安全的目标不是让模型永不犯错，而是在输入、模型或依赖出错时，仍把权限、数据和副作用限制在可接受范围内。

---

## 1. 先建立威胁模型

按数据流绘制信任边界并列出：

- 资产：身份、密钥、私有数据、预算、工具权限和业务资源；
- 主体：用户、管理员、Agent、子 Agent、MCP/A2A 对端和第三方服务；
- 入口：Prompt、文件、网页、邮件、RAG、Memory、工具返回和协议消息；
- 副作用：发送、删除、支付、发布、代码执行和权限变更；
- 攻击者能力：可控输入、恶意文档、被攻陷工具、重放消息和供应链投毒。

对每条攻击路径记录影响、发生概率、检测方式、预防控制和恢复方案。

## 2. Sandbox 与最小权限

代码执行、浏览器和文件工具应在隔离环境中运行：

- 默认无网络或使用域名 allowlist；
- 文件系统只挂载任务所需目录；
- 使用短期凭证和最小 scope；
- 限制 CPU、内存、进程数、执行时间和输出大小；
- 禁止访问宿主密钥、云元数据和其他租户数据；
- 高风险动作在 Sandbox 外仍需 Tool Gateway 复核。

Sandbox 是损失控制层，不是权限校验的替代品。

## 3. Prompt Injection 与数据外泄

把外部内容视为数据而非指令；检索、Memory 和工具结果都带来源与信任标签。模型不得因为文档声称“已获授权”而扩大权限。敏感数据进入模型、日志或外部工具前执行最小化和脱敏。

## 4. Supply Chain

Agent 供应链不仅包含软件包，还包含：

- 模型与模型路由；
- Prompt、Skill 和系统策略；
- MCP Server、A2A Agent 与 Tool Schema；
- 容器镜像、浏览器扩展和代码执行环境；
- RAG 数据源、Embedding 模型和索引；
- 评估集与发布配置。

需要锁定版本、验证来源和签名、生成 SBOM、扫描依赖与镜像、限制自动更新，并为第三方能力设置撤销开关。新增工具或 Agent 身份必须经过评审。

## 5. 身份、授权与委托

区分最终用户身份、Agent 运行身份和被委托权限。每次跨工具或跨 Agent 调用携带最小 scope、受众、租户、过期时间和可追踪的委托链。服务端基于真实身份与资源重新授权，不能信任模型生成的角色声明。

## 6. 副作用安全

写操作默认要求：

- 参数 Schema 与业务规则校验；
- 稳定的幂等键；
- 预览具体资源和影响；
- 参数绑定的人工确认；
- 执行结果中的副作用状态；
- 可审计记录和补偿流程。

超时不等于失败。重试前必须判断操作是否可能已经成功。

## 7. Red Team

红队测试应覆盖：

- 直接与间接 Prompt Injection；
- 恶意 PDF、网页、邮件、图片 OCR 和工具返回；
- 跨租户读取、权限升级和 confused deputy；
- 工具参数走私、路径穿越、SSRF 和命令注入；
- Memory/RAG 投毒与过期信息；
- 子 Agent 冒充、A2A 消息重放和身份混淆；
- 无限循环、成本耗尽、并发竞态和重复副作用；
- 日志、缓存、错误消息和 Trace 泄密。

成功攻击必须沉淀成自动化回归样本，并验证检测、阻断和恢复三个环节。

## 8. 可靠性控制

为每个任务设置步骤、时间、Token、费用和工具调用预算；对依赖使用分层超时、有限重试、退避抖动、熔断和降级。长任务持久化检查点，高风险写入采用幂等与状态核验。

## 9. 安全版本与发布

Prompt、Model、Tool、Graph、Memory Policy、Sandbox 镜像和安全策略都必须进入 Release Manifest。发布前执行权限测试、对抗评估和历史 Trace 回放；Canary 阶段监控策略拒绝、注入命中、敏感数据脱敏、重复写阻止和跨租户拒绝指标。

## 10. 事件响应

预先准备：

- 撤销工具、MCP Server、Agent Identity 和凭证；
- 停止队列与冻结高风险写操作；
- 定位受影响版本、租户、Trace 和资源；
- 保留审计证据并轮换密钥；
- 修复后回放对抗集；
- 对已产生副作用执行通知和补偿。

## 11. 上线前检查

- [ ] 是否有数据流图、资产清单和威胁模型？
- [ ] 代码与浏览器工具是否在受限 Sandbox 中？
- [ ] 第三方工具、模型和数据源是否有供应链治理？
- [ ] 跨 Agent 委托是否最小权限、短期且可追踪？
- [ ] 高风险副作用是否确认、幂等、可审计？
- [ ] Red Team 攻击是否进入回归集？
- [ ] 是否能快速撤销身份、工具和发布版本？

## 12. 小结

安全、可靠性和发布治理必须一起设计：限制模型能看到什么、能提议什么、能执行什么，并确保每个动作都可验证、可追踪、可停止和可恢复。

## 13. 深入理解：从资产到控制的威胁建模

安全设计先列资产、主体、信任边界、入口、潜在攻击与影响，再把控制落实到具体层。典型资产包括系统 Prompt、用户数据、长期记忆、凭证、工具能力、Artifact 与审计日志；主体包括终端用户、平台 Agent、远程 Agent、工具服务和运维人员。

### 13.1 主要攻击路径

- 直接注入：用户诱导模型忽略规则或泄露数据；
- 间接注入：网页、邮件、文档或工具结果携带恶意指令；
- confused deputy：Agent 借用户权限执行了用户未授权的目标；
- memory poisoning：恶意内容被持久化并影响后续会话；
- tool abuse：合法工具与合法参数组合成越权或破坏性动作；
- supply chain：模型、MCP Server、依赖、Prompt 包或数据源被替换；
- cross-tenant leakage：缓存、向量检索、日志或对象存储隔离失败。

### 13.2 分层控制

输入层做来源标记、大小限制、恶意文件扫描与敏感识别；Context 层做 ACL、租户过滤、可信度与指令/数据隔离；决策层限制动作空间；工具层做独立授权、参数策略、幂等和审批；执行层用 Sandbox、网络出口和资源限额；输出层做引用验证与 DLP；治理层维护审计、告警、密钥轮换和事件响应。

Prompt 中写“不要泄露秘密”不是安全边界。真正的边界是秘密根本不进入不必要的上下文，工具只能拿到短期最小权限凭证，网络与文件访问被执行环境限制，敏感副作用需要不可伪造的审批。

### 13.3 可靠性与安全的交叉

无限重试可能放大攻击和重复扣款；Fallback 模型可能不支持同等安全策略；恢复旧 Checkpoint 可能复活已撤销授权；缓存可能跨租户复用；详细 Trace 可能泄露原文。因此每个可靠性机制都必须重新检查身份、权限、时效与数据边界。

### 13.4 安全验证

建立持续红队集：越权访问、跨租户检索、编码混淆注入、工具结果注入、审批参数替换、重复副作用、过期令牌、恶意 Artifact 和日志泄露。指标包括攻击成功率、未授权工具执行数、敏感输出率、检测与响应时间、误报率和审计覆盖率。
