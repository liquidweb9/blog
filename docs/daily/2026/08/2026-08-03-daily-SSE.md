# 为什么 Agent 流式输出适合使用 SSE

## 一句话结论

SSE（Server-Sent Events，服务器发送事件）是一种基于 HTTP 的单向事件流：客户端建立连接后，服务器可以持续推送模型文本、工具状态和任务进度。对于“客户端提交一次任务，服务器持续返回过程”的 Agent 场景，它通常比轮询简单，也不必为了单向推送引入 WebSocket。

## 问题与场景

普通 HTTP 请求更像“一问一答”：服务器处理完全部工作后，再一次性返回结果。但一次 Agent 任务往往要经历规划、模型生成、工具调用和结果汇总，可能持续几十秒甚至更久。

如果页面一直等待最终答案，用户无法判断任务是在正常运行、等待工具，还是已经失败。轮询虽然能查询进度，却会产生大量无效请求，还要额外处理查询间隔和状态同步。

SSE 使用一条保持打开的 HTTP 响应，把执行过程拆成连续事件：

```text
用户提交任务
  → run_started
  → text_delta
  → tool_call
  → tool_result
  → text_delta
  → run_completed
```

它的核心不是“逐字显示”这一种效果，而是为长时间运行、事件驱动的任务提供一条低成本的服务器到客户端通道。

## 一个具体例子

客户端先请求事件流：

```http
GET /agent/runs/run_001/events
Accept: text/event-stream
```

服务器返回 `text/event-stream`，并持续写入事件。每个事件由空行分隔；`event` 表示类型，`id` 用于断线恢复，`data` 承载数据：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive

event: run_started
id: 101
data: {"run_id":"run_001"}

event: text_delta
id: 102
data: {"content":"我先查询产品手册。"}

event: tool_call
id: 103
data: {"call_id":"call_001","tool":"search_manual"}

event: tool_result
id: 104
data: {"call_id":"call_001","count":3}

event: run_completed
id: 105
data: {"run_id":"run_001"}
```

浏览器可以用原生 `EventSource` 按事件类型更新页面：

```javascript
const source = new EventSource("/agent/runs/run_001/events");

source.addEventListener("text_delta", (event) => {
  const { content } = JSON.parse(event.data);
  appendText(content);
});

source.addEventListener("tool_call", (event) => {
  showToolStatus(JSON.parse(event.data));
});

source.addEventListener("run_completed", () => {
  source.close();
  finishTask();
});

source.onerror = () => showReconnectStatus();
```

`EventSource` 会在意外断线后自动重连，并携带最后收到的事件 ID。不过，自动重连不等于自动恢复数据：服务端仍需保存一段事件历史，根据 `Last-Event-ID` 补发缺失事件；客户端也应按事件 ID 去重。

### SSE 和 WebSocket 怎么选

| 对比项 | SSE | WebSocket |
| --- | --- | --- |
| 通信方向 | 服务器持续推送到客户端 | 客户端和服务器双向通信 |
| 数据类型 | UTF-8 文本 | 文本与二进制 |
| 浏览器接口 | `EventSource` | `WebSocket` |
| 自动重连 | 原生支持基础重连 | 通常自行实现 |
| 典型场景 | 模型输出、任务进度、通知 | 语音、协作、游戏、双向控制 |

如果客户端只需提交一次请求，之后主要接收事件，SSE 通常已经足够。若需要在同一连接中高频发送打断指令、音视频或协作数据，再考虑 WebSocket 或 WebRTC。

原生 `EventSource` 主要面向 GET 请求，不方便自定义请求体和部分请求头。需要通过 POST 提交复杂参数或携带 Bearer Token 时，可以使用 `fetch` 读取 `response.body`，并自行解析服务器返回的 SSE 数据；取消任务则通常使用独立的 HTTP 接口。

## 实践建议

1. **定义稳定的事件协议。** 至少包含 `event_id`、`run_id`、事件类型和时间；并发工具调用再增加 `call_id` 和 `sequence`，不要依赖到达顺序推断业务关系。
2. **把重连设计成可恢复。** 服务端保存可回放的事件，客户端按 ID 去重。明确任务完成、失败和取消事件，并在终态主动关闭连接。
3. **定期发送心跳。** 用 SSE 注释行（如 `: ping`）避免网关把空闲连接关闭，同时监控连接数、持续时间、重连率和首事件延迟。
4. **关闭中间层缓冲。** 反向代理若攒够一批数据才转发，页面就失去流式效果。以 Nginx 为例，可评估 `proxy_buffering off`，应用也可返回 `X-Accel-Buffering: no`；具体配置应以实际基础设施为准。
5. **及时刷新并处理背压。** 服务端发送事件后要刷新响应缓冲；慢客户端不能无限占用内存，应设置队列上限、超时和断开策略。
6. **不要用 SSE 直接传大文件。** 事件中传文件 URL 或对象存储地址；音视频和大量二进制数据应选择更合适的传输方式。
7. **用 HTTP/2 并做容量测试。** 长连接会占用连接、内存和网关资源；上线前验证浏览器连接限制、负载均衡、服务重启和大规模并发下的行为。

SSE 不是 Agent 的必选协议，但它很好地匹配了 Agent 的执行模型：任务是长流程，过程由事件组成，而页面需要持续获得反馈。只要补齐事件回放、幂等、心跳和代理配置，它就是 Web 场景中实现 Agent 流式体验的一种务实方案。
