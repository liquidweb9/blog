# Agent 基础

> Agent 不是一种单独的模型，而是一套以模型参与决策、以运行时约束执行的软件系统。模型负责处理语义和不确定性，普通程序负责状态、权限、副作用与可靠性。

## 从 LLM 应用到 Agent

普通 LLM 应用通常完成一次固定映射：

```text
输入 → Prompt → 模型 → 输出
```

它适合摘要、分类、信息抽取和文本生成等边界明确的任务。Agent 面向的则是需要多步推进、读取环境、调用工具并根据结果调整策略的任务：

```text
目标 → 获取上下文 → 选择行动 → 执行工具
                    ↑              ↓
                    └── 更新状态 ← 观察结果
```

因此，判断一个系统是不是 Agent，关键不在于它是否调用了大模型，而在于它是否形成了“决策—行动—反馈”的闭环。

## 一个工程化定义

可以把 Agent 抽象为：

```text
Agent = Model + Context + State + Tools + Control Flow + Runtime
```

- **Model**：理解目标、处理非结构化信息并提出下一步行动
- **Context**：当前这次推理能够看到的指令、历史、资料和工具结果
- **State**：跨步骤保存的任务进度、计划、产物、错误与预算
- **Tools**：访问文件、数据库、搜索、代码执行或业务 API 的能力
- **Control Flow**：决定节点顺序、条件分支、循环和终止方式
- **Runtime**：真正执行动作，并负责权限、超时、重试、持久化和观测

模型只是其中一个组件。没有运行时约束的“自主性”，往往意味着不可预测的成本和风险。

## Agent 的基本执行循环

一次循环通常包含五步：

1. **观察**：读取目标、当前状态和上一步工具结果。
2. **决策**：判断下一步应该调用工具、请求信息还是结束任务。
3. **校验**：运行时检查动作类型、参数、权限和风险等级。
4. **执行**：调用工具，并把原始结果整理成可消费的观察信息。
5. **更新**：写入任务状态，检查是否达到完成或终止条件。

伪代码如下：

```python
state = initialize(task)

while not should_stop(state):
    proposal = model.decide(build_context(state))
    action = policy.validate(proposal, state)
    observation = tools.execute(action)
    state = reducer.update(state, action, observation)

return finalize(state)
```

这里有两个重要边界：

- 模型可以**提出**动作，但不应绕过运行时直接产生副作用。
- 是否结束不能只听模型判断，还要检查步骤数、时间、费用、连续错误和用户取消等硬约束。

## Agent、Workflow 与聊天机器人的区别

| 形态 | 控制方式 | 适合场景 | 主要风险 |
| --- | --- | --- | --- |
| 聊天机器人 | 单次或多轮文本生成 | 问答、写作、解释 | 幻觉、上下文漂移 |
| Workflow | 预先定义固定步骤 | 稳定、可枚举的业务流程 | 分支膨胀、适应性有限 |
| Agent | 模型在受限动作空间内动态决策 | 开放式、多步骤任务 | 行为不稳定、成本和副作用 |
| Agentic Workflow | 确定性骨架中嵌入局部模型决策 | 大多数生产系统 | 需要清晰划分确定与不确定部分 |

工程上更常见、也更稳妥的是最后一种：让代码控制主流程，只把意图识别、语义路由、计划生成或结果判断等难以写死的环节交给模型。

## 状态与上下文不是一回事

**状态**是系统保存的事实，例如任务编号、已完成步骤、工具结果索引和剩余预算；**上下文**是从状态及其他数据中筛选出来、本轮发送给模型的信息。

如果每次都把完整状态塞进 Prompt，会导致：

- Token 成本持续增长
- 过期信息干扰当前判断
- 敏感数据扩大暴露范围
- 关键信息被淹没

更合理的方式是让运行时维护完整状态，再按当前步骤组装最小充分上下文。

## 工具调用的责任边界

工具定义不仅要告诉模型“能做什么”，还要说明输入约束、失败方式与副作用。一次可靠的工具调用至少经过：

```text
模型提出调用
→ Schema 校验
→ 权限与风险检查
→ 幂等性处理
→ 超时与执行
→ 结果标准化
→ 写入 Trace
```

读取天气和删除数据显然不应使用同一套执行策略。高风险操作通常需要预览、显式确认、最小权限和审计记录。

## 生产系统的六个关注点

### 可控性

限制可选工具、步骤数、运行时间、Token 和费用预算；高风险动作引入人工审批。

### 可靠性

区分可重试与不可重试错误，为有副作用的操作设计幂等键，并对外部依赖设置超时、熔断和降级。

### 可观测性

记录每次模型请求、工具提议、参数校验、执行结果、状态转移、延迟和成本，让一次失败可以被重放和定位。

### 可评估性

建立包含正常、边界、无答案和攻击样本的固定任务集，分别评估任务成功率、工具选择、参数正确性、事实性和成本。

### 安全性

默认把用户输入、网页、邮件和检索文档视为不可信数据；权限控制必须发生在工具和数据层，而不是依赖模型自觉。

### 可恢复性

长任务需要检查点和持久化。进程重启、人工补充信息或外部依赖恢复后，系统应能从明确状态继续，而不是从头猜测。

## 什么时候不需要 Agent

如果任务满足以下条件，普通代码或 Workflow 往往更合适：

- 步骤固定且可以完整枚举
- 输入输出可以由规则可靠处理
- 不需要根据环境反馈调整策略
- 错误成本高，但模型决策没有明显收益
- 单次模型调用已经可以稳定完成

不要为了“更智能”而增加循环。Agent 的价值来自对不确定任务的适应能力，而它的代价是更高的测试、观测、安全和运维复杂度。

## 小结

理解 Agent 的第一步，是把模型从“系统本身”还原为“系统中的一个决策组件”。一个可用的 Agent 不只要能完成任务，还必须能解释当前状态、限制行动边界、处理失败，并让工程团队持续评估和改进。
