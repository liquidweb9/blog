# 基础密码原语

## 第1章 随机性与伪随机性

### 1.1 真随机数与伪随机数

#### 熵源

熵（Entropy）是对不确定性的度量，单位是比特。在密码学中，熵源指的是自然界中能够产生不可预测数据的物理过程。常见的熵源包括：键盘敲击的时间间隔、鼠标移动轨迹、磁盘IO等待时间、网络数据包到达时间、放射性衰变、热噪声（通过读取未初始化的内存或ADC采样的热噪声）等。

为什么我们需要熵源？因为计算机本质上是确定性的机器，任何纯算法生成的"随机数"都不可能凭空创造信息论意义上的不确定性。熵源的作用就是为密码系统注入物理世界的不可预测性。如果一个系统的密钥完全由算法生成而没有外部熵输入，那么攻击者只要复现相同的初始状态就能预测所有密钥。

实际工程中，操作系统会从各种硬件源收集熵并维护一个熵池。Linux的`/dev/random`和`/dev/urandom`就是典型的例子。需要注意的是，在不同的平台上，熵估计的算法差异很大，有些嵌入式设备可能缺乏足够的硬件熵源，这是实现密码系统时容易忽略的风险点。

#### 随机数发生器

随机数发生器（Random Number Generator, RNG）是将熵源输出的原始噪声转化为可用随机数的算法或硬件模块。RNG分为两类：

- **真随机数发生器（TRNG）**：基于物理熵源，输出不可预测的随机数。TRNG的瓶颈在于熵的采集速率通常很慢，而且需要后处理算法来去除物理采样中的偏置（bias）和相关性。
- **伪随机数发生器（PRNG）**：基于确定性算法，从一个较短的种子（seed）扩展出任意长度的随机序列。PRNG速度快、可复现，但安全性完全依赖于种子的随机性。

在密码系统中，典型做法是：用TRNG采集少量高质量的真随机数作为种子，然后交给CSPRNG（密码学安全伪随机数生成器）扩展出应用所需的全部随机数。这种混合架构兼顾了安全性和性能。

#### 密码学安全伪随机数生成器 CSPRNG

CSPRNG与普通随机数生成器的本质区别在于：CSPRNG必须满足**下一个比特不可预测性（Next-bit Unpredictability）**。也就是说，即使攻击者知道CSPRNG的所有历史输出，他也不能以优于1/2的概率正确预测下一个比特。普通随机数生成器（如C语言的`rand()`）不满足这个要求，因此绝不能用于密码学场景。

CSPRNG需要具有以下性质：
1. **伪随机性**：输出与真随机数在计算上不可区分。
2. **前向安全性（Forward Secrecy）**：即使种子被泄露，之前生成的随机数序列也不能被恢复。这是通过状态更新机制实现的——每次输出后都会更新内部状态，使得旧状态无法从新状态推导。
3. **后向安全性（Backward Secrecy / Recovery from Compromise）**：即使攻击者获取了某一时刻的内部状态，在后续注入新的熵后，之前的输出也无法被恢复。这通常通过定期向状态中混入新的熵来实现。

典型的CSPRNG实现包括：
- **/dev/urandom**：Linux内核的CSPRNG，使用ChaCha20算法。
- **getrandom()**：Linux系统调用，行为更可控。
- **Intel RDRAND**：硬件CSPRNG，基于片上熵源和AES-CBC-MAC后处理。

工程实践中，最安全的做法是使用操作系统提供的CSPRNG接口，而不是自己实现。自行实现CSPRNG是密码学中常见的安全漏洞来源之一。

#### Seed管理

种子（Seed）是CSPRNG的初始状态，其安全性直接决定整个随机数序列的安全性。种子管理的核心原则是：

1. **种子必须具有足够的熵**：种子长度至少应与安全级别匹配。128位种子提供128位安全性，256位种子提供256位安全性。种子如果不够随机（比如基于时间戳），攻击者可以暴力枚举可能的种子空间。
2. **种子必须保密**：种子一旦泄露，所有后续输出都可被复现。
3. **种子必须不可预测**：种子的生成必须使用CSPRNG本身，而非低质量的随机源。
4. **定期重新播种（Reseed）**：持续运行的CSPRNG应定期从熵源获取新数据，更新内部状态，以应对熵枯竭和长时间运行带来的安全性衰减。

一个典型的种子管理流程是：系统启动时，从硬件熵源收集至少256位数据，经过熵提取器（如Hash函数）压缩为种子，初始化CSPRNG。运行过程中，每生成一定量的输出后，混入新的熵。

### 1.2 伪随机生成器 PRG

#### PRG的定义

伪随机生成器（Pseudo-Random Generator, PRG）是一个确定性算法 $G: \{0,1\}^s \to \{0,1\}^n$，其中 $s \ll n$。它将一个短的随机种子扩展为一个更长的输出序列。这里的"伪随机"意味着输出应该与相同长度的真随机序列在计算上不可区分。

形式化定义：如果对于所有多项式时间区分器 $D$，有：

$$\left| \Pr[D(G(U_s)) = 1] - \Pr[D(U_n) = 1] \right| \leq \text{negl}(n)$$

则称 $G$ 是一个PRG。其中 $U_s$ 是长度为 $s$ 的均匀随机比特串，$U_n$ 是长度为 $n$ 的均匀随机比特串。

关键洞察：PRG是密码学中"压缩与扩张"思想的体现。密码学试图用短密钥保护大量数据，本质上就是依赖PRG将短密钥（种子）"扩张"为长的密钥流。

#### Expansion

扩展比（Expansion Ratio）定义为 $n/s$，即输出长度与种子长度之比。理论上，PRG可以扩展到任意多项式长度。

扩展的基本机制是迭代：将种子输入PRG，输出第一部分作为密钥流的一部分，第二部分作为下一轮的种子，以此类推。典型的构造方式包括：

- **基于分组密码的CTR模式**：$G(k) = E_k(0) \| E_k(1) \| \cdots \| E_k(m)$
- **基于Hash函数的HMAC_DRBG**：NIST标准，使用HMAC作为底层原语。

为什么扩展是安全的？因为PRG的安全性定义保证了无论输出多长，都不能被区分。但需要注意，任何PRG的输出都有周期性——只不过周期足够大（如 $2^{128}$），在物理可实现范围内不会发生重复。

#### Next-bit Unpredictability

下一比特不可预测性（Next-bit Unpredictability）是PRG安全性的核心定义。它指：给定PRG前 $i$ 个输出比特，攻击者无法以不可忽略的优势预测第 $i+1$ 个比特。

定理：一个PRG满足下一比特不可预测性当且仅当它是安全的（即输出与均匀随机不可区分）。这个等价性非常重要，它意味着我们可以将"输出与随机不可区分"的全局安全概念简化为"预测下一比特"的局部概念，后者在安全性证明中更容易使用。

直觉理解：如果攻击者能区分PRG输出与真随机，那么必然存在某个位置 $i$，攻击者能从这个位置之前的信息中获取关于这个位置之后的信息的知识——也就是能预测下一个比特。反之，如果能预测下一个比特，自然就能区分。

#### PRG与流密码

流密码本质上就是PRG的直接应用。流密码的工作方式如下：

1. 发送方和接收方共享一个短种子 $k$。
2. 发送方使用PRG $G$ 将种子扩展为密钥流 $G(k)$。
3. 发送方将密钥流与明文进行异或：$c = m \oplus G(k)$。
4. 接收方用相同的种子生成相同的密钥流，异或恢复明文：$m = c \oplus G(k)$。

**为什么这要求PRG是密码学安全的？** 如果攻击者从密文 $c$ 中能推断出任何关于密钥流 $G(k)$ 的模式，就能恢复明文。所以流密码的安全性完全等价于底层PRG的安全性。

流密码的优势在于速度快、实现简单、没有分组边界。但流密码有一个致命弱点：**密钥流重用是灾难性的**。如果同一个种子生成的两段密钥流被用于加密不同的消息，即 $c_1 = m_1 \oplus G(k), c_2 = m_2 \oplus G(k)$，那么攻击者可以计算 $c_1 \oplus c_2 = m_1 \oplus m_2$，从而获取明文的冗余信息。这就是为什么流密码中Nonce/IV如此重要——确保每次加密使用不同的密钥流段。

实际中，现代流密码如ChaCha20就是对PRG概念的直接实现：它使用256位种子（密钥）和96位Nonce，生成任意长度的密钥流。

### 1.3 伪随机函数 PRF

#### PRF的安全定义

伪随机函数（Pseudo-Random Function, PRF）是一个确定性函数 $F: \{0,1\}^s \times \{0,1\}^n \to \{0,1\}^m$。对于固定的密钥 $k$，$F(k, \cdot)$ 是一个从 $n$ 比特输入到 $m$ 比特输出的函数。

PRF的安全性定义：一个PRF是安全的，如果对于所有多项式时间区分器 $D$，给定对函数的黑盒访问权限，$D$ 无法区分 $F(k, \cdot)$（$k$ 随机选择）与一个真随机函数 $f: \{0,1\}^n \to \{0,1\}^m$。形式化地：

$$\left| \Pr[D^{F(k,\cdot)} = 1] - \Pr[D^{f(\cdot)} = 1] \right| \leq \text{negl}(n)$$

区分器可以自适应地查询函数任意输入并获得输出，但不能查看密钥本身。这个定义意味着：PRF的输出在攻击者看来是完全随机的，直到他显式地查询了那个输入点。

这个定义的强大之处在于：它允许我们用短密钥"模拟"一个指数级大小的真随机函数表。真随机函数 $f: \{0,1\}^n \to \{0,1\}^m$ 需要 $2^n \cdot m$ 比特存储，这在 $n=128$ 时是完全不可能的。但PRF用固定长度的密钥（如128或256位）实现了与真随机函数行为不可区分的功能。

#### PRF与随机函数的区别

从功能上看，PRF与真随机函数的行为在计算上不可区分。但两者有本质差异：

1. **描述长度**：真随机函数需要指数级描述（函数表），PRF只需要一个短密钥。
2. **确定性**：PRF $F(k, \cdot)$ 对于固定的 $k$ 和输入 $x$ 总是输出相同的结果；真随机函数也是如此（函数是确定性的）。但注意，每次随机选择 $k$ 会得到不同的PRF，就像每次随机选择真随机函数会得到不同的函数一样。
3. **可压缩性**：PRF的输出是"伪随机"而非"真随机"。对于某个固定的 $k$，PRF的输出之间存在内在关联（通过密钥 $k$），但计算上不可区分于无关。

关键理解：PRF比PRG更强。PRG可以看作PRF的一个特例：$G(k) = F(k, 0) \| F(k, 1) \| \cdots \| F(k, t)$。反过来，我们可以用PRG构造PRF（如GGM树形构造），但效率可能不高。

#### PRF在MAC、KDF和协议中的作用

PRF是密码学中应用最广泛的原语之一：

**消息认证码（MAC）**：一个安全的MAC本质上就是一个PRF。对于消息 $m$，标签 $t = F(k, m)$。安全MAC要求攻击者即使看到任意消息的标签，也不能伪造一个新消息的有效标签。这正是PRF安全性的直接推论——如果 $F$ 是安全的PRF，攻击者不能预测 $F(k, m^*)$（对于未查询过的 $m^*$），因为真随机函数在未查询点的输出是不可预测的。需要注意，只有输出空间足够大（如128位以上）的PRF才能直接用作MAC，否则攻击者可能通过碰撞攻击伪造标签。

**密钥派生函数（KDF）**：KDF将主密钥（如DH共享秘密）转换为多个子密钥。典型构造是 $K_i = F(\text{master}, \text{info} \| i)$。PRF的伪随机性保证了子密钥在计算上与随机不可区分，即使攻击者知道部分子密钥也不能推断其他子密钥。

**协议中的会话密钥**：在TLS等协议中，通信双方使用PRF从主密钥派生会话密钥、IV等。PRF的密钥为"主密钥"，不同的标签对应不同的会话密钥。这样做的好处是：即使一个会话密钥泄露，其他会话密钥的安全性不受影响（只要标签不冲突）。

### 1.4 伪随机置换 PRP

#### PRP与分组密码

伪随机置换（Pseudo-Random Permutation, PRP）是一个确定性函数 $E: \{0,1\}^s \times \{0,1\}^n \to \{0,1\}^n$，对于每个密钥 $k$，$E(k, \cdot)$ 是一个置换（双射）。PRP的安全性定义要求：$E(k, \cdot)$ 与一个随机选择的置换在多项式时间内不可区分。

**分组密码（Block Cipher）就是PRP的实际实现**。AES是最著名的分组密码/PRP。分组密码的主要参数是密钥长度 $s$（如128、192、256）和分组大小 $n$（AES为128位）。

为什么分组密码必须是置换？因为解密需要可逆性。如果加密函数 $E_k$ 不是双射，就无法唯一解密。所以分组密码天然是PRP而非PRF。

PRP的输入输出空间大小是 $2^n$，置换总数为 $2^n!$。安全的PRP意味着攻击者即使自适应地查询 $q$ 个明文-密文对，也无法区分于真随机置换。当 $q$ 接近 $2^{n/2}$ 时（因为生日悖论），开始出现区分可能性，这就是分组密码"安全边界"的来源——AES-128的安全边界大约在 $2^{64}$ 次查询。

#### Strong PRP

强PRP（Strong PRP, SPRP）是PRP的加强版本。普通PRP只要求加密方向（正向查询）不可区分，而强PRP要求加密和解密两个方向都不可区分。攻击者被允许同时自适应地查询 $E_k$ 和 $D_k$。

形式化：一个强PRP是安全的，如果攻击者无法区分 $(E_k, D_k)$ 与 $(E, D)$，其中 $E$ 是随机置换，$D$ 是其逆置换。

这个区别在实际中很重要。考虑CBC模式的加密：加密需要 $E_k$，解密需要 $D_k$。如果底层分组密码不是强PRP（即解密方向存在某些结构），攻击者可能利用解密预言机进行攻击。幸运的是，AES目前被认为是强PRP。

形式上，SPRP比PRP更强。一个SPRP自动是PRP，但反之不一定成立。Feistel网络的3轮构造可以提供PRP安全性，但需要4轮才能提供SPRP安全性（Luby-Rackoff定理）。

#### PRF与PRP之间的关系

PRF和PRP是紧密相关但不同的概念：

- **PRF**：从 $\{0,1\}^n$ 到 $\{0,1\}^m$ 的函数，不需要是双射。输出空间可以不同于输入空间。
- **PRP**：从 $\{0,1\}^n$ 到 $\{0,1\}^n$ 的置换，必须是双射。输入输出空间相同。

**PRP到PRF的转换**：如果一个PRP的输入输出空间相同，且分组长度足够大，那么它可以被视为PRF。这是因为随机置换和随机函数在 $q \ll 2^{n/2}$ 次查询内是不可区分的（这是PRP-PRF切换引理的核心）。AES-128在约 $2^{64}$ 次查询内可以安全地被视为PRF。这种切换在安全性证明中非常常见。

**PRF到PRP的转换**：反过来，从PRF构造PRP要复杂得多。标准方法是使用Feistel网络：Luby和Rackoff证明了3轮Feistel网络使用PRF作为轮函数可以得到安全的PRP，4轮得到安全的SPRP。这正是许多分组密码的设计基础。

实际选择：当需要加密（可逆）时用PRP，当只需要认证或派生时用PRF。分组密码（PRP）通常比专门设计的PRF更高效，因此很多时候分组密码也被直接用作PRF（如AES-CMAC、AES-KDF）。

## 第2章 哈希函数与承诺

### 2.1 密码学哈希函数

密码学哈希函数 $H: \{0,1\}^* \to \{0,1\}^n$ 将任意长度的输入映射为固定长度的输出（摘要/哈希值）。与普通哈希函数不同，密码学哈希函数需要满足特定的安全性质。

#### 原像抗性

原像抗性（Preimage Resistance），也称为单向性（One-wayness）：给定哈希值 $y$，找到任何满足 $H(x) = y$ 的 $x$ 在计算上是不可行的。

也就是说，哈希函数是单向的：计算 $H(x)$ 很容易，但给定 $H(x)$ 反推 $x$ 极其困难。对于 $n$ 位输出，最好的原像攻击需要大约 $2^n$ 次哈希计算（暴力搜索）。

**为什么需要原像抗性？** 在密码存储场景中，系统存储的是密码的哈希值而非明文密码。如果数据库泄露，攻击者得到的是 $H(\text{password})$，由于原像抗性，攻击者无法从哈希值还原出密码。需要注意，对于用户选择的弱密码，原像抗性并不能阻止字典攻击——这是另一层面的问题，需要通过加盐（salt）和慢哈希（如bcrypt、Argon2）来解决。

#### 第二原像抗性

第二原像抗性（Second Preimage Resistance）：给定输入 $x_1$，找到另一个输入 $x_2 \neq x_1$ 使得 $H(x_1) = H(x_2)$ 在计算上是不可行的。

与原像抗性的区别：原像抗性是从哈希值找任意原像；第二原像抗性是从给定的原像找另一个不同的碰撞原像。

**为什么需要第二原像抗性？** 考虑数字签名场景：Alice哈希消息 $m$ 得到 $h = H(m)$，然后签名 $h$。如果哈希函数不具有第二原像抗性，攻击者可以拿到 $(m, \text{sign}(H(m)))$ 后找到 $m' \neq m$ 使得 $H(m') = H(m)$，从而声称 Alice 签名的其实是 $m'$。这就是为什么哈希函数必须对每一个输入都保证第二原像抗性。

#### 碰撞抗性

碰撞抗性（Collision Resistance）：找到任意两个不同的输入 $x_1 \neq x_2$ 使得 $H(x_1) = H(x_2)$ 在计算上是不可行的。

与第二原像抗性的关键区别：碰撞攻击中攻击者可以自由选择两个输入，不受任何约束。因此碰撞攻击通常比第二原像攻击更容易（由于生日悖论，攻击复杂度只有 $2^{n/2}$ 而非 $2^n$）。

因此，一个声称具有128位安全性的哈希函数（如SHA-256）实际上只提供64位的碰撞安全性。这就是为什么现代哈希函数的输出通常至少为256位：SHA-256提供128位碰撞安全性，SHA-512提供256位碰撞安全性。

**为什么需要碰撞抗性？** 在数字签名中，如果攻击者可以构造两个有相同哈希值但内容完全不同的文档（一个看似无害，一个恶意），然后让Alice签无害的那个，攻击者就能声称Alice签了恶意的那个。更实际的攻击场景：在Git版本控制中，如果SHA-1碰撞被找到（如SHAttered攻击），攻击者可以构造两个有相同Git commit哈希的仓库。

**碰撞抗性的逐步退化**：随着计算能力的提升和攻击技术的改进，哈希函数的碰撞安全性可能下降。例如，MD5已被完全破解（碰撞可在秒级生成），SHA-1的碰撞攻击（SHAttered）需要约 $2^{63}$ 次计算，远低于 $2^{80}$ 的暴力搜索。这就是为什么行业不断推进哈希函数更新（SHA-1 → SHA-256/512 → SHA-3）。

#### 雪崩效应

雪崩效应（Avalanche Effect）：改变输入中的一个比特，输出中的大约一半比特应该发生变化。

更严格的定义是严格雪崩准则（SAC）：改变输入的第 $i$ 个比特，输出中每个比特变化的概率应为1/2。

雪崩效应不是单独的安全性质，而是哈希函数设计的基本要求。它确保了输出对输入的微小变化极度敏感，从而阻止攻击者找到输入与输出之间的相关性。

**设计意义**：没有雪崩效应的哈希函数无法提供原像抗性或碰撞抗性。如果输入的变化只导致输出发生可预测的局部变化，攻击者就可以利用差分分析等手段逐步逼近原像或构造碰撞。

#### Merkle–Damgård结构

Merkle–Damgård（MD）结构是将压缩函数 $f: \{0,1\}^{m+t} \to \{0,1\}^m$ 扩展为接受任意长度输入的哈希函数的标准方法。步骤如下：

1. **填充（Padding）**：在消息末尾添加一个"1"比特和足够多的"0"，使长度对齐到块大小的倍数。最后还附加原始消息的长度（MD强化填充）。
2. **迭代**：将消息分成大小为 $t$ 的块 $m_1, m_2, \ldots, m_k$。从初始向量 $IV$ 开始，计算：
   $$h_0 = IV$$
   $$h_i = f(h_{i-1}, m_i) \text{ for } i = 1, \ldots, k$$
3. **输出**：$H(M) = h_k$

**MD结构的安全性**：Merkle–Damgård结构的一个重要性质是：如果压缩函数 $f$ 是碰撞抗性的，那么整个哈希函数也是碰撞抗性的。这个归约证明保证了MD结构的安全性不弱于压缩函数。

**MD结构的局限性**：
- **长度扩展攻击**：如果知道 $H(M)$，可以在不知道 $M$ 的情况下计算 $H(M \| \text{pad} \| \text{extra})$。这导致MD结构不适合某些应用（如作为PRF使用）。
- **并行化困难**：迭代依赖，不能并行计算。
- **多碰撞攻击**：MD结构对多碰撞的抵抗性不如理想情况。

SHA-256、SHA-512都是MD结构的变体。SHA-3不再使用MD结构。

#### Sponge结构

Sponge结构是SHA-3（Keccak）采用的设计范式。它包含两个阶段：

1. **吸收阶段（Absorb）**：消息块与内部状态异或，然后应用置换函数 $f$。
2. **挤压阶段（Squeeze）**：从内部状态中提取任意长度的输出。

内部状态分为两部分：$r$（比特率，rate）和 $c$（容量，capacity）。总状态大小 $b = r + c$。

**与MD结构的比较**：
- Sponge没有长度扩展攻击的问题——输出长度可任意指定。
- Sponge的安全证明更为简洁，碰撞安全性约为 $2^{c/2}$，原像安全性约为 $2^{c}$。
- Sponge结构更加灵活，可同时用于哈希、PRG、PRF、AEAD等场景（如SHA-3和基于SHA-3的MAC）。
- 安全性由容量 $c$ 而非输出长度决定。SHA-3-256的容量为512位，提供256位碰撞安全性（而非MD结构中的128位）。

### 2.2 Merkle Tree

#### Merkle Root

Merkle Tree（也称为哈希树）是一种二叉树结构，其中叶子节点是数据块的哈希值，非叶子节点是其子节点哈希值的串联的哈希。Merkle Root是根节点的哈希值，是整个数据集的"数字指纹"。

构造过程：
1. 将数据分成 $n$ 个块 $d_1, d_2, \ldots, d_n$。
2. 计算叶子节点：$l_i = H(d_i)$。
3. 逐层向上：如果两个相邻节点 $a, b$ 是兄弟节点，则父节点 $p = H(a \| b)$。
4. 如果某层节点数为奇数，最后一个节点通常会自我复制（或采用特定的处理方式）。
5. 重复直到只剩下一个节点，即Merkle Root。

**为什么Merkle Root能代表整个数据集？** 由于碰撞抗性，如果攻击者试图篡改任何一个数据块，必然导致从该叶子到根路径上的哈希值发生变化，最终Merkle Root会改变。所以Merkle Root相当于一个高效的"数据指纹"——无论数据集多大，指纹只有256位。

#### Inclusion Proof

存在性证明（Inclusion Proof / Merkle Proof）是证明某个数据块属于一个Merkle Tree的证明，而不需要提供整个树。

证明过程：
1. 证明者需要证明数据块 $d_i$ 包含在Merkle Root为 $R$ 的树中。
2. 证明者提供从 $d_i$ 到根路径上的所有兄弟节点哈希值。
3. 验证者用 $d_i$ 计算叶子哈希，然后逐层向上与提供的兄弟节点哈希组合，计算根哈希。
4. 如果计算出的根哈希等于 $R$，则证明有效。

**效率分析**：对于 $n$ 个叶子节点，证明大小（兄弟节点数量）为 $O(\log n)$。验证时间复杂度也是 $O(\log n)$。这意味着对于拥有一百万个数据块的系统，存在性证明只需大约20个哈希值，验证只需20次哈希计算。

**直觉理解**：为什么只需要兄弟节点？因为验证者只需要能够从叶子逐层计算到根。对于计算某个父节点的哈希值，需要该父节点的两个子节点。验证者不知道其中一个子节点（这正是要验证的路径上的那个），所以需要证明者提供另一个子节点（兄弟节点）。

#### 数据完整性验证

Merkle Tree在数据完整性验证中有广泛应用：

**文件系统验证**：Dropbox、Google Drive等云存储服务使用Merkle Tree来验证文件同步的完整性。客户端和服务器各自计算文件的Merkle Tree，通过比较Merkle Root来快速检测不一致。当不一致时，通过二分法逐层对比，准确定位到被修改的数据块，而无需传输整个文件。

**P2P网络**：BitTorrent在下载文件时，通过验证每个数据块的Merkle Proof来确保下载的数据没有被篡改。即使从不可信的节点下载数据块，只要Merkle Root可信，就可以验证每个数据块的完整性。

**日志透明度**：Certificate Transparency使用Merkle Tree来维护一个只能追加的公开日志。任何证书的签发都记录在日志中，任何人都可以验证日志的一致性。通过Merkle Proof可以证明某个证书确实被收录，而通过检查不同服务器返回的同一时间点的Merkle Root是否一致，可以检测日志服务器是否分叉。

#### 区块链与可验证存储中的应用

**区块链（Bitcoin）**：每个区块包含一个Merkle Tree，其叶子是区块中的所有交易。Merkle Root被包含在区块头中。SPV（Simplified Payment Verification）节点不下载完整区块，只下载区块头。当需要验证某笔交易是否包含在区块中时，SPV节点只需要请求该交易的Merkle Proof（约 $\log n$ 个哈希）即可验证，无需同步整个区块。这使得轻钱包在资源受限设备上得以运行。

**以太坊**：使用更复杂的Merkle Patricia Trie，支持三种节点：扩展节点、分支节点和叶子节点。它不仅管理交易，还管理账户状态（余额、nonce、代码哈希、存储根）。这使得以太坊节点可以验证任意账户的任意状态而不需要同步整个区块链状态。

**可验证存储（如Filecoin、Arweave）**：存储矿工需要证明他们在持续存储数据。通过提交Merkle Root作为对数据的承诺，然后使用随机挑战（要求矿工在特定位置提供Merkle Proof），验证数据的完整存储。这结合了Merkle Tree的证明效率和概率性审计。

### 2.3 密码承诺 Commitment

#### Commit与Open

密码承诺（Cryptographic Commitment）是密码学中的一个两阶段协议：

1. **承诺阶段（Commit）**：承诺者选择一个值 $m$，计算承诺值 $c = \text{Commit}(m, r)$，其中 $r$ 是随机数（盲化因子）。承诺者将 $c$ 发送给接收者。此时 $c$ 绑定了 $m$，但不会泄露 $m$ 的任何信息。
2. **打幵阶段（Open）**：承诺者公开 $(m, r)$，接收者可以验证 $\text{Commit}(m, r) = c$。

承诺方案类似于把秘密写在纸上放进密封的信封里交给对方——在打开前，对方不知道内容（隐藏性）；打开后，内容不能改变（绑定性）。

#### 隐藏性

隐藏性（Hiding）：接收者在收到承诺值 $c$ 后，无法获知被承诺的值 $m$ 的任何信息。

形式化定义：对于任意两个不同的消息 $m_0, m_1$，承诺值的分布计算上不可区分：
$$\{ \text{Commit}(m_0, r) \} \approx_c \{ \text{Commit}(m_1, r) \}$$

隐藏性分为：
- **计算隐藏（Computational Hiding）**：只有计算能力有限的攻击者不能区分，但理论上可以暴力破解。
- **完美隐藏（Perfect Hiding）**：即使攻击者拥有无限计算能力，也无法区分。信息论意义上的安全性。

#### 绑定性

绑定性（Binding）：承诺者不能找到一个承诺值 $c$ 对应两个不同的消息。

形式化定义：不存在多项式时间算法能输出 $(m_0, r_0, m_1, r_1)$ 使得 $m_0 \neq m_1$ 且 $\text{Commit}(m_0, r_0) = \text{Commit}(m_1, r_1)$。

绑定性的分类：
- **计算绑定（Computational Binding）**：计算能力有限的攻击者不能找到碰撞，但理论上可能存在。
- **完美绑定（Perfect Binding）**：即使无限计算能力也不能找到碰撞。

**重要权衡**：任何承诺方案都不能同时达到完美隐藏和完美绑定。这是因为：
- 如果方案是完美隐藏的，对于同一个承诺值 $c$，存在多个 $(m, r)$ 对使得 $\text{Commit}(m, r) = c$（否则枚举所有消息空间就能确定被承诺的是哪一个）。因此理论上存在碰撞，不能是完美绑定的。
- 反之，如果方案是完美绑定的，则每个 $c$ 对应唯一的 $(m, r)$，因此枚举所有消息就能以高概率确定 $m$，不能是完美隐藏的。

因此实际方案需要权衡：选择**计算隐藏 + 完美绑定**（基于哈希的承诺）或**完美隐藏 + 计算绑定**（基于离散对数的承诺如Pedersen）。

#### 完美隐藏与计算绑定

**基于哈希的承诺**：
$$\text{Commit}(m, r) = H(m \| r)$$
- 完美绑定：如果 $H$ 是碰撞抗性的，理论上不能找到碰撞（但这是计算假设，所以实际上是计算绑定）。
- 计算隐藏：如果 $H$ 的输出分布均匀，隐藏性是计算性的。

**为什么需要随机数 $r$？** 因为如果不使用 $r$，$\text{Commit}(m) = H(m)$ 不满足隐藏性——攻击者可以穷举猜测 $m$ 并计算 $H(m)$ 与承诺值比较。随机数 $r$ 扩展了猜测空间（$r$ 通常为128位或更多），使得暴力枚举不可行。

#### Pedersen Commitment

Pedersen承诺是基于离散对数假设的承诺方案：

- **参数**：在素数阶群 $\mathbb{G}$ 中，选择两个生成元 $g, h$，使得离散对数 $\log_g(h)$ 未知。
- **Commit**：$\text{Commit}(m, r) = g^m h^r$，其中 $m \in \mathbb{Z}_q$，$r \in \mathbb{Z}_q$ 随机选择。
- **Open**：公开 $(m, r)$，验证 $c = g^m h^r$。

**性质**：
- **完美隐藏**：因为 $h^r$ 是随机群元素，对于固定的 $c$ 和 $m$，总存在某个 $r$ 使得等式成立。即使无限计算能力也无法从 $c$ 确定 $m$。
- **计算绑定**：如果攻击者能找到 $(m, r) \neq (m', r')$ 使得 $g^m h^r = g^{m'} h^{r'}$，则 $g^{m-m'} = h^{r'-r}$，从而可以计算 $\log_g(h) = (m-m') / (r'-r)$，打破了离散对数假设。
- **加法同态**：$\text{Commit}(m_1, r_1) \cdot \text{Commit}(m_2, r_2) = \text{Commit}(m_1 + m_2, r_1 + r_2)$。

加法同态是Pedersen承诺最强大的特性。在零知识证明和可验证计算中，验证者可以在不知道 $m_1, m_2$ 的情况下对承诺值进行加法运算，验证如 $m_1 + m_2 = m_3$ 这样的线性关系。

**工程实践**：生成元 $g, h$ 必须由多方参与的可验证过程生成，确保 $\log_g(h)$ 不可知。通常使用Nothing-Up-My-Sleeve（NUMS）方法，如 $g = H(\text{"g"}), h = H(\text{"h"})$。

#### 向量承诺

向量承诺（Vector Commitment）扩展了传统承诺——可以对一个向量 $(m_1, \ldots, m_n)$ 进行承诺，然后证明某个位置上的值是特定值。

$$\text{Com} = \text{Commit}(m_1, \ldots, m_n)$$

**性质**：
- 承诺值大小固定（与 $n$ 无关）。
- 可以对任意位置 $i$ 生成一个存在性证明 $\pi_i$，证明 $m_i$ 是第 $i$ 个分量的值。
- 证明大小通常为 $O(\log n)$ 或 $O(1)$。

**与Merkle Tree的关系**：Merkle Root本质上就是一个向量承诺。Merkle Proof就是位置存在性证明。但传统基于哈希的Merkle Tree证明大小为 $O(\log n)$，而某些基于配对的向量承诺（如Catalano-Fiore）可以实现 $O(1)$ 的证明大小。

向量承诺在可验证计算中非常有用：证明者需要承诺计算过程中使用的所有输入/中间变量，然后针对特定位置生成证明，验证者只需要验证承诺值和局部证明。

#### 多项式承诺

多项式承诺（Polynomial Commitment）允许承诺一个多项式 $f(x) = a_0 + a_1 x + \cdots + a_d x^d$，然后在任意点 $z$ 打开多项式并证明 $f(z) = v$。

**优势**：证明者用一个固定大小的承诺值承诺整个多项式，然后在任意点生成证明，证明大小通常为常数或对数级别（与 $d$ 无关）。

**典型的构造**：
- **KZG承诺（Kate-Zaverucha-Goldberg）**：基于配对的方案，承诺是一个群元素，证明大小是一个群元素（常数大小）。需要可信设置（Trusted Setup）。
- **Bulletproofs**：基于内积论证，不需要可信设置，但证明大小为 $O(\log d)$。

**为什么多项式承诺如此重要？** 多项式承诺是现代高效零知识证明系统（如PLONK、Marlin、Halo）的核心构建块。在可验证计算中，算术电路被编码为多项式，证明者承诺多项式，然后通过随机挑战打开特定点来验证计算的正确性。多项式承诺的常数大小证明使得这些zk-SNARK系统具有极短的证明和常数时间的验证。

**关键洞察**：多项式承诺将"证明一个大的计算"问题简化为"证明一个多项式在某点的求值"。由于Schwartz-Zippel引理，如果两个不同的多项式在随机选择的点上一致，则它们以高概率完全相同。因此随机挑战点上的打开足以证明多项式的全局正确性。

### 2.4 密码累加器

#### Membership Proof

密码累加器（Cryptographic Accumulator）允许将一个大集合 $S = \{x_1, \ldots, x_n\}$ 压缩为一个固定大小的值 $acc$（累加值），然后为每个 $x_i \in S$ 生成一个成员证明 $w_i$。

**成员证明的性质**：
- 已知 $acc$ 和 $w_i$，任何人可以验证 $x_i$ 属于 $S$。
- 证明大小通常与 $n$ 无关（常数大小）或呈对数关系。
- 伪造成员证明在计算上不可行。

**与Merkle Tree的区别**：Merkle Tree本质上是一种累加器，但其证明大小是 $O(\log n)$。而基于RSA或配对的累加器可以实现常数大小的证明。

#### Non-membership Proof

非成员证明（Non-membership Proof）证明某个元素 $x$ **不** 属于集合 $S$。这比成员证明更困难，因为证明"不在"比证明"在"需要更多的结构。

构造思路：在RSA累加器中，累加值为 $acc = g^{\prod_{x_i \in S} (x_i)}$。要证明 $x \notin S$，需要证明 $x$ 不是累加值指数的因子。这可以通过证明存在整数 $a, b$ 使得 $a \cdot \prod_{x_i \in S} (x_i) + b \cdot x = 1$（即扩展欧几里得算法），从而利用Bezout恒等式构造证明。

非成员证明在证书撤销场景中很重要：验证者需要证明某个证书没有被撤销（不在撤销列表中），而不是仅仅验证它在签发列表中。

#### RSA Accumulator

RSA累加器是最早的密码累加器之一，基于RSA假设：

- **密钥生成**：选择RSA模数 $N = pq$（$p, q$ 为素数），以及一个生成元 $g \in \mathbb{Z}_N^*$。陷门信息 $\phi(N) = (p-1)(q-1)$ 通常被丢弃或由可信方管理。
- **累加**：$acc = g^{\prod_{x_i \in S} H(x_i)} \mod N$，其中 $H$ 将元素映射为素数（确保唯一分解）。
- **成员证明**：对于 $x_j \in S$，$w_j = g^{\prod_{x_i \in S, i \neq j} H(x_i)} \mod N$。验证：$acc \stackrel{?}{=} w_j^{H(x_j)} \mod N$。
- **非成员证明**：使用Bezout恒等式，需要证明存在 $a, b$ 使得 $a \cdot \prod_{x_i \in S} H(x_i) + b \cdot H(x) = 1$。

**为什么元素必须映射为素数？** 因为我们需要唯一分解性质。如果允许合数，攻击者可能通过指数因式分解作弊。将元素映射为素数确保了集合中每个元素的唯一代表性。

**RSA累加器的优势**：常数大小的证明（无论集合多大），成员证明的验证只需一次模指数运算。

**RSA累加器的劣势**：
- 需要可信设置（或者陷门信息 $\phi(N)$ 必须被丢弃，否则可伪造证明）。
- 模指数运算开销大。
- 更新操作（添加/删除元素）需要 $O(n)$ 重算所有证明（除非使用动态累加器）。
- 元素必须映射为素数，这个映射本身有一定的计算开销。

#### 动态累加器

动态累加器（Dynamic Accumulator）支持高效的添加和删除操作，更新累加值只需要常数或对数时间，而不需要重算整个集合。

**添加元素**：添加 $x_{n+1}$ 后，新累加值 $acc' = acc^{H(x_{n+1})} \mod N$。
**删除元素**：删除 $x_j$ 后，新累加值 $acc' = acc^{H(x_j)^{-1} \mod \phi(N)} \mod N$。这需要 $\phi(N)$ 的知识，所以只有陷门的持有者可以删除元素（非陷门删除需要使用双线性映射）。

**证明更新**：成员证明也需要更新。当添加新元素后，证明 $w_j$ 需要更新为 $w_j' = w_j^{H(x_{n+1})} \mod N$。如果不更新，旧证明会失效（因为累加值变了）。这正是动态累加器的工程难点：每次集合变化后，所有现有成员都需要更新他们的证明。

**实际应用**：在证书撤销场景中，证书颁发机构维护一个撤销证书的累加器。每个未撤销证书的持有者定期获取更新后的成员证明。但每次有证书被撤销，所有"幸存"证书的证明都需要更新——频繁更新的开销是主要瓶颈。

#### 在匿名凭证和区块链中的应用

**匿名凭证（Anonymous Credentials）**：用户从颁发者获取一组属性（年龄>18、国籍等）的密码累加器成员证明。在验证时，用户可以选择性地揭示部分属性（如只证明"年龄>18"而不泄露具体年龄），然后使用零知识证明向验证者证明这些属性被包含在累加器中。这个过程保护了用户的隐私——验证者无法知道用户的具体属性值，只知道属性被权威机构认证过。

**区块链中的UTXO管理**：在区块链系统中，全节点需要知道所有未花费交易输出（UTXO）的状态。使用累加器可以将UTXO集合压缩为一个短值，轻节点只需要存储这个累加值。当需要验证某笔交易包含某个UTXO时，通过零知识证明或直接验证成员证明即可，无需同步整个UTXO集合。这对于提高轻节点的效率和可扩展性非常重要。

**可验证注册表**：在以太坊的零知识应用（如zkSync）中，使用Merkle Tree作为累加器来维护账户状态的承诺。证明者可以证明一个账户存在于状态树中且有特定余额，而不需要暴露具体是哪个账户。这通过结合Merkle Proof和零知识证明实现。

## 第3章 对称密码

### 3.1 分组密码

#### Feistel结构

Feistel结构是构造分组密码的一种通用框架，由Horst Feistel在IBM设计Lucifer密码时提出（后来成为DES的基础）。

**基本结构**：
- 将明文分成两半：$L_0, R_0$（各 $n/2$ 位）。
- 对于 $i = 1$ 到 $r$ 轮：
  $$L_i = R_{i-1}$$
  $$R_i = L_{i-1} \oplus F_i(R_{i-1}, K_i)$$
  其中 $F_i$ 是轮函数，$K_i$ 是子密钥。
- 输出 $(L_r, R_r)$ 作为密文。

**Feistel结构的核心特性**：
- **加解密结构相同**：解密与加密使用相同的算法和子密钥，只是子密钥的使用顺序相反。这极大地简化了实现——硬件只需实现加密方向，解密通过反向使用密钥调度即可。
- **轮函数 $F$ 不需要可逆**：因为无论 $F$ 是什么，Feistel结构都是可逆的。解密时，给定 $L_i, R_i$，可以恢复 $L_{i-1}, R_{i-1}$：
  $$R_{i-1} = L_i$$
  $$L_{i-1} = R_i \oplus F_i(R_{i-1}, K_i) = R_i \oplus F_i(L_i, K_i)$$
- **轮函数的伪随机性决定安全性**：Luby和Rackoff证明，如果 $F$ 是安全的PRF，那么3轮Feistel网络得到安全的PRP，4轮得到安全的SPRP。

**安全性依赖于轮数**：Feistel网络的安全性随轮数增加而提升。对于 $n=64$ 的分组，建议至少16轮（如DES的16轮）。更多的轮数提供了更好的混合（diffusion）和对抗差分/线性密码分析的能力。

**典型例子**：DES使用16轮Feistel网络，分组64位，密钥56位。Blowfish、Twofish等也使用Feistel结构。

#### SPN结构

SPN（Substitution-Permutation Network）是另一种分组密码设计范式，与Feistel结构形成对照。

**基本组件**：
1. **替代层（Substitution, S-box）**：非线性变换，提供混淆（Confusion）。通常是一个固定的查表操作，将 $m$ 位输入映射为 $m$ 位输出。
2. **置换层（Permutation, P-box）**：线性变换，提供扩散（Diffusion）。将比特位置换或混合。
3. **密钥加层（AddRoundKey）**：与轮密钥异或。

**一轮SPN操作**：
$$x \to \text{AddRoundKey}(x, K_i) \to \text{SubBytes}(x) \to \text{ShiftRows}(x) \to \text{MixColumns}(x)$$

**SPN vs. Feistel**：
- SPN在每一轮中对整个数据块进行操作，而Feistel只操作一半。因此SPN通常能更快地实现雪崩效应（1轮SPN就能改变输出的一半以上比特）。
- SPN的加解密通常不同（因为S-box和P-box组合的逆与正向操作不同），需要分别实现加密和解密逻辑。
- SPN更适合硬件实现（并行度高），而Feistel更适合软件实现（相同代码加密和解密）。
- SPN的分组大小通常更大（如AES的128位 vs DES的64位），部分原因是SPN的扩散更快，不易受生日攻击影响。

#### AES基本结构

AES（Advanced Encryption Standard）是Rijndael算法的标准化版本，使用SPN结构，分组大小128位，支持128/192/256位密钥。

**AES-128的参数**：
- 分组大小：128位（16字节）
- 密钥长度：128位
- 轮数：10轮（AES-192为12轮，AES-256为14轮）
- 状态（State）：$4 \times 4$ 字节矩阵

**每轮操作**（前9轮）：
1. **SubBytes**：每个字节通过S-box进行非线性替换。AES的S-box基于有限域 $\mathbb{F}_{2^8}$ 中的乘法逆和仿射变换构造，具有最优的差分均匀性和非线性度。
2. **ShiftRows**：状态矩阵的行循环左移。第0行不移，第1行移1字节，第2行移2字节，第3行移3字节。这提供了行间扩散。
3. **MixColumns**：状态矩阵的每列视为 $\mathbb{F}_{2^8}$ 上的4维向量，与固定矩阵 $M$ 相乘（多项式 $c(x) = 3x^3 + x^2 + x + 2$）。这提供了列内扩散。
4. **AddRoundKey**：状态与轮密钥异或。

**最后一轮**：省略MixColumns操作（使解密结构对称）。

**设计智慧**：
- **宽轨迹策略（Wide Trail Strategy）**：AES的设计确保差分和线性传播经过多轮后覆盖整个状态。MixColumns保证了活动S-box的最小数量。
- **所有操作可高效实现**：SubBytes可以通过查表实现；ShiftRows是字节重排；MixColumns可以通过查表或位运算实现；AddRoundKey是简单的异或。
- **加解密不完全对称**：因为MixColumns不是自逆的，解密需要使用InvMixColumns和InvSubBytes。但在硬件实现中，这可以通过复用加密核心加上额外的解密硬件来解决。

**安全性现状**：经过20多年的密码分析，AES-128目前仍然安全。最好的攻击（如Biclique攻击）只能将AES-128的有效密钥空间降低约4位（即 $\approx 2^{124}$ 的复杂度），在物理上不可实现。量子攻击（Grover搜索）能将AES-128的密钥搜索降为 $2^{64}$，所以行业正逐步推广AES-256以应对量子威胁。

#### 密钥扩展

密钥扩展（Key Schedule / Key Expansion）从主密钥 $k$ 派生出每一轮使用的轮密钥（Round Key）。

**AES的密钥扩展**：以AES-128为例，主密钥是16字节（128位），需要11个轮密钥（第0轮加前和10轮后各一个），每个16字节，共176字节。

算法：
1. 将16字节主密钥放入前4个字 $w[0], w[1], w[2], w[3]$（每字4字节）。
2. 对于 $i = 4$ 到 $43$：
   - 如果 $i \equiv 0 \pmod 4$：$w[i] = w[i-4] \oplus \text{SubWord}(\text{RotWord}(w[i-1])) \oplus \text{Rcon}[i/4]$
   - 否则：$w[i] = w[i-4] \oplus w[i-1]$

其中：
- **RotWord**：字的4字节循环左移一位。
- **SubWord**：对每字节应用S-box。
- **Rcon**：轮常数，在不同轮中提供差异化。

**密钥扩展的设计原则**：
- **轮密钥之间不能有简单的代数关系**：如果攻击者能从一轮密钥推导出其他轮密钥，轮数增加无法提升安全性。
- **同一轮内的4个字不能太相关**：AES密钥扩展中的 $\text{RotWord}$ 和 $\text{SubWord}$ 提供了非线性，$\text{Rcon}$ 确保各轮密钥不同。
- **主密钥的每个比特应影响多个轮密钥**：这样即使部分密钥信息泄露，也不能轻松恢复全部密钥。

**常见攻击**：针对AES-192和AES-256的相关密钥攻击（Related-Key Attack）利用了密钥扩展中的弱点（轮密钥之间的相关性稍强于预期），可以降低约4位的安全性。但这不影响AES-128，且在实际攻击场景中攻击者通常不能控制密钥关系。

#### S盒与线性层

**S盒（Substitution Box）**：提供混淆（Confusion）——使密钥与密文之间的关系复杂化。

AES的S-box具有以下精心设计的性质：
- **最大差分均匀性** $\delta = 4$：对任意非零输入差分 $\Delta x$，只有不超过4个输出差分 $\Delta y$ 可以达到。这抵抗了差分密码分析。
- **最大线性偏差** $\epsilon = 1/32$（非线性度 $NL = 112$）：S-box与任何线性函数的相似度不能超过 $1/32$。这抵抗了线性密码分析。
- **代数次数为7**：作为256种可能输入上的布尔函数，其代数表达式次数为7/8（非零线性组合的代数次数至少为7），抵抗了高次积分攻击。
- **没有不动点**：$\text{S-box}(x) \neq x$ 且 $\text{S-box}(x) \neq \bar{x}$。

**线性层（Diffusion Layer）**：提供扩散——单个明文字符的变化应影响尽可能多的密文字符。

AES的线性层由ShiftRows和MixColumns组成：
- **分支数（Branch Number）为5**：MixColumns使用MDS（Maximum Distance Separable）码，在 $\mathbb{F}_{2^8}$ 上的$[4, 2, 5]$ MDS码保证了在4字节输入中，至少5个字节在输入和输出中合计活跃。这是最优的——对于4字节到4字节的线性变换，最大可能分支数是5。
- **宽轨迹策略保证活跃S盒数量**：经过4轮AES后，任意差分或线性特征至少涉及25个活跃S盒。给定每个S盒的差分概率为 $2^{-6}$，25个活跃S盒意味着总的差分概率不超过 $2^{-150}$，远低于AES分组大小128位的穷举下限。

**设计启示**：S盒处理非线性/混淆，线性层处理扩散/排列。两者结合——混淆使密钥关系复杂化，扩散使局部模式迅速传播——共同实现了Shannon提出的"混淆与扩散"原则。

### 3.2 分组密码工作模式

分组密码本身只能加密固定长度的单个分组。工作模式（Mode of Operation）将分组密码扩展到任意长度消息的加密。

#### ECB

电子密码本模式（Electronic Codebook, ECB）是最简单的工作模式：将消息分成独立分组，每个分组用相同的密钥独立加密。

$$c_i = E_k(m_i)$$

**优点**：可以并行加密/解密，支持随机访问（直接解密第 $i$ 块而不需要其他块）。

**严重缺陷**：
- **确定性的加密**：相同的明文分组总是产生相同的密文分组。这意味着密文会泄露明文的模式信息——在图像加密中，原始图像的轮廓在密文中清晰可见。
- **重放攻击**：攻击者可以交换、删除、复制密文分组，解密时接收者无法察觉。
- **分组边界对齐**：密文分组边界与明文分组边界完全对应。

**实际应用**：在密码学中，ECB模式几乎从不单独用于加密。它唯一有价值的用途是作为构造更复杂模式的基础组件（例如，CTR模式将分组密码作为PRF使用，本质上是将AES视为ECB模式处理计数器）。

**经典反例**：ECB加密企鹅图像——密文中依然能看到企鹅的轮廓，因为相同颜色的区域产生相同的密文。

#### CBC

密文分组链接模式（Cipher Block Chaining, CBC）引入了分组间的依赖关系：

$$c_0 = IV$$
$$c_i = E_k(m_i \oplus c_{i-1})$$

其中 $IV$ 是初始化向量（Initialization Vector），必须是不可预测的随机数。

**安全性分析**：
- 链接机制确保每个密文分组依赖于之前所有明文分组。相同的明文分组在不同的上下文中产生不同的密文。
- $IV$ 的随机性至关重要：如果 $IV$ 是可预测的（如计数器），某些攻击（如BEAST攻击）可以利用这一点。
- **串行加密，并行解密**：加密时 $c_{i-1}$ 未确定前无法计算 $c_i$；解密时 $m_i = D_k(c_i) \oplus c_{i-1}$ 可以并行。
- **填充预言机攻击（Padding Oracle Attack）**：如果系统在解密时泄露填充是否有效，攻击者可以逐字节恢复明文。这是CBC模式最著名的侧信道攻击。

**为什么CBC加密需要随机IV？** 如果IV固定，相同的消息产生相同的密文，这不满足语义安全性（攻击者可以区分两次加密的消息是否相同）。随机IV确保即使相同消息被加密多次，每次的密文都不同。

**为什么不能直接使用全零IV？** 全零IV意味着第一个分组 $c_1 = E_k(m_1 \oplus 0) = E_k(m_1)$。如果攻击者已知某个消息-密文对，就能构建一个查找表。更重要的是，这与ECB的区别只是多了一个分组链接，但IV可预测仍会泄露某些模式信息。

#### CTR

计数器模式（Counter, CTR）将分组密码转换为流密码：

$$c_i = m_i \oplus E_k(\text{nonce} \| \text{counter}_i)$$

**工作原理**：
- 使用一个Nonce（每次加密唯一）和一个递增计数器构造输入分组。
- 对每个输入分组计算 $E_k(\text{nonce} \| \text{counter}_i)$ 作为密钥流块。
- 密文 = 明文 $\oplus$ 密钥流块。

**优势**：
- **完全并行**：所有密钥流块可以同时预计算。加密和解密都使用加密函数（不需要解密函数）。
- **随机访问**：可以解密任意位置的分组，只需要计算该位置的密钥流块。这对于磁盘加密等场景是巨大优势。
- **不需要填充**：最后一块密钥流可以截断到实际消息长度。不增加通信开销。
- **预处理友好**：在知道消息之前可以预先生成密钥流——这对于高吞吐量服务器来说可以降低延迟。

**安全要求**：
- **Nonce绝不能重复**：如果两个消息使用相同的 $(k, \text{nonce})$，密钥流完全相同：$c \oplus c' = m \oplus m'$，攻击者可以轻松恢复两个明文的异或，进而推导出明文。
- **计数器不能溢出**：如果计数器在加密过程中回绕，密钥流开始重复，安全性崩溃。

**CTR vs. CBC**：CTR在安全性和性能上都优于CBC，因此在现代协议（如TLS 1.3、IPsec）中已经取代了CBC。

#### OFB

输出反馈模式（Output Feedback, OFB）也是将分组密码转换为流密码：

$$s_0 = IV$$
$$s_i = E_k(s_{i-1})$$
$$c_i = m_i \oplus s_i$$

**特点**：
- 密钥流 $s_i$ 完全独立于明文和密文，只取决于密钥和IV。
- **错误传播为零**：密文中的一个比特翻转只导致明文中相同位置的比特翻转（流密码的特征）。
- 加密和解密都使用加密函数。
- 比CTR慢（串行生成密钥流），且不支持随机访问。

**为什么使用OFB？** 在通信链路中比特错误的概率较高时，OFB的错误传播为零的特性很有用（错误不会扩散到其他比特）。但在现代可靠通信中，这个优势不再重要。

#### CFB

密文反馈模式（Cipher Feedback, CFB）是另一种流密码模式：

$$s_0 = IV$$
$$c_i = m_i \oplus E_k(c_{i-1})$$

**特点**：
- 密钥流依赖于前面的密文，而非独立的计数器或状态。
- 错误传播有限：$c_i$ 的错误会影响 $m_i$（通过异或）和 $m_{i+1}$（通过影响 $E_k(c_i)$）。
- 支持分段处理：可以每次加密1字节（$j$ 比特CFB，但会降低吞吐量）。

**CFB vs. OFB**：CFB的密钥流依赖于密文，这使得重复密钥流的风险略低一些（因为密文本身也是变化的）。但CFB的错误传播比OFB多一个分组。

#### GCM

伽罗瓦/计数器模式（Galois/Counter Mode, GCM）是最常用的认证加密模式之一。

**结构**：
- **加密**：使用CTR模式加密消息。
- **认证**：在 $\mathbb{F}_{2^{128}}$ 上的GHASH（基于二进制域的通用哈希函数）对密文和附加数据进行认证。

$$(c, t) = \text{GCM-Encrypt}(k, \text{nonce}, m, a)$$

其中 $c$ 是密文，$t$ 是认证标签，$a$ 是附加认证数据。

**核心设计**：
- **加密与认证并行**：CTR加密和GHASH计算可以流水线并行。
- **$2^{32}$ 限制**：GCM的计数器是32位（下限），因此最多加密 $2^{32}-2$ 个分组（约64GB）。超过这个限制会触发计数器溢出（密钥流重复），这是GCM的一个实际限制。
- **Nonce可以是96位（推荐）或任意长度**：当Nonce为96位时，初始计数器直接设为 $nonce \| 0x00000001$；当Nonce为其他长度时，需要通过GHASH哈希处理。

**安全边界**：
- **认证标签长度**：标准标签长度为128位、120位、112位、104位或96位。更短的标签（如32位、64位）用于低带宽场景但安全性也相应降低。标签越长越安全（碰撞概率越低）。
- **Nonce绝对不能重复**：Nonce重复完全破坏安全性——攻击者可恢复认证子密钥 $H$ 并伪造任意消息。
- **安全容量**：当加密消息总数接近 $2^{32}$ 时，生日边界开始影响认证安全性（GHASH的密钥 $H$ 可能被推导）。

**为什么GCM如此流行？** GCM在硬件加速（AES-NI指令集）下的表现极为出色。现代的Intel/AMD处理器支持PCLMULQDQ指令（用于GHASH中的有限域乘法）和AES-NI，使GCM加解密达到数十Gbps的吞吐量。这使得GCM成为TLS 1.2/1.3、IPsec、SSH、Wi-Fi WPA3等协议的首选AEAD。

### 3.3 流密码

#### 同步流密码

流密码的核心思想是将消息与密钥流逐位（或逐字节）异或。在同步流密码中，密钥流完全由密钥和IV决定，与明文和密文无关。

$$\text{keystream}_i = \text{PRG}(k, \text{IV}, i)$$
$$c_i = m_i \oplus \text{keystream}_i$$

**同步的要求**：发送者和接收者的密钥流必须完全同步。如果有一个密文比特在传输中丢失或插入，后续所有比特的解密都会错误（失去同步）。

**同步流密码的关键特性**：
- 没有错误传播：一个比特的错误只影响该比特的解密。
- 没有填充：消息可以任意长度（包括位级长度）。
- 加解密速度极快（通常比分组密码更快）。
- 状态简单：只需要维护当前密钥流的位置。

#### 密钥流生成

密钥流生成是流密码的核心。密钥流必须满足：
1. **长周期**：密钥流不应在预期使用长度内重复。
2. **统计随机性**：通过所有统计随机性测试。
3. **不可预测性**：给定任意长度密钥流输出，不能预测后续比特（即Next-bit Unpredictability）。

**密钥流生成方法**：
- **基于LFSR的传统流密码**：A5/1（GSM）、RC4（WEP/TLS）。但这些已被攻破——LFSR的线性结构导致攻击者可以通过解线性方程恢复初始状态。
- **基于分组密码的密钥流**：CTR/OFB/CFB模式本质上将分组密码转换为流密码。这种方式安全可靠，利用了经过充分分析的分组密码的安全性。
- **专用流密码设计**：ChaCha20、Salsa20等专门为流密码设计的算法，在性能和安全性上都有优势。

**钥匙流生成的实践建议**：优先使用CTR模式（基于AES的流密码）或ChaCha20这样的专用流密码，避免使用RC4等传统方案。

#### Nonce重复风险

Nonce重复（Nonce Reuse）是流密码最致命的风险。如果两个消息使用相同的 $(k, \text{nonce})$ 加密：

$$c_1 = m_1 \oplus \text{keystream}$$
$$c_2 = m_2 \oplus \text{keystream}$$
$$c_1 \oplus c_2 = m_1 \oplus m_2$$

**后果**：
1. 攻击者获得两个明文的异或值。如果明文有足够冗余（如自然语言、结构化数据、图像等），通过统计分析可以恢复两个明文。
2. 在极端情况下，如果攻击者知道其中一段明文（如已知协议头），可以完全恢复对应位置的密钥流，进而解密其他使用相同密钥流加密的消息。

**为什么Nonce重复的风险被低估？** 许多开发者以为Nonce只需"唯一"而非"不可预测"，于是使用计数器作为Nonce。但问题是：如果两个系统（或同一系统的两个不同会话）在未协调的情况下选择了相同的计数器值，或者系统重启后计数器重置，就会发生Nonce重复。此外，在多线程环境中，对Nonce的原子操作管理不当也容易导致重复。

**典型灾难案例**：
- **WEP**：使用24位IV，在繁忙网络中几小时内IV就会重复。Aircrack-ng利用这个漏洞可以在几分钟内破解WEP密钥。
- **TLS 1.2的Nonce误用**：某些实现使用GCM时没有正确处理随机Nonce，导致同一密钥下Nonce重复。
- **PGP/GPG的随机数生成故障**：某些嵌入式设备上由于熵不足，导致Nonce生成重复，使得加密消息可被解密。

#### ChaCha类结构

ChaCha是Salsa20的改进版本，由Daniel Bernstein设计。它是目前最受推荐的流密码之一（与AES-GCM并列）。

**ChaCha20的核心结构**：

初始状态是一个 $4 \times 4$ 的32位字矩阵（共16个字，512位）：
```
"expand 32-byte k" | key(8 words)
counter(4 words)   | nonce(3 words)
```
其中第一行是常量（"expand 32-byte k"的6个32位字，加上2个零填充？实际是4个字）。

ChaCha的核心操作是**四分之一轮（Quarter Round）**：
$$a += b; d \oplus= a; d <<<= 16$$
$$c += d; b \oplus= c; b <<<= 12$$
$$a += b; d \oplus= a; d <<<= 8$$
$$c += d; b \oplus= c; b <<<= 7$$

每轮由8个四分之一轮组成（4个列轮和4个对角线轮），ChaCha20总共执行20轮。

**为什么ChaCha优于传统流密码？**
1. **无专利限制**：Bernstein将所有Salsa/ChaCha算法放入公有领域。
2. **无侧信道漏洞**：RC4存在已知偏差（第二个输出字节偏向0），而在ChaCha中没有这种统计偏差。ChaCha的操作只涉及32位加、异或和移位，不依赖S盒查表，不容易受基于缓存的侧信道攻击。
3. **软件性能卓越**：ChaCha在缺少AES-NI指令集的平台上（如ARM、嵌入式设备）性能远优于AES-GCM。
4. **安全性边界清晰**：ChaCha20的安全边界大约为 $2^{256}$，远远超过实际使用限制。

**实际应用**：ChaCha20-Poly1305是TLS 1.3的两个强制实现AEAD之一（另一个是AES-128-GCM）。Google的QUIC协议和Android系统也从AES-GCM转向ChaCha20-Poly1305，因为移动设备上ChaCha20的软件实现比AES-GCM更快。

### 3.4 消息认证码 MAC

消息认证码（Message Authentication Code, MAC）确保消息的**完整性**（未被篡改）和**真实性**（确实来自声称的发送者）。

$$t = \text{MAC}_k(m)$$
验证：接收者用相同密钥计算 $t' = \text{MAC}_k(m)$，检查 $t' \stackrel{?}{=} t$。

#### CBC-MAC

CBC-MAC使用分组密码的CBC模式构造MAC：

$$c_0 = 0^n$$
$$c_i = E_k(m_i \oplus c_{i-1})$$
$$t = c_n$$

**安全性条件**：
- **只能处理固定长度消息**：因为CBC-MAC对于变长消息是不安全的——给定 $t_1 = \text{MAC}_k(m_1)$ 和 $t_2 = \text{MAC}_k(m_2)$，攻击者可能构造第三条消息的合法MAC。
- **必须使用全零IV**：使用随机IV的安全性没有额外的益处，反而会导致安全证明失效。
- **消息长度必须在消息末尾或使用长度分离编码**。

**为什么变长不安全？** 假设攻击者获得 $t = \text{MAC}_k(m)$，构造 $m' = m \| (m \oplus t)$（假设 $m$ 是单块）。验证时 $c_1 = E_k(m) = t$，$c_2 = E_k(m \oplus t \oplus t) = E_k(m) = t$，所以 $\text{MAC}_k(m') = t$。攻击者成功伪造了一个新消息的MAC。

**改进方案**：使用EMAC（Encrypted MAC）或CMAC，在最后添加一个密钥相关的处理步骤来解决变长问题。

#### HMAC

HMAC（Hash-based MAC）是目前最广泛使用的MAC之一，基于密码学哈希函数。

$$\text{HMAC}_k(m) = H((k' \oplus \text{opad}) \| H((k' \oplus \text{ipad}) \| m))$$

其中：
- $k'$ 是经过填充的密钥（对于短密钥，用零填充到块长度；对于长密钥，先哈希）。
- $\text{ipad} = 0x36$ 重复（块长度次），$\text{opad} = 0x5c$ 重复。
- $H$ 是底层哈希函数（如SHA-256）。

**安全性**：
- 如果底层哈希函数是碰撞抗性的，HMAC是安全的（这是一个已被证明的定理）。
- HMAC对长度扩展攻击有天然抵抗性：即使知道 $H(k \| m)$，也不能计算 $H(k \| m \| \text{pad} \| m')$，因为 $\text{ipad}$ 和 $\text{opad}$ 与密钥的异或提供了额外的保护层。
- 不需要为HMAC实现额外的加密原语——任何可用的哈希函数都可以。

**为什么HMAC使用两次哈希？** 第一次哈希（内层）确保任何消息变化都会导致内部摘要改变；第二次哈希（外层）确保即使内层哈希被攻破（如找到碰撞），外层仍然提供安全性。此外，$\text{ipad}$ 和 $\text{opad}$ 的异或操作将密钥分成两个不同的部分，使得从外层摘要恢复内层摘要变得不可能。

#### CMAC

CMAC（Cipher-based MAC）是使用分组密码的MAC，替代了旧的CBC-MAC，支持变长消息。

**构造**：CMAC使用CBC-MAC的思路，但在最后一个分组上做了改进：
- 如果消息长度是分组长度的整数倍，最后一个分组与常数 $K_1$ 异或。
- 如果不是整数倍，消息末尾添加"10..."填充后与常数 $K_2$ 异或。
- $K_1, K_2$ 是从密钥派生的子密钥（通过对全零加密并移位得到）。

**为什么需要两个不同的子密钥？** 这解决了CBC-MAC的变长安全问题。由于最后一个分组被处理的方式不同（取决于它是否被填充），攻击者无法将两条不同长度消息的MAC关联起来。两个子密钥的引入确保了填充与否的不可混淆性。

**CMAC vs. HMAC**：
- CMAC使用分组密码（如AES），HMAC使用哈希函数。
- CMAC在硬件加速（AES-NI）下速度更快。
- HMAC在仅支持哈希函数的嵌入式系统中更易实现。
- 安全性都经过充分验证。

#### SUF-CMA安全性

强不可伪造性（Strong UnForgeability under Chosen Message Attack, SUF-CMA）是MAC的标准安全定义。

**定义**：一个MAC方案是SUF-CMA安全的，如果对于所有多项式时间攻击者 $\mathcal{A}$，下列优势可忽略：

$$\Pr\left[\begin{array}{l}
(k) \leftarrow \text{KeyGen}(1^\lambda) \\
(m^*, t^*) \leftarrow \mathcal{A}^{\text{MAC}_k(\cdot)}(1^\lambda) \\
\text{Verify}_k(m^*, t^*) = 1
\end{array}\right] \leq \text{negl}(\lambda)$$

其中 $\mathcal{A}$ 可以自适应地向MAC预言机查询任意消息的标签，且 $(m^*, t^*)$ 不能等于任何查询结果。

**SUF-CMA的要点**：
1. **适应性选择消息攻击**：攻击者可以自由选择任意消息查询标签。这模拟了现实中攻击者可能能够获取一些合法消息-标签对的场景。
2. **不可伪造**：即使看过许多消息-标签对，攻击者也不能产生一个"新对"（未查询过的消息，或已查询过的消息但不同的标签）。
3. **弱不可伪造性（UF-CMA）**：只要求不能伪造新消息的标签，但对于已查询消息的不同标签，UF-CMA不做约束。SUF-CMA要求更强——即使是已查询消息的不同标签也不能伪造。

**为什么需要SUF-CMA？** 在有些协议中，如果攻击者能对已认证的消息计算新的标签，可能会造成协议混乱。例如，在重放攻击中，攻击者可能提供新的标签变体来绕过某些检查。"强"不可伪造性提供了更安全的上界。

### 3.5 认证加密 AEAD

#### 加密与认证为什么不能随意组合

加密提供机密性，MAC提供完整性和真实性。但在实际通信中，这两者必须同时满足。用户直觉上可能认为"先加密再认证"、（encrypt-then-MAC）或"先认证再加密"、（MAC-then-encrypt）或"同时进行"、（encrypt-and-MAC）都可以。

**但并不是所有组合方式都安全：**

1. **加密并MAC（Encrypt-and-MAC）**：先计算 $c = E_k(m)$，再计算 $t = \text{MAC}_{k'}(m)$，发送 $(c, t)$。这里MAC认证的是明文 $m$ 而非密文 $c$。攻击者可能篡改 $c$，但接收者解密后得到的 $m'$ 可能通过MAC验证（如果MAC函数存在某些结构），或者更糟——从 $m$ 泄露的信息（MAC对 $m$ 的计算可能泄露 $m$ 的一部分内容）。SSH协议早期就采用了这种组合方式，发现存在安全问题。

2. **先MAC后加密（MAC-then-Encrypt）**：先计算 $t = \text{MAC}_{k'}(m)$，再计算 $c = E_k(m \| t)$，发送 $c$。这种方法中，MAC标签随着密文一起被加密。但问题是：解密时先解密得到 $m \| t$，然后验证MAC。如果解密输出的填充格式不正确（如使用CBC模式），攻击者可利用填充预言机攻击逐字节恢复明文。TLS 1.2使用了这种方式，导致了著名的Padding Oracle攻击（如POODLE攻击）。

3. **先加密后MAC（Encrypt-then-MAC）**：先计算 $c = E_k(m)$，再计算 $t = \text{MAC}_{k'}(c)$，发送 $(c, t)$。这种组合方式是**安全**的。原因有二：首先，MAC认证的是密文，任何密文篡改都会被MAC检测到；其次，攻击者无法在没有密钥的情况下从密文推导出认证标签。

**结论**：只有Encrypt-then-MAC提供了通用的安全性证明。正确的方式是对密文进行MAC，而不是对明文。

#### Encrypt-then-MAC

Encrypt-then-MAC（EtM）的详细流程：

**加密**：
1. 输入：密钥 $(k_e, k_m)$，明文 $m$，随机数 $nonce$（或IV）。
2. $c = \text{Enc}_{k_e}(m)$（使用Ind-CPA安全的加密方案，如CBC、CTR）。
3. $t = \text{MAC}_{k_m}(c)$（使用SUF-CMA安全的MAC方案，如HMAC）。
4. 输出：$(c, t)$。

**解密**：
1. 输入：密钥 $(k_e, k_m)$，密文 $(c, t)$。
2. 验证 $t' = \text{MAC}_{k_m}(c) \stackrel{?}{=} t$。如果不相等，输出 $\perp$。
3. 解密：$m = \text{Dec}_{k_e}(c)$。
4. 输出：$m$。

**为什么先验证MAC再解密？** 这是安全性的关键。如果先解密再验证，攻击者可能利用解密过程中的侧信道（如填充错误、响应时间差异）逐个比特地恢复明文。一定要在解密前验证MAC，确保消息的完整性之后再进行任何可能泄露信息的操作。

**实际应用**：IPsec使用Encrypt-then-MAC。SSH使用Encrypt-and-MAC（但在实践中是安全的，因为SSH的MAC也计算了分组序列号）。TLS 1.3也采用了Encrypt-then-MAC的思想（通过AEAD实现）。

#### Associated Data

关联数据（Associated Data, AD）是在AEAD方案中需要认证但不需要加密的数据。例如，网络包中的IP头部——路由器需要读取头部来转发，但接收端需要验证头部没有被篡改。

**AEAD的API**：
$$\text{AEAD-Encrypt}(k, \text{nonce}, \text{plaintext}, \text{ad}) \to (\text{ciphertext}, \text{tag})$$
$$\text{AEAD-Decrypt}(k, \text{nonce}, \text{ciphertext}, \text{ad}, \text{tag}) \to \text{plaintext} \text{ or } \perp$$

**为什么需要AD？**
- 在TLS中，TLS记录头部的版本号、内容类型、序列号是AD——它们需要被认证以确保不被篡改，但不能加密（否则接收方无法知道如何解析）。
- 在IPsec中，IP头部字段（如源IP、目的IP、协议号）是AD。
- 在磁盘加密中，扇区号是AD——加密同一块数据时，使用扇区号作为AD可以防止攻击者交换加密扇区。

**AD认证的安全意义**：AD确保了上下文（context）的绑定。攻击者不能将密文从一个上下文（如一个会话）移动到另一个上下文，因为AD的不同会导致标签验证失败。

#### Nonce管理

Nonce（Number used ONCE）是AEAD安全性的关键。不同的AEAD方案对Nonce的要求不同：

**Nonce要求总结**：

| 方案 | Nonce长度 | 要求 |
|------|----------|------|
| GCM | 12字节（推荐） | 对同一密钥必须唯一 |
| ChaCha20-Poly1305 | 12字节 | 对同一密钥必须唯一 |
| AES-GCM-SIV | 12字节 | 可以容忍Nonce重复（但安全性降低） |
| OCB | 15字节（AES-128） | 对同一密钥必须唯一 |

**Nonce管理策略**：

1. **计数器法**：使用单调递增的计数器。最简单、最可靠——只要保证没有两个会话使用相同的初始计数器值。风险：系统重启后计数器重置。

2. **随机数法**：从足够大的空间中随机选择。当Nonce空间足够大（如96位）时，碰撞概率极低。风险：随机数生成器出问题（如熵不足）。

3. **混合法**：高位使用计数器，低位使用随机数。兼顾了唯一性和不可预测性。

**为什么Nonce管理如此重要？** 在非容错AEAD（如GCM、ChaCha20-Poly1305）中，Nonce重复是灾难性的——认证会完全崩溃。而容错AEAD（如AES-GCM-SIV）虽然可以容忍Nonce重复，但会牺牲部分安全性（仅靠密码学保证最多泄露明文是否相同）。

**实践建议**：在1对1的通信场景中，使用计数器作为Nonce是安全的（需要持久化计数器状态）。在服务器-多客户端场景中，使用服务器分配的Unique Nonce或足够大的随机Nonce。在所有场景中，如果使用GCM，强烈建议使用12字节Nonce（避免GHASH处理的复杂度）。

#### GCM与ChaCha20-Poly1305

GCM和ChaCha20-Poly1305是当前最主流的两个AEAD方案，都是TLS 1.3的推荐实现。

**GCM（AES-GCM）**：
- 加密：AES-CTR。
- 认证：GHASH（$\mathbb{F}_{2^{128}}$上的多项式求值）。
- 特点：硬件加速极快（AES-NI + PCLMULQDQ）。
- 限制：消息长度上限约为64GB（$2^{32}-2$ 个分组）。
- 安全性：当Nonce唯一时，安全边界为 $2^{64}$ 个消息（生日边界对认证密钥的影响）。
- Nonce失败模式：灾难性——Nonce重复完全破坏安全性。

**ChaCha20-Poly1305**：
- 加密：ChaCha20流密码。
- 认证：Poly1305（$\mathbb{F}_{2^{130}-5}$上的多项式求值）。
- 特点：软件实现极快（不需要硬件加速），不依赖AES-NI。
- 限制：每个密钥可以加密 $2^{32}$ 个消息（计数器上限）。
- 安全性：安全性边界清晰，约为 $2^{256}$。
- Nonce失败模式：与GCM类似，Nonce重复也是灾难性的。

**如何选择？**

| 场景 | 推荐 |
|------|------|
| x86/x64服务器有AES-NI | AES-GCM（更快） |
| ARM/移动设备无AES-NI | ChaCha20-Poly1305 |
| 需要FIPS认证 | AES-GCM |
| 嵌入式/微控制器 | ChaCha20-Poly1305（实现简单） |
| TLS 1.3 | 两者都是强制选项 |

**关键洞察**：GCM和ChaCha20-Poly1305的安全性都是经过充分研究的，选择主要取决于目标平台的计算能力。从安全角度看，两者提供相似的安全级别（约128位），唯一的区别是ChaCha20-Poly1305不依赖硬件加速，在缺乏AES-NI的平台上表现更好。两者都需要小心的Nonce管理——这是使用者的责任而非方案的问题。

## 第4章 公钥密码

### 4.1 公钥密码基本模型

#### KeyGen

密钥生成（KeyGen）算法生成一对密钥：$(pk, sk) \leftarrow \text{KeyGen}(1^\lambda)$，其中 $pk$ 是公钥（公开），$sk$ 是私钥（保密）。

**KeyGen的核心**：利用单向函数（trapdoor one-way function）的构造。公钥指定了函数本身，私钥提供了反向计算的陷门（trapdoor）。

**形式化要求**：
1. 给定安全参数 $\lambda$（如 $\lambda=128$ 表示128位安全性），KeyGen输出指定长度的密钥对。
2. 公钥 $pk$ 完全定义加密操作，任何人都可以用 $pk$ 加密消息。
3. 私钥 $sk$ 是解密所需的秘密信息。计算 $E_{pk}(m)$ 是容易的，但计算 $D_{sk}(c)$ 只有知道 $sk$ 才可行。

**为什么KeyGen需要随机性？** 因为密钥生成必须产生不可预测的私钥。如果KeyGen是确定性的，那么同一系统生成的密钥将永远相同。这意味著KeyGen必须依赖于CSPRNG来生成足够随机的私钥，然后从私钥推导出公钥。

#### Encrypt

加密算法 $\text{Enc}_{pk}(m)$ 使用公钥 $pk$ 将明文 $m$ 转换为密文 $c$。

**安全要求（IND-CPA）**：公钥加密必须满足选择明文攻击下的不可区分性（Indistinguishability under Chosen Plaintext Attack）。这是因为在公钥密码中，攻击者知道公钥，可以自己加密任意消息。如果加密是确定性的，攻击者只需计算 $E_{pk}(m_0)$ 和 $E_{pk}(m_1)$ 然后与目标密文比较就能知道加密的是哪个消息。

**因此公钥加密必须包含随机性**：每次加密使用不同的随机数 $r$，$\text{Enc}_{pk}(m; r)$ 的输出即使对同一 $m$ 也是不同的随机分布。这正是ElGamal等方案需要随机化加密的原因。

**IND-CCA安全性**：更强的安全性要求，即使攻击者可以解密任意密文（除了挑战密文本身），也不能区分两个消息的密文。这是实际通信场景中需要的最低安全性。

#### Decrypt

解密算法 $\text{Dec}_{sk}(c)$ 使用私钥 $sk$ 将密文 $c$ 恢复为明文 $m$。

**正确性要求**：$\text{Dec}_{sk}(\text{Enc}_{pk}(m)) = m$ 对所有 $(pk, sk) \leftarrow \text{KeyGen}(1^\lambda)$ 和所有 $m$ 成立（允许可忽略的错误概率）。

**解密必须小心处理错误输出**：如果密文无效或校验失败，解密应返回 $\perp$（特殊符号）而非部分解密结果。这是因为部分解密结果可能泄露私钥信息（如Bleichenbacher攻击）。

#### 公钥与私钥

公钥和私钥的关系是公钥密码学最核心的概念：

- **公钥 = 单向函数的方向**：任何人都可以用公钥加密，这个过程是单向的——没有私钥就不能解密。
- **私钥 = 陷门**：私钥提供了逃逸单向性的能力。对于某些陷门单向函数，知道私钥使得解密变得容易。
- **公钥不能推导出私钥**：这是所有公钥密码学的基础假设。基于困难问题（大整数分解、离散对数、椭圆曲线离散对数等）。

**非对称性的代价**：公钥密码比对称密码慢几个数量级。RSA-2048的加密/解密比AES-128慢约1000倍。这使得公钥密码通常只用于加密短消息（如密钥交换中的对称密钥）。

#### 混合加密

混合加密（Hybrid Encryption）结合公钥密码和对称密码，克服公钥密码速度慢和消息长度有限的问题：

$$c_1 = E_{pk}(k) \quad\text{(使用公钥加密对称密钥)}$$
$$c_2 = \text{AEAD-Encrypt}_k(m) \quad\text{(使用对称密钥加密消息)}$$
$$\text{输出: } (c_1, c_2)$$

**为什么需要混合加密？**
1. **性能**：公钥加密慢，对称加密快。公钥只加密固定长度（如256位）的对称密钥。
2. **消息长度**：大多数公钥方案只能加密有限长度的消息（如RSA-2048最多加密245字节）。
3. **安全性**：对称加密提供认证加密（AEAD），比单独使用公钥加密更安全。

**KEM/DEM框架**：混合加密的形式化模型。
- KEM（Key Encapsulation Mechanism）：生成对称密钥 $k$，并输出其公钥加密 $c_1$。
- DEM（Data Encapsulation Mechanism）：用 $k$ 认证加密消息 $m$。

实际中，$c_1 = \text{Enc}_{pk}(k)$ 通常不是直接加密 $k$，而是通过KEM封装一个临时密钥。KEM确保了即使攻击者得到 $c_1$ 也不能恢复 $k$（满足IND-CCA安全性）。

**示例（TLS 1.3的混合密钥交换）**：
1. 客户端随机生成临时ECDH密钥对 $(sk_e, pk_e)$，发送 $pk_e$ 给服务器。
2. 服务器也生成临时密钥对，计算共享秘密 $s = \text{ECDH}(sk_s, pk_e)$。
3. 双方从 $s$ 派生对称密钥 $k = \text{KDF}(s)$。
4. 后续通信使用AES-GCM或ChaCha20-Poly1305认证加密。

这就是混合加密：ECDH（公钥）用于交换对称密钥，AEAD（对称）用于加密消息。

### 4.2 RSA

#### RSA密钥生成

RSA密钥生成的数学基础：

1. 选择两个大素数 $p, q$（通常各1024位）。
2. 计算 $n = p \times q$（RSA模数，2048位）。
3. 计算 $\phi(n) = (p-1)(q-1)$（欧拉函数）。
4. 选择公钥指数 $e$，通常 $e = 65537$（$2^{16}+1$），原因是：这是一个费马素数，二进制表示为两个"1"比特（低计算开销）且与 $\phi(n)$ 互质的概率极高。
5. 计算私钥指数 $d \equiv e^{-1} \pmod{\phi(n)}$（扩展欧几里得算法）。
6. 公钥：$(n, e)$；私钥：$(n, d)$。

**为什么 $e=65537$ 是标准选择？**
- $e=3$ 太小：如果三个不同的接收者使用相同的 $e=3$ 和不同 $n$，且用同一明文加密，攻击者可以用中国剩余定理恢复明文（Hastad's broadcast attack）。
- $e=65537$ 足够大，抵抗小指数攻击，同时加密时只需17次模乘（因为 $65537 = 2^{16}+1$，二进制中只有两个1）。
- $\gcd(e, \phi(n)) = 1$ 以高概率成立，因为 $65537$ 是素数且 $p, q$ 是安全素数时 $\phi(n)$ 不含因子 $65537$。

**安全性考虑**：$p$ 和 $q$ 必须是随机生成的大素数，且长度应接近（防止Fermat因式分解）。$|p-q|$ 不能太小（防止平方根攻击）。$p-1$ 和 $q-1$ 应有大素因子（防止Pollard's $p-1$ 攻击）。

#### 教科书RSA的问题

教科书RSA就是直接计算 $c \equiv m^e \pmod{n}$。这存在严重问题：

1. **确定性加密**：同一个明文总是产生相同的密文，不满足IND-CPA安全性。攻击者可枚举消息空间验证猜测。

2. **乘法同态性**：$E(m_1) \cdot E(m_2) \equiv m_1^e \cdot m_2^e \equiv (m_1 \cdot m_2)^e \equiv E(m_1 \cdot m_2) \pmod{n}$。攻击者可以在不知道明文的情况下操纵密文。

3. **小消息攻击**：如果 $m < 2^{\lfloor \log_2 n / e \rfloor}$，那么 $m^e < n$，密文不经过模约减。攻击者只需计算 $\sqrt[e]{c}$ 即可恢复 $m$。

4. **广播攻击**：同一消息 $m$ 发送给 $e$ 个不同的接收者（各自有 $n_i$），攻击者可以通过中国剩余定理求解方程组。

5. **选择密文攻击**：攻击者想要解密 $c$，可以询问解密预言机 $c' \equiv c \cdot r^e \pmod{n}$（盲化），得到 $m' \equiv m \cdot r \pmod{n}$，然后计算 $m \equiv m' \cdot r^{-1} \pmod{n}$。这就是教科书RSA完全不能抵抗选择密文攻击的原因。

**总结**：教科书RSA从未被用于实际——它只是一个教学原型。所有实际部署都使用填充方案（如OAEP）来消除这些弱点。

#### OAEP

最优非对称加密填充（Optimal Asymmetric Encryption Padding, OAEP）是RSA的标准填充方案，目的是消除教科书RSA的安全漏洞。

**OAEP结构**：

$$\text{OAEP}(m) = X \| Y$$
其中 $X = m \oplus G(r) \| 0^{k_1}$，$Y = r \oplus H(X)$。

- $m$：明文（填充后）。
- $r$：随机 $k_0$ 位字符串。
- $G, H$：哈希函数（如SHA-256），视为随机预言机。
- $k_0, k_1$：参数（$k_0$ 通常为 128 或 256 位，$k_1$ 为 64 或 128 位）。
- $0^{k_1}$：固定的检查位，用于检测解密错误。

**加密**：$c \equiv (\text{OAEP}(m))^e \pmod{n}$。
**解密**：$m = \text{OAEP}^{-1}(c^d \mod n)$。

**OAEP如何解决教科书RSA的问题？**

1. **随机化**：$r$ 使得同一消息每次加密都不同，满足IND-CPA。
2. **非齐性**：由于Hash函数的雪崩效应，翻转密文的任何比特都会导致完全不同的解密结果，抵抗了选择密文攻击（IND-CCA）。
3. **可检测性**：如果在解密时 $0^{k_1}$ 验证失败，输出 $\perp$，阻止攻击者利用部分信息。
4. **抵抗小消息攻击**：消息在填充后长度接近 $n$ 的位长，$m^e$ 总是超过 $n$。

**为什么OAEP安全？** OAEP的安全性在随机预言机模型（ROM）下被严格证明：如果RSA是陷门单向置换，那么RSA-OAEP是IND-CCA安全的。这个证明将任何攻击OAEP的攻击者转化为破解RSA本身的攻击者（归约证明）。

**OAEP的局限性**：
- 要求 $n$ 足够大以容纳填充和消息（最小 2048 位 RSA + OAEP）。
- 在随机预言机模型中证明安全——如果哈希函数在实际中表现不佳，安全性可能受影响。
- 没有提供认证加密（如果需要认证，必须在消息中添加签名或使用AEAD）。

**实际应用**：RSA-OAEP是TLS 1.2中RSA密钥交换的标准填充方案。在PKCS#1 v2.2标准中被规范。

#### RSA签名

RSA不仅用于加密，也是常用的数字签名方案。

**RSA签名**：
- 签名：$\sigma \equiv m^d \pmod{n}$（用私钥指数）。
- 验证：$m \stackrel{?}{\equiv} \sigma^e \pmod{n}$（用公钥指数）。

**教科书RSA签名的问题**：
1. **存在性伪造**：攻击者随机选择 $\sigma$，计算 $m \equiv \sigma^e \pmod{n}$，即可伪造签名 $(\sigma, m)$。虽然 $m$ 可能不是有意义的消息，但对于某些协议这可能带来风险。
2. **乘法同态性**：$\sigma_1 \cdot \sigma_2 \equiv m_1^d \cdot m_2^d \equiv (m_1 \cdot m_2)^d \pmod{n}$。这意味着给定两个有效签名，可以伪造其乘积的签名。

**解决方案：签名时使用哈希 + 填充**：
$$\sigma \equiv (\text{PSS}(m))^d \pmod{n}$$

**PSS（Probabilistic Signature Scheme）**：RSA签名的标准填充方案。
- 使用随机的盐值（salt）使签名随机化。
- 证明在ROM下是安全的（EU-CMA，存在性不可伪造）。
- 最终被采纳为PKCS#1 v2.2标准。

**RSA签名的安全要求**：消息必须先哈希再签名。如果直接签名长消息，签名速度极慢且签名长度固定（等于RSA模数）。哈希使得任意长度消息都可以被签名，且哈希的碰撞抗性保证了签名的安全性。

#### RSA常见实现风险

RSA实现中常见的安全漏洞：

1. **时序攻击（Timing Attack）**：模指数运算的时间与指数比特模式相关。如果实现中的平方-乘循环在比特为1时做乘法，在比特为0时不执行，攻击者可以通过测量解密/签名时间来逐比特恢复私钥指数 $d$。

   防御：使用**常数时间实现**（始终执行乘法和条件赋值），或使用Montgomery乘法等恒定时间算法。

2. **侧信道攻击**：通过功耗分析、电磁辐射等物理信道泄露私钥信息。防御：使用RSA盲化——在解密时，先将密文乘以 $r^e$ 后解密，再乘以 $r^{-1}$ 恢复明文。

3. **Bleichenbacher攻击（百万消息攻击）**：针对PKCS#1 v1.5填充的攻击。攻击者可以向服务器发送经过修改的密文，观察服务器返回的错误类型（填充有效 vs 无效），从而逐步恢复明文。这种方法需要约一百万个自适应查询。防御：使用OAEP（OAEP自己就可以抵抗选择密文攻击），或确保服务器返回一致的错误响应（不泄露填充是否有效）。

4. **错误攻击（Fault Attack）**：物理诱导计算错误（通过电压抖动、激光照射等），迫使RSA签名计算出现错误。如果签名 $(m, \sigma)$ 和错误签名 $(m, \sigma')$ 都有效，攻击者可以分解 $n$。防御：签名时进行正确性验证，或使用**冗余计算**（计算两次）。

5. **模数共享**：不同实体共享相同的 $n$ 但不同的 $e$。如果两个公钥 $(n, e_1)$ 和 $(n, e_2)$ 共享同一 $n$，且 $\gcd(e_1, e_2) = 1$，那么两个密文 $c_1 = m^{e_1} \mod n$ 和 $c_2 = m^{e_2} \mod n$ 会导致明文暴露（扩展欧几里得算法）。防御：每个实体生成独立的模数 $n$。

6. **$p$ 或 $q$ 泄露**：如果私钥的素数 $p$ 或 $q$ 通过侧信道泄露，确保安全的责任就完全没有了——只需分解 $n$ 即可。私钥的所有组件都应妥善保护。

**工程启示**：实现RSA远比理解其数学原理复杂。安全实现需要处理常数时间、盲化、错误一致性和填充验证等多个层面的细节。这是为什么在大多数场景中推荐使用高级库（如libsodium、OpenSSL、BoringSSL）而非自行实现。

### 4.3 ElGamal

#### ElGamal加密

ElGamal加密基于Diffie-Hellman密钥交换的思路，在素数阶群中操作。

**密钥生成**：
- 选择大素数 $q$ 和生成元 $g$（通常使用 $q$ 阶循环群 $\mathbb{G}$）。
- 随机选择私钥 $x \in \mathbb{Z}_q^*$。
- 计算公钥 $h = g^x \in \mathbb{G}$。
- 公钥：$(q, g, h)$；私钥：$x$。

**加密**：
- 选择随机数 $r \in \mathbb{Z}_q^*$（临时密钥）。
- 计算 $c_1 = g^r$（共享秘密的"公钥部分"）。
- 计算共享秘密 $s = h^r = (g^x)^r = g^{xr}$。
- 计算 $c_2 = m \cdot s$（明文乘以共享秘密）。

**密文**：$(c_1, c_2)$。

**解密**：
- 计算共享秘密 $s = c_1^x = (g^r)^x = g^{xr}$。
- 恢复明文 $m = c_2 \cdot s^{-1}$。

**安全性**：ElGamal的安全性基于计算Diffie-Hellman（CDH）假设——给定 $g^a$ 和 $g^b$，计算 $g^{ab}$ 是困难的。如果CDH是难的，则ElGamal的加密明文在被动攻击下是安全的。

#### 随机化加密

ElGamal的核心特性就是随机化：每次加密选择不同的随机 $r$，得到不同的密文。同一明文 $m$ 被加密两次得到的密文 $(g^r, m \cdot h^r)$ 和 $(g^{r'}, m \cdot h^{r'})$ 分布完全不同。

**随机化的意义**：
- 保证了IND-CPA安全性：攻击者不能通过比较密文来确定加密的是哪个消息。
- 每次加密都重新生成临时密钥，即使多次加密同一明文，结果也不同。
- 随机数 $r$ 必须是真随机的：如果 $r$ 可预测或重复，加密安全性完全崩溃（攻击者可以恢复共享秘密 $h^r$）。

**随机数 $r$ 的管理**：与对称密码的Nonce不同，这里的 $r$ 必须在每次加密时重新随机生成，且不能重复。如果两个加密使用相同的 $r$，攻击者可以通过 $c_2 / c_2' = m / m'$ 恢复消息的比值，并且如果知道 $m$ 就能恢复 $m'$。

#### 乘法同态性

ElGamal具有乘法同态性：

$$E(m_1) \cdot E(m_2) = (g^{r_1}, m_1 \cdot h^{r_1}) \cdot (g^{r_2}, m_2 \cdot h^{r_2}) = (g^{r_1+r_2}, (m_1 \cdot m_2) \cdot h^{r_1+r_2}) = E(m_1 \cdot m_2)$$

**同态加密的意义**：给定两个密文 $E(m_1), E(m_2)$，任何人都可以（在不知道私钥的情况下）计算 $E(m_1 \cdot m_2)$。这使ElGamal成为部分同态加密（PHE）的经典例子。

**应用场景**：
- **电子投票**：投票可以加密后以同态方式累加（假设"是"=1，"否"=0，票数加成）。
- **密封投标**：投标人可以提交加密投标，然后打开时证明总和正确。
- **隐私保护计算**：在密文上执行乘法运算。

**局限性**：ElGamal是乘法同态，不是加法同态（Paillier加密是加法同态）。如果要实现加法同态，可以通过将消息编码为 $g^m$ 的形式实现加法（因为 $g^{m_1} \cdot g^{m_2} = g^{m_1+m_2}$），但这只能用于小消息（因为离散对数不可计算）。

#### 重随机化

重随机化（Re-randomization）是ElGamal的另一个重要特性：给定一个ElGamal密文 $(c_1, c_2)$，任何人可以对它"重新随机化"——产生另一个密文 $(c_1', c_2')$，解密后得到相同的明文，但密文看起来完全不同。

**重随机化方法**：选择随机 $r'$，计算：
$$c_1' = c_1 \cdot g^{r'} = g^{r+r'}$$
$$c_2' = c_2 \cdot h^{r'} = m \cdot h^{r+r'}$$

**为什么重随机化有价值？**

1. **匿名化**：在电子投票中，一个投票被处理后，重随机化可以切断密文与原始投票者的联系。即使攻击者知道了某个密文对应某个投票人，重随机化后的密文在计算上无法与原始密文关联。

2. **混合网络（Mix Network）**：多个服务器依次重随机化并重新排序密文，打破输入输出对应关系。这对于匿名通信（如Tor中的Mix思路）和电子投票至关重要。

3. **可验证洗牌**：在重新排序和重随机化后，可以通过零知识证明证明操作的正确性（不减码也不替换密文），但不泄露原始的对应关系。

**与同态结合**：重随机化 + 乘法同态使ElGamal成为构建更复杂密码协议（如阈値加密、可验证秘密共享、分布式密钥生成）的基础构件。

### 4.4 椭圆曲线密码

#### ECC密钥

椭圆曲线密码（Elliptic Curve Cryptography, ECC）使用椭圆曲线上的点群代替传统有限域的乘法群。

**椭圆曲线的方程**（Weierstrass形式）：
$$y^2 = x^3 + ax + b \pmod{p}$$

**椭圆曲线群**：由曲线上所有点 $(x, y)$ 加上一个无穷远点 $\mathcal{O}$（单位元）组成，定义加法运算。椭圆曲线上的点加法具有群结构。

**标量乘法**：$Q = k \cdot P = P + P + \cdots + P$（$k$ 次）。这是ECC的核心操作。从 $k$ 和 $P$ 计算 $Q$ 是容易的（$O(\log k)$ 次点加），但从 $Q$ 和 $P$ 恢复 $k$ 是困难的（椭圆曲线离散对数问题，ECDLP）。

**ECC密钥生成**：
- 私钥：随机整数 $d \in [1, n-1]$，其中 $n$ 是基点 $G$ 的阶。
- 公钥：$Q = d \cdot G$（$G$ 是标准化的基点）。

**ECC的优势**：与RSA和DSA相比，ECC在相同安全级别下使用更短的密钥。例如：

| 安全级别 | RSA密钥长度 | ECC密钥长度 |
|---------|------------|------------|
| 80位 | 1024位 | 160位 |
| 112位 | 2048位 | 224位 |
| 128位 | 3072位 | 256位 |
| 256位 | 15360位 | 512位 |

**效率意义**：256位ECC密钥的计算速度比3072位RSA快约10倍。在资源受限的环境中（智能卡、移动设备、IoT设备），ECC的短密钥和快速计算是巨大优势。

**标准曲线**：NIST P-256（secp256r1）、secp256k1（Bitcoin）、Curve25519（X25519）、Curve448。

#### ECDH

椭圆曲线Diffie-Hellman（ECDH）是Diffie-Hellman密钥交换的椭圆曲线版本：

1. Alice生成密钥对：私钥 $a$，公钥 $A = a \cdot G$。
2. Bob生成密钥对：私钥 $b$，公钥 $B = b \cdot G$。
3. Alice计算共享秘密：$S = a \cdot B = a \cdot (b \cdot G) = ab \cdot G$。
4. Bob计算共享秘密：$S = b \cdot A = b \cdot (a \cdot G) = ab \cdot G$。
5. 双方得到相同的 $S$。

**安全性**：ECDH的安全性基于椭圆曲线计算Diffie-Hellman（ECDH）假设——给定 $aG$ 和 $bG$，计算 $abG$ 是困难的。这与传统DH类似，但使用更短的密钥。

**为什么推荐Curve25519（X25519）？**
- 使用蒙哥马利形式 $y^2 = x^3 + 486662x^2 + x$，支持仅使用 $x$ 坐标的计算（不需要处理 $y$ 坐标，节省带宽）。
- 使用扭曲安全（twist security）设计，抵抗相关的不安全曲线攻击。
- 常数时间实现，没有侧信道漏洞。
- 无需验证公钥是否在曲线上——因为X25519的设计保证输入总是安全的（即使是低阶点）。

**X25519（用于TLS 1.3）**：是目前TLS 1.3中部署最广泛的密钥交换算法，以Curve25519为基础。

#### ECIES

椭圆曲线集成加密方案（Elliptic Curve Integrated Encryption Scheme, ECIES）是混合加密的ECC实现。

**ECIES流程**：

1. **密钥生成**：
   - 接收者：私钥 $d$，公钥 $Q = d \cdot G$。

2. **加密**：
   - 发送方选择临时密钥对 $(k, R = k \cdot G)$。
   - 计算共享秘密 $S = k \cdot Q = kd \cdot G$（点）。
   - 将 $S$ 通过KDF派生对称密钥：$K_e \| K_m = \text{KDF}(S_x)$（$S_x$ 是 $S$ 的x坐标）。
   - 使用对称加密加密消息：$c = E_{K_e}(m)$。
   - 使用MAC认证：$t = \text{MAC}_{K_m}(c)$。
   - 输出：$(R, c, t)$。

3. **解密**：
   - 计算 $S = d \cdot R = dk \cdot G$。
   - 派生对称密钥同上。
   - 验证MAC，解密。

**为什么ECIES使用KDF？** ECDH共享秘密是曲线上的一个点，它的分布可能不均匀（有偏）。KDF将共享秘密提取为均匀的对称密钥，消除了这种偏置。

**与RSA-OAEP的比较**：
- RSA-OAEP：加密直接用RSA（慢），消息长度受限于RSA模数。
- ECIES：加密使用对称密码（快），消息长度无限制（数据加密部分与公钥无关）。
- ECIES提供认证加密（因为使用了MAC），RSA-OAEP不提供。
- ECIES需要临时密钥对（计算量和通信成本略高）。

#### ECDSA

椭圆曲线数字签名算法（ECDSA）是DSA的椭圆曲线版本。

**签名（对消息 $m$）**：
1. 计算 $e = H(m)$。
2. 选择随机临时密钥 $k \in [1, n-1]$（每签名一次必须重新随机生成）。
3. 计算 $R = k \cdot G$，取 $r = R_x \mod n$。
4. 计算 $s = k^{-1}(e + r \cdot d) \mod n$。
5. 签名对：$(r, s)$。

**验证**：
1. 计算 $e = H(m)$。
2. 计算 $u_1 = e \cdot s^{-1} \mod n$，$u_2 = r \cdot s^{-1} \mod n$。
3. 计算 $P = u_1 \cdot G + u_2 \cdot Q$（$Q$ 是签名者的公钥）。
4. 验证 $P_x \equiv r \pmod{n}$。

**ECDSA的注意事项**：

1. **$k$ 必须唯一且保密**：如果两次签名使用相同的 $k$，可以解方程恢复私钥 $d$。此外，如果 $k$ 被泄露（如通过侧信道），私钥也立即泄露。著名的Sony PlayStation 3签名密钥就是因为使用固定的 $k$ 而被破解。

2. **$k$ 必须是真随机数**：攻击者不能预测 $k$ 的任何比特。如果 $k$ 的生成有偏差（如某些字节偏向0），攻击者可以收集多个签名恢复私钥（如通过格攻击lattice attack）。

3. **哈希是关键**：必须对消息哈希后再签名。如果直接签名消息，攻击者可利用ECDSA的代数结构构造选择性伪造（例如，签名随机值然后声称这是对某消息的签名）。

**为什么ECDSA需要恢复公钥？** 在某些场景中（如以太坊交易），记录签名和消息即可恢复签名者的公钥。这使得交易可以包含签名（r, s, v），而不需要显式包含公钥。以太坊利用这个特性将交易费用与签名者关联。

#### EdDSA

EdDSA（Edwards-curve Digital Signature Algorithm）是Ed25519和Ed448的签名算法，由Daniel Bernstein等人设计。

**与ECDSA的关键区别**：

1. **确定性签名**：EdDSA使用确定性 $k$ 生成（基于私钥和消息哈希派生临时密钥），而非随机选择。这消除了$k$重用和$k$随机性不足的风险。

2. **不使用ECDSA的模逆运算**：避免模逆运算是降低实现复杂度的关键。

3. **单一曲线**：EdDSA专为Edwards曲线设计（Ed25519使用Curve25519的扭曲Edwards形式）。避免了ECDSA中多条曲线带来的实现和标准化问题。

4. **批量验证**：EdDSA支持对多个签名同时验证，速度比单独验证更快。

**EdDSA的签名过程**：
1. 哈希私钥和消息：$r = H(sk \| m)$（确定性的 $r$）。
2. 计算 $R = r \cdot G$。
3. 计算 $h = H(R \| Q \| m)$。
4. 计算 $S = r + h \cdot sk \mod n$。
5. 签名对：$(R, S)$。

**EdDSA的优势**：
- 确定性：消除了随机数生成器出错的风险。
- 速度：比ECDSA快约2-3倍。
- 安全性：经过严格的密码分析，没有已知的有效攻击。
- 在签名中显式包含 $R$ 和 $S$，避免了ECDSA中的 $r$ 恢复问题。

**为什么选择EdDSA？** 在可用的情况下，EdDSA（特别是Ed25519）是所有场景的首选签名方案。它比ECDSA更简单、更快、更安全。TLS 1.3原生支持EdDSA，SSH、OpenPGP、Signal等协议都已迁移到Ed25519。

### 4.5 密钥交换与KEM

#### Diffie–Hellman密钥交换

Diffie-Hellman（DH）密钥交换允许两个通信方在不安全的信道上建立共享秘密。

**基本协议**：

1. 选择公共参数：大素数 $p$ 和生成元 $g \in \mathbb{Z}_p^*$（或椭圆曲线群参数）。
2. Alice选择私钥 $a$，计算公钥 $A = g^a \mod p$，发送 $A$。
3. Bob选择私钥 $b$，计算公钥 $B = g^b \mod p$，发送 $B$。
4. Alice计算共享秘密 $S = B^a = (g^b)^a = g^{ab} \mod p$。
5. Bob计算共享秘密 $S = A^b = (g^a)^b = g^{ab} \mod p$。

**安全性**：基于计算Diffie-Hellman（CDH）假设和判定性Diffie-Hellman（DDH）假设。被动攻击者看到 $A, B$ 不能计算 $g^{ab}$（CDH假设）。

**为什么不能直接使用 $g^{ab}$？** $g^{ab}$ 通常不直接用作对称密钥，因为其分布可能不均匀。需要经过KDF后使用。

**DH的问题**：
1. **无认证**：DH本身不认证通信双方的身份。攻击者可以在中间截获并替换公钥（中间人攻击）。
2. **静态DH不安全**：如果长期使用同一私钥 $a$，存在Identity Hiding和forward secrecy的问题。
3. **性能**：传统模运算DH（$\mathbb{Z}_p^*$）的计算开销比ECDH大很多。

#### 中间人攻击

中间人攻击（Man-in-the-Middle, MitM）是DH面临的主要威胁：

**攻击过程**：
1. Alice发送 $A$ 给Bob，攻击者M拦截。
2. M生成自己的密钥对 $(a', A' = g^{a'})$，发送 $A'$ 给Bob（冒充Alice）。
3. Bob以为收到Alice的公钥，发送 $B = g^b$。
4. M拦截后，发送 $B' = g^{b'}$ 给Alice（冒充Bob）。
5. Alice计算 $S_1 = (B')^a = g^{ab'}$。
6. Bob计算 $S_2 = (A')^b = g^{a'b}$。
7. M可以计算 $S_1 = B^a$ 和 $S_2 = A^b$。

**结果**：Alice和Bob各自认为与对方建立了秘密信道，但实际上M与Alice共享 $S_1$，与Bob共享 $S_2$。M可以解密来自Alice的消息，读取后再用 $S_2$ 加密发送给Bob（或篡改消息）。

**防御MitM**：必须使用**认证密钥交换**（AKE）。核心方法是引入身份验证，确保公钥来源可信。实现方式包括：
- **签名**：双方使用长期签名密钥对DH公钥签名。
- **静态DH**：将长期公钥嵌入DH计算结果中。
- **口令认证密钥交换（PAKE）**：使用弱口令认证，如SRP。
- **PKI**：通过证书认证公钥的真实性。

#### 认证密钥交换

认证密钥交换（Authenticated Key Exchange, AKE）在DH的基础上增加了身份认证，防止中间人攻击。

**常见AKE协议**：

1. **Station-to-Station（STS）协议**：
   - 双方执行DH交换获得共享秘密 $S$。
   - Alice向Bob发送 $\text{Sign}_{sk_A}(A \| B)$（用长期签名密钥签名交换的公钥）。
   - Bob向Alice发送 $\text{Sign}_{sk_B}(A \| B)$。
   - 双方验证签名，确保交换的公钥来自声明方。

2. **签名DH（TLS 1.2的DHE-RSA）**：
   - 服务器用长期RSA密钥对DH参数签名。
   - 客户端用服务器的证书公钥验证签名。
   - 建立的会话通过签名得到认证。

3. **MQV / HMQV**：高效的两轮AKE协议，将长期密钥和临时密钥结合计算共享秘密。HMQV（哈希化MQV）在标准的ROM下被证明安全。

4. **TLS 1.3**：使用以下AKE方式之一：
   - (EC)DHE + 签名：临时DH + 服务器签名。
   - PSK + (EC)DHE：预共享密钥 + 临时DH的混合。
   - PSK only：仅使用预共享密钥。

**核心原则**：临时DH（ephemeral DH）提供前向安全（Forward Secrecy）——即使长期密钥泄露，过去的会话密钥也不能被恢复。长期签名提供认证——确保公钥来源可信。

#### Key Encapsulation Mechanism

密钥封装机制（Key Encapsulation Mechanism, KEM）是公钥密码的一种抽象，专门用于在通信双方之间安全传输对称密钥。

**KEM vs. 公钥加密**：
- 公钥加密可以加密任意消息。
- KEM只能封装（安全传输）一个随机选定的对称密钥。

**KEM的API**：

$$\text{KEM.KeyGen}(1^\lambda) \to (pk, sk)$$
$$\text{KEM.Encaps}(pk) \to (c, k)$$
$$\text{KEM.Decaps}(sk, c) \to k$$

其中 $c$ 是封装（密文），$k$ 是对称密钥。

**为什么KEM存在？**

1. **安全性简化**：KEM只需要安全地传输一个随机生成的对称密钥，这比公钥加密整个消息更容易设计和证明安全。KEM的IND-CCA安全性（不可区分性）的证明比公钥加密方案的证明更简洁。

2. **实际使用模式匹配**：几乎所有实际使用中，公钥密码都用于加密对称密钥（混合加密）。KEM直接支持这个使用模式。

3. **抵抗填充攻击**：KEM不需要处理消息填充（OAEP等），减少了实现出错的概率。例如，RSA-KEM比RSA-OAEP实现更简单且安全。

4. **后量子密码的基础**：大多数后量子密码方案（如Kyber）被设计为KEM而非公钥加密。NIST的后量子密码竞赛中，标准化的KEM方案（CRYSTALS-Kyber）将成为主流。

**RSA-KEM**：
- Encaps：随机选择 $k \in \{0,1\}^{256}$，计算 $c \equiv k^e \pmod{n}$，输出 $(c, k)$。
- Decaps：计算 $k \equiv c^d \pmod{n}$。
- 安全性要求 $k$ 的分布均匀且与RSA模数匹配（所以 $k$ 通常经过哈希或OAEP填充后使用）。

#### KEM与公钥加密的关系

KEM和公钥加密（PKE）之间存在紧密的理论关系——它们可以互相转化：

**从PKE到KEM**：给定一个公钥加密方案 $(\text{Gen}, \text{Enc}, \text{Dec})$，可以构造KEM：
- Encaps($pk$)：生成随机 $k$，计算 $c = \text{Enc}_{pk}(k)$，输出 $(c, k)$。
- Decaps($sk, c$)：计算 $k = \text{Dec}_{sk}(c)$。

**从KEM到PKE（混合加密）**：给定KEM和对称加密（DEM），可以构造公钥加密：
- Enc($pk, m$)：$(c_1, k) = \text{KEM.Encaps}(pk)$；$c_2 = \text{DEM.Enc}_k(m)$；输出 $(c_1, c_2)$。
- Dec($sk, (c_1, c_2)$)：$k = \text{KEM.Decaps}(sk, c_1)$；$m = \text{DEM.Dec}_k(c_2)$。

**安全性关系**：
- 如果KEM是IND-CCA安全的，且DEM是IND-CCA安全的，则混合加密是IND-CCA安全的。
- 分离KEM和DEM的安全性使得分析变得更简单：只需要证明每个组件（KEM和DEM）的安全性，然后通过组合定理得到整体安全性。

**现代趋势**：新一代公钥密码标准（如HPKE——Hybrid Public Key Encryption）完全围绕KEM/DEM框架设计。TLS 1.3虽然名义上使用ECDH密钥交换，但实际上也遵循了KEM的思路——使用临时DH作为KEM，派生对称密钥作为DEM密钥。

#### 混合密钥交换

混合密钥交换（Hybrid Key Exchange）结合两种或多种密码系统的安全性。即使其中一种被攻破，协议仍然保持安全。

**为什么需要混合？**
1. **量子威胁**：现有公钥密码（RSA、ECDH、ECDSA）在未来量子计算机上会被Shor算法破解。但后量子密码（如格密码）的信任度还不够高——可能存在尚未发现的攻击。
2. **保守防御**：任何单一密码系统都可能在某天被攻破。混合使用多种系统提供了冗余安全。
3. **标准化过渡**：在从经典密码向后量子密码过渡期间，混合实现允许同时部署两种系统。

**TLS 1.3的混合方案**（TLS混合密钥交换草案）：
- 同时执行两个KEM：经典KEM（如X25519）和后量子KEM（如Kyber-512）。
- 组合两个共享秘密：$S_{\text{combined}} = S_{\text{classic}} \| S_{\text{pq}}$。
- 使用KDF从组合秘密派生会话密钥。

**混合的安全特性**：
- **任一种安全则整体安全**：只要经典KEM和后量子KEM中至少一个是安全的，混合KEM就是安全的。
- **对称密钥安全由两者共同保护**：攻击者需要同时破解两个KEM才能计算会话密钥。
- **不增加轮数**：混合密钥交换通常可以在现有的握手轮数内完成（如将后量子KEM的公钥和密文附加到TLS握手中）。

**实践中的混合**：
- Google的"New Hope"实验：在Chrome和Google服务器之间部署了X25519 + NewHope的混合密钥交换。
- Cloudflare的SIDH实验：在TLS中部署了X25519 + SIKE（不过SIDH/SIKE后来被发现可被攻破，这恰恰说明了混合部署的谨慎——如果部署的是纯SIKE，影响会更严重）。
- NIST后量子密码标准：计划将CRYSTALS-Kyber作为KEM标准，并与现有ECDH混合使用以实现过渡。

**混合的未来**：在量子计算成熟前，行业将逐步采用混合密钥交换（ECDH + Kyber、ECDH + Dilithium签名等）。过渡策略包括：
1. 先增加混合密钥交换（不影响现有系统）。
2. 再逐步淘汰经典算法（当后量子密码的信任度足够高时）。
3. 保持长期兼容性（同时支持多种密码套件）。

混合密钥交换体现了密码工程中的一个重要原则：**不要把所有鸡蛋放在一个篮子里**。通过同时依赖多种密码原语，确保即使其中一个被攻破，系统仍然安全。
